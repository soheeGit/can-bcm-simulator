| 확인 | 예상 | 실제 |
| --- | --- | --- |
| 1.8 ~ 2.4초 차속 프레임의 데이터 (`D205`, `E605` ...)는 몇 km/h인가 | 5km/h | ❌ **14.90 / 15.10 km/h**. 리틀 엔디안이라 `data[0]`(`D2`)이 낮은 자리, `data[1]`(`05`)이 높은 자리 → `0x05D2` = 1490 → 14.90 km/h. `E605` → `0x05E6` = 1510 → 15.10 km/h. `05`만 보면 5처럼 보이지만 그건 **높은 바이트**라서 5 × 256 = 1280을 뜻한다 |
| 처음으로 잠기는 시각과 규칙 | 1.9초 | ✅ 1.9초, **T3** (1.8초는 14.90이라 아직 15 미만, 1.9초가 처음 15.10) |
| 잠금 명령 횟수 | 1회 | ✅ 1회 |
| 상태 전이 횟수 |  | **2회**: 1.9초 IDLE → DRIVING_LOCKED (T3), 7.5초 DRIVING_LOCKED → IDLE (T7) |

- 14.90 ↔ 15.10을 30번 오가는데 잠금이 한 번뿐인 이유 → 속도가 왔다갔다 했을때, 계속 잠금 해제와 잠금이 반복되면 안되기 때문에 🔺 (그래야 하는 **이유**는 맞다. 코드가 **어떻게** 그렇게 만드는지도 적어 둔다)
  - **다시 잠그지 않는 이유:** 잠금 규칙 T3은 **IDLE 줄**이다. 1.9초에 DRIVING_LOCKED가 된 뒤로는 `switch`에서 `case BCM_STATE_DRIVING_LOCKED:`만 보니까 T3은 **확인조차 안 한다** → 15.10이 몇 번 와도 잠금 명령이 안 나간다
  - **풀리지 않는 이유:** DRIVING_LOCKED에서 빠져나가는 T7은 "**0 km/h + P단**"이다. 14.90은 0이 아니니 T7이 안 맞는다 → 상태 그대로
  - 즉 들어가는 문턱(15.00)과 나오는 문턱(0 + P)이 **다르기** 때문 = 히스테리시스. 둘이 같았다면(15.00) 14.90에서 풀리고 15.10에서 또 잠근다 (2번 실험)
- 5.8 ~ 7.0초에 감속하면서 15 km/h 아래로 내려가는데도 아무 일이 없는 이유 → 위와 같다. 해제 조건은 "15 미만"이 아니라 **"0 km/h + P단"**이라서, 15 아래로 내려가는 것만으로는 아무 규칙도 안 맞는다
  - 7.0초에 0 km/h가 되어도 아직 **기어 D**(`300#0203...`의 `03`)라 T7이 안 맞는다 → 신호 대기처럼 잠금 유지
  - 7.5초에 기어가 **P**(`300#0200...`의 `00`)로 바뀌는 순간 0 km/h + P → **T7**로 IDLE

- 실제 차였다면 무슨 일이 일어났을까 → 막히는 길에서 3초 동안 문 잠금 모터가 **16번 "철컥"** 거린다 (0.2초마다). 운전자는 고장이라고 생각하고, 모터와 걸쇠는 빨리 닳는다. 게다가 0.1초마다 "잠김 / 안 잠김"이 바뀌니 그 사이에 문이 **잠기지 않은 순간**이 계속 생긴다
  - 경고도 마찬가지: 경고 해제 문턱을 3 km/h로 했다면 2 ↔ 4 km/h에서 경고음이 "삑-뚝-삑-뚝" 끊긴다

- 이렇게 "코드를 일부러 망가뜨려서 테스트가 잡는지 보는 것"을 무엇이라고 부르고, 왜 하나 → **뮤테이션 테스트(mutation testing)**. 코드에 작은 돌연변이(mutant)를 넣어서, 테스트가 그걸 **잡으면(실패하면)** 좋은 테스트, **못 잡으면(그래도 통과하면)** 그 부분을 지키는 테스트가 없다는 뜻
  - 왜 하나: "테스트가 다 통과한다"는 것만으로는 테스트가 **제대로 지키고 있는지** 모른다. 아무것도 확인하지 않는 테스트도 통과는 하니까. 이번 실험으로 "히스테리시스가 깨지면 13개가 잡는다"는 걸 **증명**했다
  - 테스트 커버리지(몇 줄이 실행됐나)보다 한 단계 더 강한 확인. 커버리지 100%여도 `ASSERT`가 없으면 버그를 못 잡는다
  - Java에는 **PIT**(pitest)라는 도구가 있어서 `>`를 `>=`로, `&&`를 `||`로 자동으로 바꿔 가며 수백 번 돌려 준다. 우리는 손으로 한 번 해 본 것
  - M4-3 0번에서 `next`를 빠뜨렸을 때 테스트가 잡은 것도 사실상 같은 경험이었다 (실수 = 자연 발생한 돌연변이)

## 3. 문턱 상수

```c
#define BCM_LOCK_SPEED_CENTI     1500u  /* 15.00 km/h 이상이면 자동 잠금 */
#define BCM_STOPPED_SPEED_CENTI  0u     /* 0.00 km/h = 정차 */
#define BCM_MOVING_SPEED_CENTI   300u   /* 3.00 km/h 초과면 "달리는 중" */
```

- `c.speed == 0u`도 뜻이 분명한데 굳이 `BCM_STOPPED_SPEED_CENTI`를 만든 이유 → **"이 0은 히스테리시스의 나오는 문턱"이라는 걸 드러내려고.** 숫자 `0`만 보면 "그냥 0"인지 "설계에서 정한 값"인지 알 수 없다
  - **문턱이 한곳에 모인다:** `bcm.h`를 열면 들어가는 문턱(1500), 나오는 문턱(0), 달리는 중(300)이 **나란히** 보인다. 히스테리시스는 "두 문턱의 **간격**"이 핵심이라, 둘이 한눈에 보여야 간격을 판단할 수 있다
  - **바뀔 수 있는 값이다:** 실제 차에서는 센서 노이즈 때문에 정차해도 0.05 km/h처럼 0이 아닌 값이 올 수 있다. 그러면 "1 km/h 미만 = 정차"로 바꿀 수도 있다. 상수로 두면 그때 **한 줄**만 고치면 T7과 T11이 같이 바뀐다 (`c.speed == 0u`가 두 군데 흩어져 있으면 하나만 고치는 실수가 생긴다). 단, 조건을 `==`에서 `<=`로 바꾸는 건 코드도 고쳐야 한다
  - **검색이 된다:** `grep BCM_STOPPED_SPEED_CENTI`로 "정차를 판단하는 곳"을 전부 찾을 수 있다. `0u`로 검색하면 상관없는 0이 수십 개 나온다
  - M1-1의 "매직 넘버 대신 상수(`MSG_ID_VEHICLE_SPEED`)"와 같은 이유. 이슈 할 일의 "매직 넘버 금지"가 이것
- 이슈의 "`#define` 또는 설정 구조체" 중 `#define`을 고른 이유. 설정 구조체(`BcmConfig`)라면 무엇이 좋아지나 → 지금은 문턱이 **프로그램 실행 중에 바뀔 일이 없어서** `#define`이 가장 단순하다

| | `#define` (지금) | 설정 구조체 `BcmConfig` |
| --- | --- | --- |
| 모양 | `#define BCM_LOCK_SPEED_CENTI 1500u` | `typedef struct { uint16_t lock_speed_centi; ... } BcmConfig;` → `bcm_init(&ctx, &cfg)` |
| 값이 정해지는 때 | **컴파일할 때** (바꾸려면 다시 빌드) | **실행할 때** (파일, 옵션에서 읽을 수 있음) |
| 메모리 | 안 씀 (숫자가 코드에 박힘) | 구조체만큼 씀 |
| 차종마다 다른 값 | 차종마다 따로 빌드 | 같은 프로그램에 설정만 바꿔서 |
| 테스트 | 모든 테스트가 같은 문턱 | 테스트마다 다른 문턱을 넣어 볼 수 있음 |

  - 설정 구조체가 좋아지는 경우: "SUV는 20 km/h, 세단은 15 km/h"처럼 **같은 코드를 여러 설정으로** 쓸 때. 실제 ECU에서는 이런 값을 **캘리브레이션 파라미터**라고 부르고, 생산 라인에서 차종별로 써 넣는다 (코딩 / 변형 코딩, variant coding)
  - 지금 바꾸면 `bcm_init`, `bcm_step`의 매개변수와 테스트가 모두 바뀌어야 한다 → 필요해질 때 바꾸는 게 낫다 (YAGNI: You Aren't Gonna Need It)
  - Java로 치면 `#define` = `static final int LOCK_SPEED = 1500;`, 설정 구조체 = `@ConfigurationProperties`로 `application.yml`에서 읽는 값

## 4. 잠금 명령: 진입 시 1회 vs 유지 중 계속

- 이 프로젝트의 결정과 이유 (`fsm-design.md` 6번) → **진입 시 1회.** `door_lock_cmd`는 T3이 실행된 그 판단에서만 1이고, DRIVING_LOCKED에 머무는 동안은 0이다 (Mealy 출력, 23번 노트 4번)
  - 이유: 잠금은 **모터를 돌리는 동작**이다. "유지 중 계속"이면 0x400을 보낼 때마다(100ms) "잠가라"가 나가서 모터가 계속 돈다
  - "잠가라"는 **명령(한 번 하면 되는 일)**이고, "경고음 ON"은 **상태(계속 유지돼야 하는 것)**라서 보내는 방식이 다르다
  - 이번 M4-4 테스트가 확인하는 것: `test_lock_cmd_only_once`(같은 입력으로 3번 판단 → 잠금 1번), `test_hysteresis_lock_jitter`(14.90 ↔ 15.10 30번 → 잠금 1번), 시나리오 05의 `도어 잠금 명령 : 1회`
- "유지 중 계속"을 고르는 실제 차도 있다. 어떤 장점이 있을까 (힌트: 0x400 프레임 하나가 버스에서 사라지면) → **명령이 한 번 사라져도 다음 프레임에서 다시 전해진다**

```
진입 시 1회:    1.9초 [잠가라 ✉️] → 노이즈로 이 프레임이 깨짐 ❌ → 2.0초 [ - ] → 2.1초 [ - ] ...
                → 도어 제어기는 끝까지 못 받음 → BCM은 "잠금 주행", 실제 문은 안 잠김 😱

유지 중 계속:   1.9초 [잠가라 ❌ 깨짐] → 2.0초 [잠가라 ✅] → 2.1초 [잠가라] ...
                → 100ms 늦게라도 반드시 전해진다
```

  - CAN은 오류가 나면 송신 쪽이 자동으로 **재전송**하긴 하지만(M1), 버스가 꺼져 있었거나(수신 제어기가 아직 켜지는 중), 수신 쪽이 바빠서 놓치면 그 한 번은 사라진다
  - 그래서 실무에서는 둘을 섞는 경우가 많다
    - **N회 반복 후 멈추기:** 진입하면 3~5 프레임 동안 "잠가라"를 보내고 멈춘다 → 놓칠 확률은 줄이고 모터를 계속 돌리지는 않는다
    - **"명령"이 아니라 "원하는 상태"를 계속 보내기:** "잠가라"(이벤트) 대신 "잠겨 있어야 함 = 1"(상태)을 계속 보내고, **받는 쪽**이 "이미 잠겨 있으면 무시"한다 → 모터 반복 문제는 받는 쪽이 해결. Moore 출력처럼 된다
    - **확인 응답:** 도어 제어기가 "잠겼음" 신호를 돌려보내고, BCM은 그게 올 때까지 다시 보낸다 (웹의 ACK, 재시도와 같다)
  - 이 프로젝트는 파일 모드라 프레임이 사라지지 않으니 **1회**로 충분하다. M5(vcan 실시간)에서 이 결정을 다시 볼 수 있다
  - 웹으로 치면: 1회 = 메시지를 한 번만 보내는 "at-most-once", 계속 보내기 = "at-least-once"(중복은 받는 쪽이 멱등하게 처리). Kafka, 메시지 큐에서 고민하는 것과 같은 문제

- `test_hysteresis_lock_jitter`에서 14.90 ↔ 15.10 말고 **14.99 ↔ 15.00**도 넣은 이유 → **문턱에 딱 붙은 가장 작은 흔들림**도 확인하려고. 1499와 1500은 centi 단위로 **1 차이**(0.01 km/h)라, 이보다 더 촘촘하게 흔들릴 수는 없다
  - 15.00은 정확히 잠금 문턱이다 (`>=`라서 잠김). 그래서 이 쌍은 "문턱 **위**와 **바로 아래**"를 오가는 최악의 경우
  - 14.90 ↔ 15.10은 "현실적인 흔들림", 14.99 ↔ 15.00은 "경계값". M4-3의 1600 / 1500 / 1499 경계값 테스트(25번 노트 7번)와 같은 생각을 **반복**에 적용한 것
  - centi 정수라서 15.00과 14.99를 **정확히** 넣을 수 있다. float였다면 15.0이 14.9999...로 저장돼서 "경계"가 흐려졌을 것
- `test_hysteresis_warning_jitter`의 `buzzer_off_while_warning`이 세는 것 → **WARNING에 한 번 들어간 뒤로 경고음이 꺼진 판단의 횟수** = 경고음이 "깜빡인" 횟수

```c
if (out.state == BCM_STATE_WARNING) { entered_warning = true; }        /* 한 번이라도 들어갔으면 */
if (entered_warning && !out.warning_buzzer) { r.buzzer_off_while_warning++; }   /* 그 뒤로 꺼지면 +1 */
```

  - 기대값은 **0**: 문이 열린 채 2 km/h로 느려져도 경고음은 계속 울려야 한다 (경고 해제 문턱은 3이 아니라 **0**, T11)
  - 상태 전이 횟수(`transitions == 1`)만 봐도 되지만, 사람이 실제로 듣는 건 **경고음**이라 그걸 직접 센다. "삑-뚝-삑-뚝"을 숫자로 잡는 것
  - 처음 몇 번(WARNING에 들어가기 **전**)은 경고음이 꺼져 있는 게 정상이라 세지 않는다 → `entered_warning` 깃발이 필요한 이유
- `run_jitter()`가 `bcm_init`을 안 하고 **같은 ctx**로 계속 `bcm_step`을 부르는 이유 (다른 테스트의 `step_from()`과 비교) → 히스테리시스는 "**이전 상태에 따라** 결과가 달라지는 것"이라, 상태를 **이어서** 들고 가야 확인할 수 있다

| | `step_from()` (M4-3) | `run_jitter()` (M4-4) |
| --- | --- | --- |
| 하는 일 | 원하는 상태를 **직접 넣고** 판단 **1번** | 같은 ctx로 판단을 **30번 연속** |
| 확인하는 것 | 규칙 하나 (이 상태 + 이 입력 → 이 결과) | **시간에 따른 흐름** (30번 동안 몇 번 바뀌었나) |
| ctx | 매번 새로 설정 (given) | 앞 판단의 결과가 다음 판단의 시작 |

  - 매번 `bcm_init`을 하면 항상 IDLE에서 시작하니까, 15.10이 올 때마다 T3이 맞아서 잠금이 30번의 절반만큼 나온다 → 히스테리시스를 테스트할 수 없다 (실제 프로그램에서 `bcm_init`을 루프 안에서 부르는 버그와 같은 모양, 24번 노트 1번)
  - 그래서 `run_jitter()`는 실제 `log_read_stream`처럼 **`bcm_init` 한 번 + `bcm_step` 여러 번**으로 돌린다 → 단위 테스트이지만 시나리오처럼 "흐름"을 본다
  - 두 방식은 서로 보완한다: `step_from()`은 **한 줄씩 정확하게**, `run_jitter()`는 **이어 붙였을 때 깜빡이지 않는지**. M4-7의 표 기반 테스트는 앞쪽, 시나리오 통합 테스트는 뒤쪽을 키운 것
