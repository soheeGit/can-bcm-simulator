# 11. 범용 비트 추출 함수 `can_get_bits()` (M2-1)

> 코드: `include/can_signal.h`, `src/can_signal.c`, `tests/test_can_signal.c`
> 실행: `make test`

## 1. 이 함수가 하는 일

```c
uint32_t can_get_bits(const uint8_t data[8], uint8_t start_bit, uint8_t length);
```

- 한 줄 설명 → CAN 데이터 8바이트에서 start_bit부터 length비트만큼의 신호 값(raw)을 꺼낸다
- M1-3 연습 문제에서 손으로 했던 것과의 관계 → 정의서를 계속 보면서 했어야 했는데, 함수 하나면 끝난다 ✅ 더 정확히는: 손으로 했던 **바이트 합치기(문제 A) + 마스크로 자르기(문제 D)를 똑같은 순서로 자동화**한 것이다. 정의서는 여전히 필요하다 — "start 몇, 길이 몇"이라는 **숫자는 정의서에서** 가져와 넣는다. 함수는 계산만 대신 해준다
- 정의서의 신호를 이 함수로 꺼내면? (빈칸 채우기)

| 신호 | 정의서 | 호출 |
| --- | --- | --- |
| VehicleSpeed | start 0, 길이 16 | `can_get_bits(data, 0, 16)` |
| DoorFL | start 0, 길이 1 | `can_get_bits(data, 0, 1)` |
| Trunk | start 4, 길이 1 | `can_get_bits(data, 4, 1)` |
| Gear | start 8, 길이 3 | `can_get_bits(data, 8, 3)` |
| AliveCounter | start 56, 길이 4 | `can_get_bits(data, 56, 4)` |

## 2. 동작 원리 (2단계)

```c
/* 1) 8바이트를 Little-endian으로 하나의 64비트 숫자로 합친다 */
uint64_t word = 0;
for (i = 0; i < 8; i++) {
    word |= (uint64_t)data[i] << (8 * i);
}

/* 2) 밀어서 내리고, 마스크로 자른다 */
return (uint32_t)(word >> start_bit) & low_mask(length);
```

- 1단계에서 `data[i] << (8 * i)`의 의미 (i = 0, 1, 2일 때) → Little-endian 순서로 합친다는 뜻 ✅ 각 바이트를 **자기 자리까지 왼쪽으로 민다**: i = 0 → 0칸(비트 0~7), i = 1 → 8칸(비트 8~15), i = 2 → 16칸(비트 16~23). 뒤 바이트일수록 큰 자리로 간다
- 왜 `uint64_t`로 합치나? → 8바이트 전체 비트 수가 64이기 때문에 ✅
- `(uint64_t)data[i]`처럼 시프트 전에 형변환하는 이유 (M0-4 승격) → 안 바꾸면 `uint8_t`가 `int`(32비트)로 승격된 뒤 밀린다. `data[7]`은 56칸을 밀어야 하는데 32비트를 32칸 이상 밀면 UB → 먼저 64비트로 바꿔서 밀 공간을 만든다
- 2단계는 M0-5의 어떤 공식인가? → **"start부터 len비트 꺼내기"** `(x >> start) & ((1u << len) - 1u)` (밀어서 내리고, 마스크로 자르기)

### 손으로 따라가기: `{0x30, 0x12}`, start 4, 길이 12

```
1) word = 0x12 << 8 | 0x30 = 0x1230 = 0001 0010 0011 0000
2) word >> 4 = 0x0123          = 0000 0001 0010 0011
   mask(12) = 0x0FFF           = 0000 1111 1111 1111
   결과 = 0x123 (291)          = 0000 0001 0010 0011
```

## 3. `low_mask()` — 길이 32의 함정

```c
static uint32_t low_mask(uint8_t length) {
    if (length >= 32u) {
        return 0xFFFFFFFFu;
    }
    return (1u << length) - 1u;
}
```

- `if` 없이 `(1u << length) - 1u`만 쓰면 length = 32일 때 무슨 일이? (M0-6 실험 3) → 돌아서 0으로 적용된다. ✅ 맥에서는 `1u << 32`가 한 바퀴 돌아 `1u << 0` = 1 → `1 - 1` = **마스크 0** → 무엇을 꺼내든 결과가 **항상 0**이 된다 (원래 원한 마스크는 `0xFFFFFFFF`). 그리고 C 표준상 UB라 다른 CPU에서는 또 다른 값이 나올 수 있다 → 32는 따로 처리한다
- 이걸 확인하는 테스트 이름 → test_get_32bit_full ✅ (`test_get_32bit_upper_half`도 길이 32)

## 4. 잘못된 인자 처리 — 설계 결정

| 잘못된 경우 | 예시 |
| --- | --- |
| data가 NULL | `can_get_bits(NULL, 0, 8)` → 읽을 데이터가 없음 (그대로 읽으면 Segfault) |
| length가 0 | `can_get_bits(data, 0, 0)` → 꺼낼 비트가 없음 |
| length가 32보다 큼 | `can_get_bits(data, 0, 33)` → 반환 타입 `uint32_t`에 안 담김 |
| start + length가 64보다 큼 | `can_get_bits(data, 60, 8)` → 8바이트(64비트) 밖까지 읽게 됨 |

- 이 함수는 잘못된 인자에 **0을 반환**하기로 했다. 다른 방법과 비교:

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| ① 0 반환 (선택) | 사용법이 가장 간단하다 (`x = can_get_bits(...)` 한 줄). 프로그램이 멈추지 않는다 | 진짜 값 0과 "실패"를 **구분할 수 없다** |
| ② `bool` 반환 + 결과는 포인터로 (`bool can_get_bits(..., uint32_t *out)`) | 성공/실패를 **확실히 구분**한다 | 호출할 때마다 변수 준비 + `if` 검사가 필요해서 코드가 길어진다 |
| ③ `assert()`로 프로그램 중단 | 실수를 **즉시, 크게** 알려준다 (개발 중에 좋음) | 실제 차에서 제어기가 **멈추면 안 된다**. 그리고 배포 빌드(`NDEBUG`)에서는 assert가 사라져 검사도 없어진다 |

- ①을 고른 이유 (힌트: 인자는 어디서 오나? 런타임 데이터 vs 정의서 상수) → `start_bit`와 `length`는 CAN에서 들어오는 **런타임 데이터가 아니라**, 정의서를 보고 **코드에 적는 상수**다 (`can_get_bits(data, 8, 3)`). 그래서 잘못된 인자는 "실행 중에 생기는 일"이 아니라 **"프로그래머가 숫자를 잘못 적은 실수"**다
  - 이런 실수는 **테스트로 잡는다** → 신호마다 디코더 테스트(M2-3~5)를 만들면 잘못 적은 숫자는 바로 FAIL
  - 실행 중에는 절대 일어나지 않을 상황이므로, 호출할 때마다 `bool`을 검사하는 비용(②)을 낼 필요가 없다
  - 그래도 혹시 모를 실수에 **메모리 밖을 읽거나 UB가 나지 않도록** 0을 돌려주며 안전하게 끝낸다 (방어적 프로그래밍)
  - 반대로 **CAN에서 들어오는 값**(DLC, ID 등)은 런타임 데이터라서 실패가 실제로 일어난다 → 그쪽은 `can_frame_is_valid()`처럼 **bool로 결과를 알려준다**(M1-2)
  - Java로 치면: 프로그래머 실수 = `IllegalArgumentException`(테스트에서 잡을 버그), 런타임 데이터 오류 = 반드시 처리해야 하는 검증 실패

## 6. 구현 방식 비교 (이슈 할 일)

| 방식 | 설명 | 장단점 |
| --- | --- | --- |
| A. 64비트로 합쳐서 한 번에 (선택) | 8바이트를 `uint64_t` 하나로 합친 뒤 `>> start`, `& mask` 한 번 | 👍 코드가 짧고 M0-5 공식 그대로라 읽기 쉽다. 👍 손 계산(M1-3)과 순서가 같다. 👎 `uint64_t` 연산이 필요하다 (32비트 MCU에서는 조금 느릴 수 있음) |
| B. 비트 하나씩 반복 | `length`번 돌면서 비트 n을 `data[n / 8]`의 `n % 8`에서 하나씩 꺼내 결과에 붙인다 | 👍 64비트 타입이 필요 없다. 👎 반복문 안에 계산이 많아 실수하기 쉽고, 길이만큼 반복하니 느리다 |

```c
/* B 방식 참고 (안 쓴 코드) */
uint32_t value = 0;
for (uint8_t k = 0; k < length; k++) {
    uint8_t n = start_bit + k;                        /* 전체 비트 번호 */
    uint32_t bit = (data[n / 8] >> (n % 8)) & 1u;     /* 그 비트 하나 */
    value |= bit << k;                                /* 결과의 k번째 자리에 */
}
```

- A를 고른 이유 → **읽기 쉽고 정확한 게 우선**이다. 정의서의 "8바이트를 이어 붙인 비트 번호"를 코드가 그대로 표현한다 (64비트로 이어 붙이기). 테스트로 검증하기도 쉽다. 속도 차이는 신호 몇 개를 100ms마다 꺼내는 수준이라 의미가 없다. 나중에 성능이 문제가 되면 그때 측정하고 바꾼다
