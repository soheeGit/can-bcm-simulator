| 3.4초 | 0x300, 0x200만 옴 | **500ms** | DRIVING_LOCKED (유지) | `500 > 500`은 **거짓** → 아직 끊김 아님 |

| 7.0초 | 0 km/h, D | | DRIVING_LOCKED (유지) | T7 ❌ (D) |
| **7.5초** | P | | **IDLE** | T7 |

  - **왜 3.4초가 아닌가:** 끊김 조건이 `now - rx > 500`(**초과**)이라서, 딱 500ms인 3.4초는 아직 끊김이 아니다. 3.5초에 600ms가 되어 처음으로 참
  - **왜 하필 3.5초에 알아채나:** BCM은 **프레임이 들어올 때만** 판단한다 (fsm-design 8번). 차속이 끊겨도 0x300, 0x200은 100ms마다 오니까, 그때마다 "차속이 언제 마지막으로 왔지?"를 확인한다 → 3.4초 다음 판단 시점이 3.5초
  - **4.0초 한 시각 안에서 상태가 바뀌는 이유:** 같은 4.0초에도 프레임이 0x300 → 0x200 → 0x100 순서로 3개 오고, 프레임마다 판단한다. 앞의 두 번은 차속이 여전히 끊긴 상태라 WARNING, 마지막 0x100에서 차속이 돌아와 DRIVING_LOCKED
  - 마지막 차속 50 km/h를 계속 믿었다면, 3.0~3.9초 동안 실제 속도와 상관없이 "50 km/h로 잘 가고 있다"고 착각했을 것이다

## 3. FSM이란

- 상태 머신(FSM)을 한 문장으로 → **"지금 어떤 상태인지"를 하나 기억하고, 입력이 올 때마다 정해진 규칙(전이 표)에 따라 다음 상태로 바꾸는 것.** FSM = Finite State Machine (유한 상태 기계). "유한"은 상태의 개수가 정해져 있다는 뜻 (여기서는 3개)
  - 같은 입력이라도 **지금 상태에 따라** 결과가 다르다. 예: 문 열림 + 40 km/h → IDLE이면 T4, DRIVING_LOCKED이면 T6. 입력만 보는 게 아니라 "지금까지 어떻게 왔는지"(상태)를 같이 본다
  - 신호등이 대표적인 예: 빨강 → (시간 지남) → 초록 → 노랑 → 빨강
- Java/Spring에서 비슷한 것 (예: 주문 상태 `ORDERED → PAID → SHIPPED`) → 주문 상태를 `enum`으로 두고, "결제 완료" 이벤트가 오면 `ORDERED`일 때만 `PAID`로 바꾸는 코드가 바로 FSM이다

| 주문 시스템 | 이 BCM |
| --- | --- |
| `enum OrderStatus { ORDERED, PAID, SHIPPED, CANCELED }` | `IDLE`, `DRIVING_LOCKED`, `WARNING` |
| "결제 완료" 이벤트 | 프레임 도착 (차속, 문, 시동) |
| `if (status == ORDERED) status = PAID;` | `if (state == IDLE && 15 km/h 이상 ...) state = DRIVING_LOCKED;` |
| `SHIPPED`인데 결제 이벤트가 오면 무시/오류 | 표에 맞는 줄이 없으면 상태 유지 |
| 상태가 바뀔 때 메일 발송 | 상태가 바뀔 때 잠금 명령, 경고음 |
| Spring Statemachine | 이 프로젝트는 라이브러리 없이 `switch`로 직접 (M4-3) |

  - 차이: 주문은 **이벤트**(결제했다)가 오면 바뀌고, BCM은 **값**(차속이 몇이다)을 계속 보고 조건이 맞으면 바뀐다. 그래서 BCM은 같은 값이 100ms마다 계속 들어와도 상태가 그대로여야 한다
- 상태(state), 조건(guard), 동작(action)이 각각 무엇인지 전이 표의 칸과 연결해서 →

| 용어 | 뜻 | 전이 표의 칸 | 예 (T3) |
| --- | --- | --- | --- |
| 상태 (state) | 지금 어디에 있나 | "현재 상태", "다음 상태" | IDLE → DRIVING_LOCKED |
| 조건 (guard) | 이 전이를 해도 되나? (참일 때만 전이) | "조건" | `ign_run && speed ≥ 15 && all_closed` |
| 동작 (action) | 전이하면서 하는 일 | "동작" | 도어 잠금 명령, `locked = true` |

  - guard는 "문지기"라는 뜻. 조건을 통과해야 다음 상태로 들어갈 수 있다
  - 진입 동작(entry action): 어떤 상태에 **들어갈 때** 하는 일. 예: WARNING에 들어가면 경고음 ON. 이탈 동작(exit action): **나갈 때** 하는 일. 예: WARNING에서 나가면 경고음 OFF

## 4. Moore vs Mealy

- Moore 머신 / Mealy 머신의 차이 → **출력을 무엇으로 정하느냐**의 차이

| | Moore | Mealy |
| --- | --- | --- |
| 출력을 정하는 것 | **지금 상태만** | 상태 + **이번 전이(입력)** |
| 언제 출력이 나오나 | 그 상태에 있는 **동안 계속** | 전이가 **일어나는 순간만** |
| 비유 | 방에 불이 켜져 있다 (방에 있는 동안 계속 밝음) | 문을 열 때 "딩동" (여는 순간 한 번) |

- 이 설계에서 `warning_buzzer`는 어느 쪽이고, `door_lock_cmd`는 어느 쪽인가? 왜 그렇게 나눴나 →
  - `warning_buzzer` = **Moore**. `state == WARNING`이면 ON. WARNING에 있는 **동안 계속** 울려야 하니까 상태만 보면 된다. 어떤 길로 WARNING에 왔는지(T4, T5, T6)는 상관없다
  - `door_lock_cmd` = **Mealy**. **T3이 실행되는 그 순간만** 1. DRIVING_LOCKED에 있는 동안 계속 1이면 100ms마다 잠금 모터를 돌리게 된다. 그리고 같은 DRIVING_LOCKED로 와도 T3(IDLE에서)이면 잠그고 T9(WARNING에서)이면 안 잠근다 → **어느 전이로 왔는지**가 출력을 정한다
  - 정리: "**계속 유지돼야 하는 것**"(경고음, 상태 표시)은 Moore, "**한 번만 해야 하는 명령**"(잠금)은 Mealy. 실무 FSM도 이렇게 섞어 쓰는 경우가 많다

## 5. 우선순위 (표를 위에서부터 보는 이유)

- T1(시동 OFF)이 맨 위에 있는 이유 → **시동을 끄면 무조건 IDLE이어야 하기 때문.** 어떤 상태든, 다른 신호가 어떻든 상관없이 이겨야 한다. 시동을 끄면 다른 제어기들도 송신을 멈추니 신호가 끊기는 게 정상인데, T1이 아래에 있으면 T5/T8(신호 이상)이 먼저 맞아서 **시동을 꺼도 경고음이 계속** 울린다 (1번 표의 12번)
  - Spring Security의 필터 순서, `if-else if` 체인에서 "가장 강한 조건을 맨 위에" 두는 것과 같다
- DRIVING_LOCKED에서 문이 열려 있고 **동시에** 차속 신호가 끊기면 T5와 T6 중 무엇이 실행되나? 결과가 같다면 순서가 왜 중요한가 → **T5**가 실행된다 (위에 있으니까). 둘 다 WARNING으로 가서 결과는 같지만 순서가 중요한 이유:
  - **로그의 이유가 달라진다** (M4-3: `STATE DRIVING_LOCKED -> WARNING (T5: signal lost)`). 정비사가 로그를 볼 때 "문 때문"인지 "신호 고장 때문"인지가 다르다. 신호를 못 믿는 상태에서는 "문 열림"이라는 판단 자체를 믿을 수 없으니, 신호 이상을 먼저 보는 게 맞다
  - **조건을 계산할 때 안전하다**: T6의 `speed > 3`은 차속을 알아야 의미가 있다. T5가 먼저 "신호를 믿을 수 있나?"를 걸러 주니까, 아래 줄들은 신호가 믿을 만하다고 **가정하고** 쓸 수 있다
  - **결과가 다른 쌍도 있다**: WARNING의 T8(신호 이상이면 유지)과 T9(문 닫히면 복귀). 문은 닫혔는데 차속이 끊긴 상황에서 T9가 먼저면 → DRIVING_LOCKED로 갔다가 → 다음 프레임에 T5로 다시 WARNING → 또 T9 → ... **왔다 갔다** 반복한다. T8이 먼저라서 WARNING에 머문다

## 6. 히스테리시스

- 히스테리시스란 → **들어가는 문턱과 나오는 문턱을 다르게 두는 것.** 값이 문턱 근처에서 흔들려도 상태가 깜빡이지 않게 한다
  - 에어컨: 26도에 켜고 **24도**에 끈다. 둘 다 25도로 하면 25.0 ↔ 25.1을 오갈 때마다 켜졌다 꺼졌다 한다
  - 이 설계: 잠금은 **15 km/h 이상**, 해제는 **0 km/h + P**. 경고는 **3 km/h 초과**로 들어가서, 문이 열린 채로는 **0 km/h**가 되어야 나온다
- 잠금 문턱(15 km/h)과 해제 문턱(0 km/h + P)을 같은 값(예: 둘 다 15)으로 하면 무슨 일이 생기나 → 시내에서 14 ↔ 16 km/h를 오가면 **잠금 → 해제 → 잠금 → 해제**가 반복된다. 잠금 명령이 몇 초마다 나가서 잠금 모터가 계속 "철컥철컥" 돌고, 운전자는 고장이라고 느낀다. 모터 수명도 줄어든다
  - M4-4에서 "14.9 ↔ 15.1을 반복해도 잠금이 반복되지 않는다"는 테스트로 확인한다

## 7. Fail-safe

- Fail-safe란 → **고장이 나면 안전한 쪽으로 동작하는 것.** "모르면 위험하지 않은 쪽을 고른다"
  - 철도 신호: 신호기가 고장 나면 **빨간불**(정지)로. 엘리베이터: 전기가 끊기면 브레이크가 **걸린다**
  - 이 BCM: 판단에 필요한 신호를 믿을 수 없으면 → 경고(WARNING)로 운전자에게 알린다. 잠금 상태에서는 그 상태를 유지한다 (잠금을 풀지 않음)
  - 반대 개념 Fail-operational: 고장이 나도 기능을 **계속** 해야 하는 경우 (예: 조향, 브레이크). 그래서 이중화(부품 2개)를 한다. 기능 안전 표준 **ISO 26262**가 이런 걸 다룬다 (M4-6)
- 차속이 끊겼을 때 마지막 값(50 km/h)을 계속 믿으면 안 되는 이유 → **마지막 값은 "그때"의 값이지 "지금"의 값이 아니다.** 신호가 끊긴 동안 차는 급정거했을 수도, 더 빨라졌을 수도 있다. 50 km/h를 믿고 있으면 실제로는 멈춰서 문을 열어도 "50 km/h로 달리는데 문 열림"이라고 잘못 경고하거나, 반대로 진짜 위험을 놓칠 수 있다
  - 웹으로 치면 캐시 만료(TTL). 오래된 캐시를 계속 쓰면 틀린 데이터를 보여 준다. 그래서 500ms라는 **유효 기간**을 둔 것
- IDLE에서는 신호가 끊겨도 WARNING으로 가지 않게 한 이유 (T2) → IDLE은 **아무것도 안 하는 상태**라 이미 안전하기 때문. 신호를 모르면 잠그지 않는다 = IDLE에 머문다 = 그 자체가 Fail-safe
  - 시동 직후에는 다른 제어기가 아직 켜지는 중이라 신호가 하나도 안 와 있다. 이걸 "끊김"으로 보고 경고음을 울리면 **시동 걸 때마다** 삑 소리가 난다
- 기어를 `inputs_ok`에 넣지 않은 이유 → 기어는 **"정차 후 IDLE로 돌아갈지"(T7)**에만 쓰이기 때문. 기어를 모르면(`GEAR_INVALID`) T7이 안 맞아서 **DRIVING_LOCKED에 머물 뿐**이다. 잠금을 유지하는 건 위험하지 않다
  - 반대로 기어를 `inputs_ok`에 넣으면, 기어 신호 하나가 튀었을 때(시나리오 04의 2.2초) 달리는 중에 경고음이 울린다 → 쓸데없는 경고. "그 신호가 **어떤 판단에 쓰이는지**"를 보고 Fail-safe 대상을 고른다

## 8. `locked`를 상태와 따로 기억하는 이유

- `locked`가 없으면 WARNING에서 빠져나올 때 무엇을 모르게 되나 → **WARNING에 오기 전에 문을 잠갔었는지**를 모른다. WARNING으로 오는 길이 IDLE(T4)에서도, DRIVING_LOCKED(T5, T6)에서도 있어서, 문이 닫혔을 때 **어디로 돌아가야 할지** 정할 수 없다
  - 무조건 DRIVING_LOCKED로 돌아가면 → T4(문 열고 출발)로 온 경우 잠금 명령도 없이 "잠김"이라고 표시된다 (실제로는 안 잠겼는데)
  - 무조건 IDLE로 돌아가면 → 02의 5.0초에 IDLE로 갔다가 다음 프레임에 T3으로 **잠금 명령을 또** 낸다 (이미 잠겨 있는데)
- `locked`를 없애고 상태를 하나 더 만드는 방법(`WARNING_LOCKED`, `WARNING_UNLOCKED`)과 비교하면 →

| | `locked` 변수 (이 설계) | 상태를 나눔 |
| --- | --- | --- |
| 상태 개수 | 3개 | 4개 |
| 0x400 BcmState | 그대로 (0~2) | 2비트라 4개까지는 되지만, 받는 쪽(계기판)은 경고가 2종류일 필요가 없다 |
| 전이 표 | 짧다 | WARNING 줄이 거의 두 벌이 된다 |
| 장점 | 단순하다 | "기억"까지 전부 상태에 있어서 표만 보면 모든 게 보인다 (순수한 FSM) |

  - 이렇게 상태 말고 따로 기억하는 값을 **확장 상태(extended state)**라고 한다. UML 상태 머신, Spring Statemachine의 "extended state variables"와 같은 개념
  - 기억할 게 늘어날 때마다 상태를 나누면 상태가 곱으로 늘어난다 (상태 폭발). 그래서 "**외부에 보여 줄 모습**"은 상태로, "**내부 기억**"은 변수로 두는 경우가 많다

## 9. 빈틈 찾기

- 이 표에서 아직 동작이 이상하거나 정의가 애매한 조합을 하나 찾아본다 →
  - **빈틈 1: 정차 중에 도어 신호가 아예 끊기면 경고음이 멈추지 않는다.** DRIVING_LOCKED로 달리다가 D단으로 신호 대기(0 km/h) 중에 도어 제어기가 고장 나면 → T5로 WARNING → 그다음은 T8("신호 이상이면 유지")만 맞아서 **시동을 끌 때까지** 경고음이 계속 울린다. 차가 멈춰 있는데 계속 울리는 건 과하다
    - 고칠 방법 후보: "차속은 알고 0 km/h이면, 신호 이상이어도 경고음은 끈다" 같은 줄 추가. 대신 그러면 "고장 났다"는 사실을 운전자가 모르게 된다 → 경고등(별도 출력)으로 나누는 게 실차에 가깝다
  - **빈틈 2: 노이즈 한 번에 경고가 울린다.** 도어 신호가 한 프레임만 잘못 "열림"으로 와도 T6으로 바로 WARNING → 100ms 뒤 T9로 복귀 → 경고음이 "삑" 하고 끊긴다. 이건 **M4-5 디바운싱**(3회 연속 같은 값일 때만 인정)으로 막는다
  - **빈틈 3: 기어 신호가 계속 무효면 IDLE로 못 돌아간다.** 정차해서 P에 넣어도 기어 신호가 고장이면 DRIVING_LOCKED에 머문다. 위험하진 않지만(잠김 유지) 시동을 꺼야 풀린다
  - 셋 다 **위험하지는 않은 쪽**으로 틀려 있다 (경고가 과하거나, 잠금이 오래 유지됨). Fail-safe 설계에서는 "틀리더라도 안전한 쪽으로 틀리게" 하는 게 목표다. 1은 지금 고칠지, 문서에 "알려진 한계"로 남길지 정해야 한다
