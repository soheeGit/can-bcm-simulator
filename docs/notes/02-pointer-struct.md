# 02. 포인터, 배열, 구조체 (M0-3)

> 실험 코드: `playground/pointer/`
> 실행: `make -C playground/pointer run` (하나만: `./playground/pointer/build/01_pointer_basics`)
>
> 💡 각 실험은 **실행 전에 "예상" 칸을 먼저 채우고** 실행해서 "실제"와 비교하기

## 실험 1: 포인터 기초 (`01_pointer_basics.c`)

| 번호 | 예상 | 실제 |
| --- | --- | --- |
| [2] `&x` 와 [3] `p` 는 같은 값? | 같은 값 | 같은 값 |
| [4] `*p` | 10 | 10 |
| [5] `*p = 20` 이후 `x` | 20 | 20 |
| [7] `sizeof(int *)` | 4 | 8 |
| [8] `sizeof(char *)` | 4 | 8 |

- `&` 의 뜻 → 주소
- `*` 의 뜻 (선언할 때 `int *p` vs 사용할 때 `*p`) → 
    - 선언할 때 int *p: "p는 int를 가리키는 포인터 타입이다"
    - 사용할 때 *p: "p에 적힌 주소로 찾아가서 그 값을 읽거나 쓴다" (역참조)
- `int *`와 `char *`의 크기가 같은 이유 → 포인터는 "주소(칸 번호)" 하나만 담아서 무엇을 가리키든 크기가 같다. int, char는 "그 주소에서 몇 바이트를 읽을지"를 알려줄 뿐이다.
- 주석 실험 `*q = 1;` (NULL에 쓰기) 결과:

```
Segmentation fault: 11
```

- Java의 `NullPointerException`과 다른 점 → NULL(0번 주소) 근처는 OS가 일부러 막아둔 구역이라, 접근하면 CPU가 감지하고 OS가 프로세스를 강제 종료한다(SIGSEGV). Java처럼 예외를 던지는 게 아니라 프로그램이 그냥 죽는다.

## 실험 2: swap (`02_swap.c`)

| | 예상 x, y | 실제 x, y |
| --- | --- | --- |
| [1] `swap_value(x, y)` 후 | 1, 2 | 1, 2 |
| [2] `swap_pointer(&x, &y)` 후 | 2, 1 | 2, 1 |

- `swap_value` 안에서는 바뀌었는데 밖에서는 안 바뀐 이유 →  함수에 x, y의 값이 복사되어 넘어가서, 함수 안에서는 복사본(a, b)만 바뀌었다. 원본 x, y는 그대로다.
- `swap_pointer`는 왜 되나? → x, y의 주소를 넘겼기 때문에, 함수가 *a, *b로 그 주소에 찾아가서 원본 값을 바꿀 수 있다. (포인터 a, b 자체는 바뀌지 않는다)
- Java로 `int` 두 개를 swap하는 함수를 만들 수 있나? → 못 만든다. Java도 값을 복사해서 넘기고, 변수의 주소(&x)를 꺼낼 방법이 없다. 배열이나 객체에 담아 넘겨야 한다.

## 실험 3: 배열과 포인터 (`03_array_pointer.c`)

| 번호 | 예상 | 실제 |
| --- | --- | --- |
| [3] `data` 와 [4] `&data[0]` 는 같은 값? | 같은 값 | 같은 값 (`0x16fd82b80`) |
| [5] `data+0` → `data+1` 주소 차이 | 1바이트 | 1바이트 (`...b80` → `...b81`) |
| [6] main 안 `sizeof(big)` | 20 | 20 |
| [6] 함수 안 `sizeof(arr)` | 8 | 8 (포인터 크기) |
| [7] `values+0` → `values+1` 주소 차이 | 4바이트 | 4바이트 (`...b58` → `...b5c`) |

- 배열 이름 `data`는 사실 무엇인가? → 주소값
- `data[i]` 와 `*(data + i)` 의 관계 → 같은것
- `data + 1`은 1바이트, `values + 1`은 4바이트 증가한 이유 → 포인터 + 1은 "원소 1개 크기만큼" 이동한다. uint8_t는 1바이트, uint32_t는 4바이트라서 증가량이 다르다.
- 함수 안에서 `sizeof`가 배열 크기가 아닌 이유 → 함수에 배열을 넘기면 첫 원소의 주소(포인터)만 넘어간다. 그래서 함수 안의 sizeof는 배열 크기가 아니라 포인터 크기(8)다.
- 그래서 C 함수는 배열을 받을 때 무엇을 같이 받아야 하나? → 배열의 길이(len)를 같이 받아야 한다. 함수는 주소만 받아서 배열 크기를 알 수 없다.

## 실험 4: 구조체 (`04_struct.c`)

| 번호 | 예상 | 실제 |
| --- | --- | --- |
| [1] `b = a; b.x = 99` 후 `a.x` | 1 | 1 |
| [2] `move_value(a)` 후 `a.x` | 101 | 1 |
| [3] `move_pointer(&a)` 후 `a.x` | 201 | 101 |
| [5] `sizeof(Point)` | 8 | 8 |
| [6] `sizeof(Point *)` | 8 | 8 |

- `Point b = a;` 가 Java와 다른 점 →  Java는 객체의 참조만 복사해서 둘이 같은 객체를 공유한다. C는 구조체 내용 전체를 복사해서 별개의 두 구조체가 된다.
- `.` 과 `->` 는 언제 쓰나? → 구조체 변수에는 ., 구조체 포인터에는 ->를 쓴다. p->x는 (*p).x와 같다.
- 큰 구조체를 함수에 넘길 때 포인터로 넘기는 이유 → 구조체 전체를 복사하면 느리고 메모리를 많이 쓴다. 포인터는 주소(8바이트)만 복사하므로 빠르고, 원본도 수정할 수 있다. 수정하면 안 될 때는 const 포인터로 넘긴다.

## 실험 5: 구조체 패딩 (`05_padding.c`)

| | 멤버 크기 합 | 예상 sizeof | 실제 sizeof | offsetof |
| --- | --- | --- | --- | --- |
| `OrderA` (u8, u32, u8) | 6 | 6 | 12 | a=0, b=4, c=8 |
| `OrderB` (u32, u8, u8) | 6 | 6 | 8 | b=0, a=4, c=5 |
| `CanFrameLike` (u32, u8, u8[8]) | 13 | 6 | 16 | id=0, dlc=4, data=5 |

- 패딩이 생기는 이유 (정렬, alignment) → CPU가 데이터를 빨리 읽으려면 4바이트 타입은 4의 배수 주소에서 시작해야 한다(정렬). 컴파일러가 자리를 맞추려고 빈 바이트(패딩)를 끼워 넣는다.
- `OrderA`와 `OrderB`의 크기가 다른 이유 → OrderA는 u8 뒤에 u32가 와서 u32를 4번 자리로 밀어내느라 패딩이 생긴다. OrderB는 u32를 맨 앞에 둬서 빈틈이 적다. 큰 멤버부터 나열하면 크기가 줄어든다.
- `CanFrameLike`의 남는 바이트는 어디에 생기나? → 맨 끝(13~15번)에 3바이트. 전체 크기를 4의 배수(16)로 맞추기 위해서다.
- 그래서 구조체를 통신 데이터에 `memcpy`로 그대로 덮어쓰면 위험한 이유 → 구조체에는 패딩이라는 보이지 않는 빈칸이 있고, 그 위치가 컴파일러/CPU마다 달라서 통신 데이터의 바이트 위치와 어긋날 수 있다. 그래서 통신 데이터는 바이트 배열에서 비트 연산으로 꺼낸다.

## 실험 6: const 포인터 (`06_const_pointer.c`)

| 선언 | 값 변경 (`*p = ...`) | 대상 변경 (`p = ...`) |
| --- | --- | --- |
| `const uint8_t *p` | ❌ 불가 | ⭕ 가능 |
| `uint8_t *const q` | ⭕ 가능 | ❌ 불가 |

- 외우는 법: `const`가 `*` **왼쪽**이면 "가리키는 값" 고정, `*` **오른쪽**이면 "포인터(주소)" 고정
- 실행 결과 해석
  - `[1] *p = 0x33` → `p = buf2;`로 대상 변경에 성공했다 (buf2[0] = 0x33)
  - `[2] buf1[0] = 0xAA` → `*q = 0xAA;`로 값 변경에 성공했다 (원래 0x11)

- 주석 실험 결과: 셋 다 **컴파일 에러** (실행 전에 막힌다)

```
실험 1 (*p = 0x00):
error: read-only variable is not assignable

실험 2 (q = buf2):
error: cannot assign to variable 'q' with const-qualified type 'uint8_t *const'

실험 3 (data[0] = 0xFF):
error: read-only variable is not assignable
```

- 파서 함수가 `const uint8_t *data`를 받는 이유 → 파서는 데이터를 **읽기만** 해야 한다. const를 붙이면 실수로 원본을 바꾸는 코드를 컴파일러가 막아주고(실험 3), 함수 선언만 봐도 "이 함수는 data를 바꾸지 않는다"는 걸 알 수 있다.
- Java `final`과 비교 → Java `final`은 변수(참조) 고정만 가능. C는 "포인터 고정"과 "값 고정"을 따로 정할 수 있다.

## 실험 7: 스택 vs 힙 (`07_stack_heap.c`)

| 번호 | 실제 |
| --- | --- |
| [1] 지역 변수 주소 (스택) | `0x16b466b98` |
| [2] malloc 주소 (힙) | `0x1051453e0` |

| | 스택 (stack) | 힙 (heap) |
| --- | --- | --- |
| 무엇이 들어가나 | 지역 변수, 함수 인자 | `malloc`으로 요청한 메모리 |
| 언제 생기고 사라지나 | 함수 시작 시 생기고 **함수가 끝나면 자동으로 사라짐** | `malloc` 때 생기고 **`free` 할 때까지 남아 있음** |
| 누가 관리하나 | 컴파일러가 자동으로 | **내가 직접** (GC 없음) |
| Java로 치면 | 메서드의 지역 변수 | `new`로 만든 객체 (단, Java는 GC가 치워줌) |

- 두 주소가 많이 떨어져 있는 이유 → 스택과 힙은 OS가 나눠준 **서로 다른 메모리 구역**이기 때문. 스택은 높은 주소 쪽, 힙은 낮은 주소 쪽에 따로 자리 잡는다.
- `free`를 안 하면? → 다 쓴 메모리가 반납되지 않고 계속 점유된 채로 남는다 (**메모리 누수, memory leak**). 프로그램이 오래 돌수록 쓸 수 있는 메모리가 줄어들고, 결국 `malloc`이 실패(NULL 반환)한다.
- 주석 실험 (`make_point_stack`) 결과:

```
error: address of stack memory associated with local variable 'p' returned [-Werror,-Wreturn-stack-address]
```

- 지역 변수 주소를 반환하면 안 되는 이유 → 지역 변수는 스택에 있어서 **함수가 끝나는 순간 사라진다**. 사라진 자리의 주소(dangling pointer)를 받아 쓰면, 그 자리는 다음 함수 호출이 덮어쓰기 때문에 엉뚱한 값이 나온다. 컴파일러가 경고하고, `-Werror` 때문에 에러로 막혔다.
- 임베디드에서 `malloc`을 피하는 이유 →
  - 메모리가 작아서(수십~수백 KB) 누수가 조금만 있어도 금방 바닥난다
  - 할당/해제를 반복하면 메모리가 조각나서(단편화) 공간이 있어도 큰 덩어리를 못 받을 수 있다
  - `malloc`에 걸리는 시간이 일정하지 않아서, 정해진 시간 안에 반응해야 하는 제어기(예: 10ms 주기)에 위험하다
  - 차량이 몇 시간씩 꺼지지 않고 동작해도 절대 멈추면 안 된다 → MISRA-C도 동적 할당을 금지한다
  - 그래서 필요한 메모리는 **전역/정적 변수나 고정 크기 배열로 미리 잡아둔다** (이 프로젝트도 동일)

## 정리: Java 참조 vs C 포인터

| | Java | C |
| --- | --- | --- |
| 객체/구조체 대입 `b = a` | 참조만 복사 → 둘이 **같은 객체**를 공유 | 내용 **전체 복사** → 별개의 두 구조체 (실험 4) |
| 함수에 객체/구조체 넘기기 | 참조가 복사됨 → 함수에서 바꾸면 **원본도 바뀜** | 구조체 전체가 복사됨 → 원본 그대로. 원본을 바꾸려면 **포인터(`&a`)**로 넘김 (실험 4) |
| 함수에 `int` 넘기기 | 값 복사 → 원본 그대로 | 값 복사 → 원본 그대로. 바꾸려면 **포인터(`&x`)**로 넘김 (실험 2) |
| 주소 값을 직접 보기 | 불가능 | `&x`로 주소를 얻고 `%p`로 출력 가능 (실험 1) |
| 주소 계산 (`p + 1`) | 불가능 | 가능. `+1`은 **원소 1개 크기만큼** 이동 (실험 3) |
| null 접근 | `NullPointerException` → `try-catch`로 처리 가능, stack trace 제공 | 검사 없음 → **Segmentation fault**로 프로세스 강제 종료 (MCU에서는 조용히 메모리 손상) (실험 1) |
| 배열 길이 | `arr.length`로 항상 알 수 있음, 범위 밖 접근 시 예외 | 함수에 넘기면 길이 정보가 사라짐 → **길이를 따로 넘겨야** 함, 범위 밖 접근도 에러 없음 (실험 3) |
| 메모리 해제 | GC가 자동으로 | 스택은 함수 종료 시 자동, 힙은 **`free`로 직접** 해제 (실험 7) |

> **한 줄 요약:** C는 언제나 **값을 복사**해서 넘긴다. 원본을 바꾸고 싶으면 원본의 **주소**를 복사해서 넘긴다. 그리고 그 과정에서 아무도 안전 검사를 해주지 않는다.
