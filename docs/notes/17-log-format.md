# 17. 입력 로그 포맷 정의 (M3-1)

> 정의서: [`docs/log-format.md`](../log-format.md)

## 1. 로그 파일이란?

- 한 줄 설명 → CAN 버스에 오간 프레임을 **시간 순서대로 한 줄씩 글자로 기록한 파일**. "언제(시각), 어느 버스에서, 어떤 ID로, 어떤 데이터가" 왔는지 남긴다
- 왜 필요한가? (실제 차나 vcan0 없이 개발하려면) →
  - **실제 차나 vcan0 없이도** 프로그램을 돌릴 수 있다. 맥에서는 vcan0을 못 쓰는데(M0-1), 파일만 있으면 M3~M4를 맥에서 전부 개발할 수 있다
  - **같은 상황을 몇 번이고 똑같이 재현**할 수 있다. "주행 중 문 열림" 같은 상황을 파일로 만들어 두면 매번 같은 입력으로 테스트할 수 있다 (실제 차로는 매번 똑같이 만들기 어렵다)
  - 실무에서도 실차 주행 중 CAN을 **녹화**해 두고, 사무실에서 그 로그로 문제를 분석하거나 재현한다
- 웹으로 치면? → **HTTP 요청 로그 / 녹화된 트래픽**. 실제 서버에 들어온 요청을 파일로 저장해 두고, 테스트 서버에 그대로 다시 보내서(리플레이) 버그를 재현하는 것과 같다. 또는 테스트용 **fixture 파일**(JSON 샘플 데이터)

## 2. 한 줄 읽기

```
(0.100000) vcan0 100#1027000000000000
```

| 필드 | 값 | 뜻 |
| --- | --- | --- |
| 타임스탬프 | `(0.100000)` | 괄호 안에 소수점 있는 초 → 0.1초 = **100ms**에 받음 |
| 인터페이스 | `vcan0` | 어느 CAN 버스에서 받았는지 (파서는 무시) |
| ID | `100` | Standard ID `0x100` → VEHICLE_SPEED (차속) |
| 데이터 | `1027000000000000` | 2글자씩 → `10 27 00 00 00 00 00 00` (8바이트) |
| DLC (계산) | `8` | 데이터 16글자 ÷ 2 = 8 |

- DLC를 따로 안 적는 이유 → 데이터의 값으로 DLC가 **정확히 계산**된다: 데이터 글자 수 ÷ 2 = DLC. 따로 적으면 데이터 길이와 DLC가 **서로 다르게 적힐 수 있어서**(예: DLC 8인데 데이터 4바이트) 오히려 헷갈린다. 하나로만 표현하면 어긋날 일이 없다
- 이 줄을 `CanFrame`으로 바꾸면? (M1-2 지정 초기화로 써 보기) →

```c
CanFrame f = {
    .id   = 0x100,
    .dlc  = 8,
    .data = {0x10, 0x27, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00}
};
/* 타임스탬프 100ms는 CanFrame에 없다 → 파서가 따로 돌려준다 (디스패처의 now_ms로 사용) */
```

## 3. candump 형식을 고른 이유

- 직접 형식을 만들지 않고 candump 형식을 쓰는 이유 (M5와 연결) →
  - **같은 파일을 두 곳에서 쓴다.** M3에서는 `bcm_sim --file`로 읽고, M5에서는 리눅스 `canplayer`로 vcan0에 **그대로 재생**한다. 형식을 직접 만들면 M5에서 변환 도구를 또 만들어야 한다
  - **반대 방향도 된다.** vcan0에서 `candump -l`로 녹화한 파일을 바로 `bcm_sim --file`에 넣을 수 있다 (M5-10 E2E 테스트에서 BCM 출력을 녹화해서 검증)
  - **이미 업계에서 쓰는 형식이다.** 리눅스 CAN 개발자라면 다 아는 형식이라 설명이 필요 없고, can-utils의 다른 도구(`log2long`, `cansniffer` 등)로도 열어볼 수 있다
  - 웹으로 치면 로그를 내 마음대로 만들지 않고 **표준 형식(JSON Lines, Apache 로그 형식)**으로 남겨서 기존 분석 도구를 그대로 쓰는 것과 같다
- 타임스탬프를 실제 시각이 아니라 0초부터 쓰는 이유 →
  - **읽기 쉽다.** `(1697800000.123456)`보다 `(0.100000)`이 "시작하고 100ms 뒤"라는 게 바로 보인다
  - **손으로 시나리오를 만들기 쉽다** (M3-4). 0초부터 100ms씩 늘려 쓰면 된다
  - **테스트할 때마다 결과가 같다.** 실제 시각은 실행할 때마다 바뀌지만, 상대 시각은 항상 같아서 "500ms 타임아웃" 같은 계산을 예측할 수 있다
  - 파서는 둘 다 읽을 수 있다 (`docs/log-format.md` 정상 예시 5번). 실제 candump 파일은 첫 프레임 시각을 빼서 0초 기준으로 바꿔 쓸 수 있다

## 4. 주석 규칙 — 설계 결정

- 파서는 `#` 주석을 허용하는데, 시나리오 파일에는 주석을 안 넣기로 한 이유 →
  - 컨테이너에서 can-utils의 `log2long`으로 직접 확인했다:

```
정상 줄 3개만 있는 파일   → 3줄 다 읽음 ✅
"# comment" + 정상 줄    → 아무것도 출력 안 함 ❌ (주석에서 멈춤)
```

  - 시나리오 파일은 M5에서 리눅스 `canplayer`로 **그대로 재생**해야 한다 → 리눅스 도구가 못 읽는 주석이 있으면 안 된다 (candump 형식을 고른 이유가 사라짐)
  - 그래도 우리 파서는 주석을 허용한다 → **손으로 만드는 테스트 파일**(M3-2, M3-3)에는 "이 줄은 일부러 틀린 줄" 같은 설명을 달 수 있게
  - 정리: **우리 파서는 너그럽게 읽고, 시나리오 파일은 엄격하게 쓴다** (M1-3 견고성 원칙: 보낼 때는 엄격하게, 받을 때는 너그럽게)
  - `canplayer`가 주석을 어떻게 처리하는지는 vcan이 되는 M5-2에서 직접 확인한다
- 그럼 시나리오 설명은 어디에 쓰나? → **`data/scenarios/README.md`**에 따로 쓴다 (M3-4). 시나리오마다 "무슨 상황인지, 몇 ms에 무슨 일이 일어나는지, BCM이 어떻게 반응해야 하는지(기대 결과)"를 적는다. 로그 파일은 **데이터만**, 설명은 **문서에** — 역할을 나눈다 (웹에서 테스트 fixture JSON에는 데이터만 두고, 설명은 테스트 코드나 README에 쓰는 것과 같다)

## 5. 잘못된 예시 직접 판정해 보기

아래 줄이 정상인지, 아니면 무엇이 문제인지 써 보기

| 줄 | 정상? | 문제 |
| --- | --- | --- |
| `(0.5) vcan0 200#01` | 정상 ✅ | 없음. 500ms, 0x200, DLC 1, 운전석 열림 |
| `(0.5) vcan0 200#1` | 비정상 ✅ | 데이터가 **홀수 자리**(1글자) → 반 바이트는 없다 |
| `(0.5) vcan0 0200#01` | 비정상 ✅ | ID가 **4자리** → Standard ID는 정확히 3자리 |
| `(0.5) vcan0 200#` | 비정상 → ❌ **정상** | 데이터 0글자 = **DLC 0**. 0은 짝수이고 0~16자리 범위 안이라 문법상 정상 (정상 예시의 `555#`와 같음). 다만 0x200은 최소 길이 1바이트라 **디코더에서** 거부된다 (6번 "값 오류") |
| `(0.5)vcan0 200#01` | 비정상 ✅ | 타임스탬프와 인터페이스 사이에 **공백이 없음** → 필드 사이는 공백 한 칸 |
| `(0.5) vcan0 200#ZZ` | 비정상 ✅ | `Z`는 **16진수가 아님** (0~9, A~F만 가능) |

> 6개 중 5개 정답. `200#`을 틀렸다 → "데이터가 비어 있으면 이상하다"고 느꼈지만, **CAN은 DLC 0인 프레임도 정상**이다 (M1-1: 데이터 0~8바이트). 문법상 정상인지와 그 메시지로 쓸 수 있는지는 다른 문제

## 6. 문법 오류 vs 값 오류

- `(0.1) vcan0 800#00`은 파서를 통과하나? 그다음 어디서 걸리나? → **파서는 통과한다.** ID가 16진수 3자리이고 데이터도 짝수 자리라 **문법은 맞다** → `CanFrame { id = 0x800, dlc = 1 }`이 만들어진다. 그다음 `can_frame_is_valid()`(M1-2)에서 **ID가 0x7FF 초과**라 거부된다 (디스패처는 `DISPATCH_ERROR`)

```
"(0.1) vcan0 800#00"
   ↓ ① 파서 (M3-2): 글자 모양 검사 → 통과 → CanFrame { id = 0x800, dlc = 1 }
   ↓ ② can_frame_is_valid() (M1-2): 값 범위 검사 → ID > 0x7FF → 거부 ❌
```

| 단계 | 검사하는 것 | 예 | 담당 |
| --- | --- | --- | --- |
| ① 문법 | **글자 모양**이 형식에 맞나 (괄호, 공백, `#`, 16진수, 자리 수) | `200#1`(홀수), `200#ZZ`, `0200#01` | 파서 (M3-2) |
| ② 값 | 만들어진 프레임의 **값이 범위 안**인가 | `800#00`(ID > 0x7FF) | `can_frame_is_valid()` (M1-2) |
| ③ 의미 | 그 **메시지로** 쓸 수 있나 | `200#`(DLC 0 < 도어 최소 1바이트) | 디코더 (M2) |

- 이렇게 두 단계로 나눈 이유 (M1-2 `can_frame_is_valid()`와 연결) →
  - **각자 한 가지만 책임진다.** 파서는 "글자 → CanFrame 변환"만, `can_frame_is_valid()`는 "CanFrame 값 검사"만 한다. 파서가 ID 범위까지 검사하면 같은 검사가 두 군데 생긴다
  - **입력이 어디서 오든 값 검사는 같다.** CanFrame은 로그 파일(M3)에서도, vcan0 소켓(M5)에서도 온다. 소켓에는 파서가 없으니, 값 검사를 파서 안에 넣으면 소켓 쪽에서 빠진다. `can_frame_is_valid()`를 디스패처 입구에 두면 **어느 경로로 오든 한 번은 걸러진다**
  - 웹으로 치면 ① JSON 문법 오류(`400 Bad Request`, 파싱 실패)와 ② `@Valid` 검증 실패(필드 값이 범위 밖)를 나누는 것과 같다. Jackson은 파싱만, Bean Validation은 값 검증만 한다
