# 04. 비트 연산 (M0-5)

> 실험 코드: `playground/bits/`
> 실행: `make -C playground/bits run` (하나만: `./playground/bits/build/01_operators`)
>
> 💡 각 실험은 **실행 전에 "예상" 칸을 먼저 채우고** 실행해서 "실제"와 비교하기

## 0. 손 계산 먼저 (실행 전에!)

`0xB4`에서 **비트 2~5 (4비트)** 꺼내기

```
0xB4 를 2진수로   : 10110100
비트 번호         : 7 6 5 4 3 2 1 0
오른쪽으로 2칸 밀기:  00101101
하위 4비트만 남기기:  1101
결과 (10진수)     : 13
```

## 실험 1: 비트 연산자 6종 (`01_operators.c`)

`a = 0xB4 (1011 0100)`, `b = 0x0F (0000 1111)`

| 번호 | 연산 | 예상 (2진수) | 실제 |
| --- | --- | --- | --- |
| [1] | `a & b` | 00000100 | 0000 0100 (0x04) |
| [2] | `a \| b` | 10111111 | 1011 1111 (0xBF) |
| [3] | `a ^ b` |  | 1011 1011 (0xBB) |
| [4] | `~a` | 01001011 | 0100 1011 (0x4B) |
| [5] | `a << 1` | 101101000 | 0110 1000 (0x68) — 9비트째가 uint8_t로 잘림 |
| [6] | `a >> 2` | 0010110100 | 0010 1101 (0x2D) — 오른쪽 끝 2비트는 버려짐 |

- `&`(AND) 규칙 → 둘 다 1일 때만 1
- `|`(OR) 규칙 → 둘 중 하나만 1이어도 1
- `^`(XOR) 규칙 → 둘이 다르면 1 (b가 1인 자리만 a가 뒤집힌다 → toggle에 사용)
- `~`(NOT) 규칙 → 0은 1로, 1은 0으로 반대
- [7] `a << 1`이 360인 이유 (uint8_t로 자르기 전) → 왼쪽으로 1칸 밀면 ×2. 180 × 2 = 360. uint8_t가 int로 승격된 상태라 255를 넘어도 잘리지 않았다.
- [8] `a >> 2`가 45인 이유 (`>> n`은 수학적으로 무엇과 같나?) → 오른쪽으로 n칸 밀면 ÷2ⁿ (나머지 버림). `>> 2`는 ÷4라서 180 / 4 = 45.

## 실험 2: 마스크와 비트 추출 (`02_mask_extract.c`)

| 번호 | 예상 | 실제 |
| --- | --- | --- |
| [1] `(1u << 4) - 1` (2진수) | 0000 1111 | 0000 1111 (0x0F) |
| [2] `0xB4`의 bit 2 / bit 0 | 1/0 | 1 / 0 |
| [3] `(0xB4 >> 2) & 0x0F` | 0000 1101 | 0000 1101 (0x0D = 13) |
| [4] IgnState / Gear | 0000 0010 / 0000 0011 | 2 (ON) / 3 (D) |

- `(1u << n) - 1`이 "하위 n비트가 전부 1"이 되는 이유 → `1u << n`은 "1 뒤에 0이 n개"다. 거기서 1을 빼면 10진수 `1000 - 1 = 999`처럼 아래 자리가 전부 최대값(2진수에서는 1)이 된다.
- 비트 하나 검사 공식 `(x >> n) & 1u` 해석 → 알고 싶은 n번째 비트를 맨 오른쪽(0번 자리)으로 끌어내리고(`>> n`), 나머지 비트는 `& 1`로 전부 지운다. 결과가 1이면 그 비트가 켜진 것이다.
- 여러 비트 꺼내기 공식 `(x >> start) & mask` 해석 → 같은 원리를 여러 비트로 늘린 것이다. 꺼낼 구간을 맨 오른쪽으로 내리고(`>> start`), 필요한 길이만큼 마스크로 자른다(`& mask`). **밀어서 내리고, 마스크로 자르기.**
- 0번 손 계산 결과와 [3]이 같은가? → 같다. 둘 다 `1101` = 13.
- [4]처럼 바이트 2개를 합친 뒤 꺼내는 이유 → CAN 신호는 바이트 경계에 맞춰 들어 있지 않다. 신호 정의서는 "start bit 8, 길이 3"처럼 **8바이트 전체를 이어 붙인 비트 번호**로 위치를 정한다. 그래서 바이트들을 엔디안 규칙대로 하나의 숫자로 합친 뒤(M0-4 실험 5), 비트 번호로 꺼낸다. 여러 바이트에 걸친 신호(예: start 4, 길이 12)도 같은 방식으로 꺼낼 수 있다. → M2-1 `can_get_bits()`의 방식

## 실험 3: set / clear / toggle (`03_set_clear_toggle.c`)

| 번호 | 연산 | 예상 `doors` | 실제 |
| --- | --- | --- | --- |
| [1] | `doors \|= 1 << FL` | 0000 0000 | 0000 0001 (0x01) — 운전석 열림 |
| [2] | `doors \|= 1 << TRUNK` | 0000 0000 | 0001 0001 (0x11) — 운전석 + 트렁크 열림 |
| [3] | `doors &= ~(1 << FL)` | 1111 1110 | 0001 0000 (0x10) — 운전석 닫힘, 트렁크만 열림 |
| [4] | `doors ^= 1 << RR` | 1111 0110 | 0001 1000 (0x18) — 뒷좌석 오른쪽 열림 |
| [5] | `doors ^= 1 << RR` (또) | 1111 1110 | 0001 0000 (0x10) — 뒷좌석 오른쪽 다시 닫힘 |
| [9] | `0x1F &= (1 << FL)` (`~` 빠뜨림) | 0000 0001 | 0000 0001 (0x01) ✅ |

> 예상이 틀린 이유 (복습용)
> 0. `|=`의 `|`는 AND가 아니라 **OR**다. AND로 계산해서 `0000 0000 & 0000 0001 = 0000 0000`으로 예상했다. AND로는 0인 비트를 켤 수 없어서 set에는 OR를 쓴다. (`||` → `|` OR, `&&` → `&` AND)
> 1. `1 << 0`은 0이 아니라 **1**이다. 0칸 밀면 그대로다. (FL = 0번 비트)
> 2. `doors |= x`는 `doors = doors | x`의 줄임말이다. 결과가 doors에 **저장되고 다음 줄로 이어진다**.
> 3. [3]의 결과는 마스크 `~(1 << FL)` = 1111 1110 자체가 아니라, **doors와 AND 한 값**이다.

- set에 `|`를 쓰는 이유 → OR는 "하나라도 1이면 1"이다. 마스크가 1인 칸은 무조건 1이 되고, 마스크가 0인 칸은 원래 값 그대로라서 **원하는 비트만 켜고 나머지는 건드리지 않는다**.
- clear에 `& ~`를 쓰는 이유 → `~`로 마스크를 뒤집으면 끌 칸만 0이고 나머지는 전부 1이 된다(1111 1110). AND는 0인 칸을 무조건 0으로 만들고 1인 칸은 그대로 두므로, **원하는 비트만 끄고 나머지는 그대로 둔다**.
- toggle에 `^`를 쓰는 이유 → XOR는 "다르면 1"이다. 마스크가 1인 칸은 0↔1로 뒤집히고, 0인 칸은 그대로다. 그래서 두 번 하면 원래대로 돌아온다([4] → [5]).
- [9]에서 `~`를 빠뜨리면 무슨 일이 생겼나? → "운전석만 닫기"를 하려다가 반대로 **운전석만 남고 나머지(조수석, 뒷좌석, 트렁크)가 전부 0**이 됐다. 마스크가 반대라서 끌 칸만 남기고 나머지를 지워버린 것. 실제 차라면 "문이 열려 있는데 닫혔다고 판단"하는 위험한 버그다.

## 실험 4: 비트 유틸 함수 + 테스트 (`04_bit_utils.c`)

- 테스트 결과:

```
15 passed, 0 failed
```

- `count_bits`가 동작하는 방식 → 맨 아래 비트가 1인지 `x & 1u`로 보고 개수에 더한 뒤, `x >>= 1`로 한 칸 밀어서 다음 비트를 맨 아래로 내린다. x가 0이 될 때까지(= 1이 더 없을 때까지) 반복한다.
  - 0xB4 = 1011 0100 → 1이 4개 → 4
- `CHECK` 매크로가 실패할 때 무엇을 출력하나? → **파일:줄 번호**, 실패한 **코드 그대로**, **기대값과 실제값**. 성공하면 아무것도 출력하지 않고 개수만 센다.
- 일부러 테스트 하나를 틀리게 바꿔보면? (72줄 `toggle_bit(..., 5), 5)` → `..., 5), 4)`로 변경)

```
$ make -C playground/bits          ← 빌드만 함 (테스트는 실행 안 됨!)
$ ./playground/bits/build/04_bit_utils
  FAIL 04_bit_utils.c:72  toggle_bit(toggle_bit(0xB4, 5), 4) → 기대 0xB4, 실제 0x84
14 passed, 1 failed
```

  - 왜 0x84? → bit 5를 뒤집고(0xB4 ^ 0x20 = 0x94) bit 4를 뒤집었다(0x94 ^ 0x10 = 0x84). **같은 비트를 두 번 뒤집어야** 원래대로 돌아온다.
  - FAIL 메시지만 보고 몇 번째 줄, 어떤 호출, 얼마나 틀렸는지 바로 알 수 있다 → 디버깅 시간이 줄어든다

- 종료 코드(`echo $?`)는? 성공 시 / 실패 시 → 테스트 프로그램은 성공 시 **0**, 실패 시 **1** (`return failed == 0 ? 0 : 1;`). `make` 자체는 빌드만 하므로 빌드가 되면 0이다. → M0-7에서 `make test`가 테스트까지 실행하게 만들면, 테스트 실패 = make 실패가 된다 (CI에서 PR을 막는 원리)

## 실험 5: `1` vs `1u` (`05_unsigned_literal.c`)

| 번호 | 예상 | 실제 |
| --- | --- | --- |
| [1] `1u << 31` | 1000 0000 0000 0000 0000 0000 0000 0000 | 2147483648 (0x80000000) ✅ |
| [2] `(1u << 31) > 0` | true | true ✅ |
| [3] `1 << 31` (signed) |  | **-2147483648** (음수!) |
| [4] `(1 << 31) > 0` | 정의할 수 없다 | false (이 컴퓨터에서는) — 표준상으로는 UB라 "정의할 수 없다"가 정답 ✅ |

- [3]이 음수가 된 이유 → `1`은 signed int라서 **맨 위 비트(31번)가 부호 비트**다. 부호 비트가 1이면 음수로 읽는다. `1000 0000 ... 0000`을 signed int로 읽으면 int의 최솟값 -2147483648(INT_MIN)이 된다. 같은 비트를 unsigned로 읽으면 2147483648이다. (M0-4 실험 1: 비트는 같고 해석만 다르다)
  - 게다가 signed 값을 부호 비트까지 밀어 넣는 건 C 표준상 **정의되지 않은 동작(UB)**이다. 이 컴퓨터에서는 음수가 나왔지만, 컴파일러 최적화에 따라 다른 결과가 나와도 할 말이 없다.
- 비트 연산에서 항상 `1u`를 쓰는 이유 → `1u`는 unsigned라 부호 비트가 없다. 31번 비트까지 안전하게 밀 수 있고, 결과가 음수가 되거나 UB가 생길 일이 없다. 비트 연산의 대상은 "숫자"가 아니라 "비트 패턴"이므로 항상 unsigned(`1u`, `uint8_t`, `uint32_t`)로 다룬다.
  - [5] 같은 이유로 `uint8_t`도 시프트 전에 `(uint32_t)`로 바꾼다: `(uint32_t)0xFF << 24` = 0xFF000000

## 치트시트

| 하고 싶은 것 | 코드 |
| --- | --- |
| n번째 비트가 1인지 확인 | `(x >> n) & 1u` |
| n번째 비트 켜기 (set) | `x \|= (1u << n)` |
| n번째 비트 끄기 (clear) | `x &= ~(1u << n)` |
| n번째 비트 뒤집기 (toggle) | `x ^= (1u << n)` |
| 하위 n비트 마스크 | `(1u << n) - 1u` |
| start부터 len비트 꺼내기 | `(x >> start) & ((1u << len) - 1u)` |
| 값 하나라도 켜져 있나? | `x != 0u` |

> 규칙: 비트 연산에는 항상 unsigned (`1u`, `uint32_t`). `uint8_t`를 시프트할 때는 먼저 `(uint32_t)`로 바꾼다. clear에는 `~`를 빠뜨리지 않는다.
