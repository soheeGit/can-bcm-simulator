## 1. 디바운싱이란

- 디바운싱을 한 문장으로 → **신호가 바뀌었을 때 바로 믿지 않고, 같은 값이 N번 연속으로 와야 "진짜 바뀌었다"고 인정하는 것.** 이 프로젝트는 도어 프레임 **3개 연속**

```
노이즈:     닫힘  열림  닫힘  닫힘        → 1번만 튐 → 무시, 계속 "닫힘"
진짜 열림:  닫힘  열림  열림  열림  열림   → 3번째에 "열림" 인정 → 경고
연속 횟수:        1     2     3 ✅
```

  - 가짜(노이즈)는 한두 번 튀고 끝나지만, 진짜로 열린 문은 **계속** "열림"이 온다. 그 차이로 구별한다
  - 대가: 진짜로 열려도 **200ms 늦게** 안다 (100ms 주기 × (3 - 1)). 시나리오 02의 경고가 4.0초 → 4.2초
  - 비유: 소문은 한 사람에게 들으면 넘기고, 세 사람에게서 같은 얘기를 들으면 믿기
- 이름의 유래 (스위치의 "bounce") → 버튼을 누르면 안의 금속 접점이 부딪히면서 **1~5ms 동안 여러 번 튕긴다**(bounce). 그대로 읽으면 한 번 누른 게 여러 번 누른 걸로 읽힌다. 이 튕김을 없앤다(de-)고 해서 **de-bounce**
  - 키보드, 엘리베이터 버튼, 리모컨 등 버튼이 있는 거의 모든 기기에 들어 있다
  - 차에서는 버튼뿐 아니라 도어 스위치, 브레이크 스위치처럼 **켜짐/꺼짐 센서** 전반에 쓴다. 덜컹거림, 전기 노이즈로 신호가 튀기 때문
  - 웹 프론트의 검색창 debounce("입력이 멈추고 300ms 뒤에 요청")도 "너무 자주 바뀌는 걸 바로 따라가지 않는다"는 생각은 같지만, 그건 **조용한 시간**을 기준으로, 여기는 **같은 값이 온 횟수**를 기준으로 한다
- 히스테리시스(M4-4)와 비교: 둘 다 흔들림을 막는데 무엇이 다른가 → **막는 수단이 다르다.** 히스테리시스는 **값**(기준선 두 개), 디바운싱은 **횟수(시간)**

| | 히스테리시스 | 디바운싱 |
| --- | --- | --- |
| 무엇으로 막나 | **값의 기준선을 두 개**로 (켜는 문턱 ≠ 끄는 문턱) | **같은 값이 N번 연속**이어야 인정 (시간/횟수) |
| 어떤 신호에 맞나 | 숫자가 연속으로 변하는 **아날로그 같은 신호** (차속, 온도) | 켜짐/꺼짐뿐인 **2값 신호** (문, 버튼). 값이 두 개라 기준선을 둘 수 없다 |
| 이 프로젝트에서 | 15 km/h 이상 잠금 / 0 km/h + P 해제 (M4-4, 시나리오 05) | 도어 프레임 3개 연속 (M4-5, 시나리오 06) |
| 대가 | 가운데 구간에서는 상태가 **바로 안 따라감** (10 km/h에서 잠겼을 수도, 안 잠겼을 수도) | 진짜 변화도 **N-1 주기 늦게** 반응 |

  - 둘을 같이 쓰기도 한다: 차속처럼 노이즈가 심한 숫자 신호는 "N번 연속 15 이상일 때 잠금"처럼 **둘 다** 적용할 수 있다
  - 공통점: 둘 다 **"지금까지의 상태를 기억"**해야 한다 (히스테리시스는 `state`, 디바운싱은 `candidate`와 `count`). 그래서 둘 다 `BcmContext` 안에 있다

| --- | --- | --- | --- |
| 3.0초 | FL 1프레임 | 무시 | ✅ 무시. `[3.000s] 도어 FL=1` 로그는 찍히지만(디스패처는 받음) `STATE` 줄이 없다. FL 연속 1번 → 3.1초 닫힘으로 다시 셈 |

- 표에 없는 4.0초 **트렁크 1프레임**도 같은 이유로 무시됐다 (`[4.000s] 도어 ... TRUNK=1`은 있지만 `STATE` 없음)
- 로그 두 종류를 비교하면 디바운싱이 한 일이 보인다: `도어` 줄은 디스패처가 받은 **원래 값**(노이즈 포함 12번 바뀜), `STATE` 줄은 BCM이 **인정한 것**(2번)

- 4.4 ~ 4.6초에 FL이 2번 열렸는데도 무시된 이유 (문마다 따로 세기) → FL만 따로 보면 **열림 → 닫힘 → 열림**이라 **연속이 아니기** 때문. 4.5초에는 FL이 닫힘(RR만 열림)이라 FL의 연속 횟수가 거기서 끊기고 1부터 다시 센다

```
시각        4.4   4.5   4.6   4.7
FL 값       열림  닫힘  열림  닫힘
FL 연속     1     (닫힘 1)  1    (닫힘 1)   → 3이 안 됨
RR 값       닫힘  열림  닫힘  닫힘
RR 연속     -     1     (닫힘 1)  ...      → 3이 안 됨
```

  - "열림이 2번 왔다"가 아니라 "**연속으로** 3번"이어야 한다. 횟수를 **누적**하는 게 아니라 다른 값이 오면 **처음부터** 다시 센다 (`count = 1u`)
- 문 5개를 하나로 묶어서(`DoorStatus` 전체가 같아야 인정) 셌다면 4.4 ~ 4.6초는 어떻게 됐을까 → 4.4 ~ 4.6초는 **똑같이 무시**된다. `{FL}`, `{RR}`, `{FL}` 세 상태가 매번 달라서 묶어서 세도 3번 연속이 안 된다. 문제는 **진짜 열림과 노이즈가 겹칠 때** 생긴다

```
FL이 진짜로 계속 열려 있는데, RR에 한 프레임 건너 노이즈가 튄다면

시각          5.0   5.1    5.2   5.3    5.4   ...
받은 값       {FL}  {FL,RR} {FL}  {FL,RR} {FL}

묶어서 세기:  1     1(다름) 1(다름) 1     1     → 전체가 3번 똑같은 적이 없음 → FL 열림을 영원히 인정 못 함 😱
문마다 세기:  FL 1  FL 2    FL 3 ✅ → 5.2초에 인정. RR은 1번씩만 → 무시
```

  - 묶어서 세면 **상관없는 문의 노이즈 때문에 진짜 열림을 놓친다** → 위험한 쪽으로 틀린다 (경고를 안 함)
  - 문마다 따로 세면 각 문이 **자기 센서만** 보고 판단한다. 센서가 5개로 따로 있으니 디바운싱도 5개로 따로 하는 게 맞다
  - 대가: 기억할 것이 5배 (`BcmDebounced` 5개). 그래도 1개에 3바이트라 15바이트뿐

## 3. "판단 횟수"가 아니라 "도어 프레임 수"를 센다

- `bcm_step`은 100ms에 몇 번 불리나? 그중 도어 값이 새로 들어오는 건 몇 번인가 → 한번. 🔺 (도어 값은 **1번**이 맞다. `bcm_step`은 **3번**)
  - 100ms마다 프레임이 3개(0x300, 0x200, 0x100) 오고, `bcm_step`은 **프레임마다** 불리니까 **3번**
  - 그중 도어 값(0x200)이 새로 들어오는 건 **1번**. 나머지 2번(0x300, 0x100 때문에 불린 판단)에는 `in->doors`가 아까 값 **그대로** 남아 있다
- `bcm_step` 횟수로 셌다면 시나리오 06의 3.0초 노이즈 1프레임은 어떻게 됐을까 → **무시되지 않고 3.1초에 가짜 경고가 난다** (복사본으로 직접 실험)

```
판단  프레임        in->doors.fl    판단 횟수로 셈
3.0초 0x300         0 (닫힘)        -
3.0초 0x200 ← 노이즈 1 (열림)        1
3.0초 0x100         1 (그대로 남음)  2     ← 같은 프레임을 또 셈
3.1초 0x300         1 (그대로 남음)  3 ✅  ← "3번 연속" → 인정 → WARNING 😱
3.1초 0x200         0 (닫힘)        다시 1
```

  - 도어 프레임은 **1개**뿐인데, 그 값이 `VehicleInputs`에 남아 있는 동안 다른 프레임 때문에 판단이 2번 더 일어나서 **같은 값을 3번** 센 것
  - 실험 결과: 시나리오 06의 상태 전이가 4회 → **12회**. 노이즈 4개가 전부 가짜 경고가 됐다 (`[3.100s] DRIVING_LOCKED -> WARNING`, `[3.600s] ...`, `[4.100s] ...`, `[4.500s] ...`)
  - 즉 "3번 연속"이 사실상 "**1번**"이 되어 디바운싱이 아무 효과가 없다. 그래서 "판단 횟수"가 아니라 "**새 도어 프레임이 몇 개 왔나**"를 세야 한다
- 그래서 디스패처에 `doors_rx_count`를 추가했다. `doors_rx_ms`(받은 시각)가 바뀌었는지로 판단하지 않은 이유 → **받은 시각은 "새 프레임인가?"를 확실하게 알려 주지 못하기 때문.** 두 프레임이 **같은 시각**일 수 있다

| 방법 | "새 도어 프레임이 왔나?" 판단 | 문제 |
| --- | --- | --- |
| `doors_rx_ms`가 바뀌었나 | 시각이 다르면 새 프레임 | 같은 시각에 도어 프레임이 2개 오면 **하나를 놓친다** |
| `doors_rx_count`가 늘었나 (이번 방식) | 개수가 늘면 새 프레임 | 없음. 프레임을 받을 때마다 **반드시 +1** |

  - 같은 시각이 되는 경우: 로그 파일에 같은 타임스탬프 줄이 2개 있을 때 (시나리오 04처럼 줄을 끼워 넣거나 재생 도구가 몰아서 쓸 때), 시간이 거꾸로 가서 상대 시각이 0으로 고정될 때(M3-3), 실시간 모드(M5)에서 1ms 안에 두 프레임이 올 때
  - 시각은 "**언제**" 받았는지(타임아웃용, M4-6), 개수는 "**몇 개**" 받았는지(디바운싱용). 묻는 게 다르니 따로 둔다
  - 덤: 테스트도 쉬워진다. 시각을 매번 바꿀 필요 없이 `in.doors_rx_count++`(`new_door_frame()`) 한 줄로 "새 프레임"을 만들 수 있다

## 4. 첫 프레임은 바로 인정 (`debounce_seed`)

- 첫 도어 프레임도 3번 기다리면 무슨 일이 생기나 (힌트: `doors_known`, T2) → 처음 **200ms 동안 "문이 어떤지"를 BCM이 제대로 모르는 구간**이 생긴다. 그 구간을 어떻게 처리하든 문제가 있다

| 기다리는 동안 문을... | 무슨 일이 생기나 |
| --- | --- |
| **닫힘으로 본다** (`stable`의 시작값 0) | **증거 없이** "닫힘"이라고 믿는다. 문을 연 채로 시동을 걸었는데 BCM은 200ms 동안 "다 닫혔다"고 판단한다 → Fail-safe(모르면 안전한 쪽으로)의 **반대** |
| **모름으로 본다** (`doors_known = false`) | IDLE에서는 T2(신호 이상 → 대기)에 걸려서 200ms 동안 **아무 판단도 못 한다**. 주행 중 BCM이 재시작됐다면 DRIVING_LOCKED → T5로 **가짜 Fail-safe 경고** |

  - 첫 프레임을 바로 인정하면(`debounce_seed`) 둘 다 피한다. 첫 값은 **진짜로 받은 값**이라 "증거 없는 가정"이 아니고, 기다리지 않으니 판단이 늦지도 않다
  - 디바운싱의 목적은 "**바뀐 값**을 의심하기"다. 첫 프레임은 비교할 이전 값이 없으니 "바뀐" 게 아니다 → 의심할 이유가 없다
  - 대가: 하필 **첫 프레임이 노이즈**면 그 값을 바로 믿는다. 하지만 다음 프레임부터는 진짜 값이 3번 연속 오니까 **200ms 뒤에 바로잡힌다** (스스로 고쳐진다)
  - `doors_known`(신호가 오나, M4-6 타임아웃)과 디바운싱(값을 믿나)을 **섞지 않은 것**도 이 때문. 둘을 섞으면 "디바운싱 중 = 신호 끊김"처럼 보여서 위의 두 번째 줄 문제가 생긴다
  - 테스트에서도 효과가 있다: `driving()`으로 만든 입력은 첫 프레임이라 바로 인정된다 → M4-3, M4-4의 테스트 100여 개를 도우미(`driving`, `step_from`) 몇 줄만 고치고 **내용은 그대로** 쓸 수 있었다 (`test_debounce_first_sample_immediate`가 이 규칙을 지킨다)

## 5. 반응이 늦어지는 대가

- 시나리오 02의 WARNING이 4.0초 → 4.2초로 늦어졌다. 200ms 늦게 경고하는 게 괜찮은 이유 / 괜찮지 않을 수도 있는 경우 →
  - **괜찮은 이유:** 경고음은 **운전자에게 알리는** 기능이다. 사람이 소리를 듣고 반응하는 데만 0.5 ~ 1초가 걸리니, 0.2초 늦는 건 거의 차이가 없다. 반대로 노이즈 때문에 가짜 경고가 "삑삑" 나면 운전자가 경고를 **무시하는 습관**이 생긴다 (양치기 소년). 그게 더 위험하다
  - 거리로 보면: 40 km/h ≈ 초속 11 m → 0.2초에 약 **2.2 m** 더 간다
  - **괜찮지 않을 수 있는 경우:** 사람이 아니라 **기계가 바로 반응해야** 하는 기능. 예를 들어 "문이 열리면 차를 바로 멈춰라"(자율주행), 에어백, 브레이크처럼 **밀리초 단위**가 중요한 것은 200ms가 너무 길다. 그런 신호는 디바운싱 대신 센서를 2개 달아서(이중화) 둘이 같은 값일 때만 믿는 식으로 빠르게 거른다
  - 정리: 지연을 얼마나 허용할지는 **그 기능이 무엇을 하느냐**로 정한다. 경고(사람 반응) = 수백 ms 괜찮음, 제어(기계 반응) = 수 ms
- N을 10으로 하면? 1로 하면? → 복사본으로 직접 돌려 봤다

| N | 반응 지연 | 시나리오 02 경고 | 시나리오 06 (노이즈 4개) | 상태 전이 (06) |
| --- | --- | --- | --- | --- |
| **1** (디바운싱 없음) | 0 | 4.0초 | **노이즈 4개 전부 가짜 경고** (3.0, 3.5, 4.0, 4.4초) | **12회** |
| **3** (지금) | 0.2초 | 4.2초 | 전부 무시, 5.2초만 경고 | 4회 |
| **10** | 0.9초 | **4.9초** | 전부 무시, 5.9초만 경고 | 4회 |

  - **N = 1:** 디바운싱이 없는 것과 같다. 빠르지만 노이즈가 다 경고가 된다
  - **N = 10:** 노이즈에는 아주 강하지만 **0.9초** 늦다 (40 km/h면 약 10 m). 더 큰 문제는 **1초보다 짧게 열린 문은 아예 못 알아챈다**는 것. 시나리오 02는 문이 정확히 10프레임(4.0 ~ 4.9초) 열려 있어서 **마지막 프레임에 겨우** 잡혔다. 0.8초만 열렸다 닫혔다면 경고가 한 번도 안 났다 → 진짜 위험을 놓친다
  - N은 "**노이즈는 보통 몇 프레임까지 튀나**"보다 조금 크게, "**진짜 변화는 최소 몇 프레임 지속되나**"보다는 작게 정한다. 도어 노이즈는 보통 1 ~ 2프레임, 사람이 문을 열면 최소 수백 ms → 3이 그 사이에 있다
  - 실제 차에서는 신호마다 N을 다르게 하고, 시험 차로 노이즈를 측정해서 정한다 (캘리브레이션, 26번 노트 3번). 그래서 `BCM_DOOR_DEBOUNCE_COUNT`를 상수로 빼 둔 것

## 6. 세그폴트 사건과 Makefile 의존성

M4-5를 만드는 중에 `dispatcher.h`의 `VehicleInputs`에 필드를 추가했더니 `./build/bcm_sim`이 **아무것도 안 찍고 종료 코드 139**로 끝났다. `make clean && make` 후에는 정상.

- 종료 코드 139의 뜻 → **세그폴트(Segmentation fault)로 강제 종료됐다**는 뜻. 프로그램이 접근하면 안 되는 메모리를 건드려서 운영체제가 죽인 것
  - 규칙: 신호(signal)로 죽으면 종료 코드 = **128 + 신호 번호**. 세그폴트는 `SIGSEGV` = 11 → 128 + 11 = **139**
  - 그래서 우리 프로그램이 정한 0 / 1 / 2(M3-6)가 아닌 이상한 숫자가 나왔다. `printf`로 찍기 전에 죽어서 화면에 아무것도 안 나왔다
  - 비슷한 것: 134 = 128 + 6(`SIGABRT`, `abort()`나 Sanitizer가 멈출 때, M0의 Abort trap)
- 왜 생겼나 (힌트: `main.o`는 언제 컴파일됐나, 구조체 크기) → **파일마다 `VehicleInputs`의 크기를 다르게 알고 있었기 때문**

| | `doors_rx_count` 추가 전 | 추가 후 |
| --- | --- | --- |
| `sizeof(VehicleInputs)` | **36**바이트 | **40**바이트 (직접 확인) |

```
1. dispatcher.h에 필드 추가 (36 → 40바이트)
2. make → Makefile은 ".c가 바뀌었나"만 봄
     src/dispatcher.c, src/bcm.c   → 고쳤으니 다시 컴파일 → "40바이트"로 앎
     src/main.c, src/log_reader.c  → 안 고쳤으니 건너뜀 → 옛날 .o는 "36바이트"로 앎 ❌
3. 링크해서 하나로 합침 → 서로 크기를 다르게 아는 코드가 섞임
4. main()이 스택에 36바이트짜리 VehicleInputs를 만들고 → dispatcher가 40바이트로 보고 씀
     → 마지막 4바이트(doors_rx_count)가 옆에 있던 BcmContext나 LogReadStats를 덮어씀
     → 엉뚱한 값으로 망가진 포인터를 따라가다가 💥 세그폴트
```

  - **컴파일러도 링커도 아무 경고를 안 했다.** 각 `.o`는 그 자체로는 멀쩡했고, 링커는 크기가 맞는지 확인하지 않는다 → C에서 가장 찾기 어려운 버그 종류
  - M4-3에서 테스트가 옛날 코드로 통과했던 것(`touch`로 해결)과 **같은 종류**의 문제(오래된 빌드). 그때는 "결과가 이상함"이었고, 이번엔 메모리가 깨져서 **죽었다**
  - Java는 클래스 파일에 필드 정보가 들어 있어서 맞지 않으면 `NoSuchFieldError`, `IncompatibleClassChangeError`로 바로 알려 준다. C는 구조체 크기와 위치를 **컴파일할 때 숫자로 박아 넣어서** 실행할 때는 모른다
- Makefile에 추가한 `-MMD -MP`와 `-include ...d`가 하는 일 → **".c가 어떤 .h를 썼는지"를 컴파일러가 기록하고, make가 그 기록을 읽게** 한다

```makefile
DEPFLAGS := -MMD -MP
$(BUILD)/%.o: src/%.c | $(BUILD)
	$(CC) $(CFLAGS) $(DEPFLAGS) -c $< -o $@          # 컴파일하면서 build/main.d도 만든다
...
-include $(OBJS:.o=.d) ...                           # 그 .d 파일들을 Makefile에 붙여 읽는다
```

```
# build/main.d (컴파일러가 만든 파일)
build/main.o: src/main.c include/bcm.h include/dispatcher.h include/can_frame.h ...
```

| 부분 | 하는 일 |
| --- | --- |
| `-MMD` | 컴파일할 때 `.d` 파일에 "이 `.o`는 이 `.c`와 이 `.h`들에 달려 있다"를 적는다 (시스템 헤더 `<stdio.h>` 등은 빼고) |
| `-MP` | 헤더를 **지우거나 이름을 바꿔도** "그 헤더 없음" 에러가 안 나게 빈 규칙을 같이 적는다 |
| `-include ...d` | `.d` 파일들을 Makefile에 붙여 읽는다. `-`는 "파일이 없어도 괜찮음" (처음 빌드할 때는 `.d`가 아직 없으니까) |

  - 이제 `dispatcher.h`가 바뀌면 make가 `.d`를 보고 "`main.o`도 이 헤더에 달려 있네" → 다시 컴파일한다
  - 함께 고친 것: `.d`가 헤더를 의존성에 추가하니까, 테스트 링크 명령의 `$^`에 `.h`도 섞여 들어와서 `clang: error: cannot specify -o when generating multiple output files`가 났다 → `$(filter %.c %.o,$^)`로 `.c`, `.o`만 골라 넘기게 고쳤다
  - Gradle, Maven은 이런 의존성 추적을 **알아서** 한다. C는 컴파일러 옵션으로 직접 켜야 한다
- 실험: `touch include/dispatcher.h` 후 `make`하면 어떤 `.c`가 다시 컴파일되나 → **`src/bcm.c`, `src/dispatcher.c`, `src/log_reader.c`, `src/main.c` 4개** (맥, 리눅스 컨테이너 둘 다 같음)
  - 4개 모두 `dispatcher.h`를 직접 또는 다른 헤더를 거쳐 `#include`한다 (`main.c` → `bcm.h` → `dispatcher.h`처럼)
  - `can_signal.c`, `logger.c`, `cli.c` 같은 나머지는 `dispatcher.h`를 안 쓰니까 **건너뛴다** → 필요한 것만 정확히 다시 컴파일
  - `touch`는 내용은 안 바꾸고 "바뀐 시각"만 지금으로 찍는 명령이라, 헤더를 고친 것처럼 make를 속여서 확인할 수 있다

- `new_door_frame()` 도우미가 `doors_rx_count++`를 하는 이유 → **"새 도어 프레임이 왔다"를 흉내 내려고.** BCM은 `doors_rx_count`가 **늘었을 때만** 디바운싱을 한다(3번). 테스트에서 `in.doors.fl = true;`만 바꾸고 개수를 안 늘리면, BCM은 "새 프레임이 안 왔네" 하고 그 값을 **아예 안 본다**

```c
static void new_door_frame(VehicleInputs *in, bool fl_open) {
    in->doors.fl = fl_open;     /* 프레임 안의 값 */
    in->doors_rx_count++;       /* 디스패처가 하는 일을 대신: "프레임 1개 받음" */
}
```

  - 실제 프로그램에서는 디스패처(`can_dispatch`)가 0x200을 해석할 때마다 `doors_rx_count++`를 한다. 테스트는 디스패처 없이 BCM만 확인하니까 그 일을 **대신** 해 준다
  - 실제로 이걸 깜빡해서 M4-4의 `test_hysteresis_warning_jitter`가 실패했었다 → `run_jitter()`에도 `doors_rx_count++`를 넣어서 고쳤다
- `test_debounce_counts_frames_not_steps`가 확인하는 것 → **3번에서 본 함정을 막았는지.** 도어 프레임은 1개(`new_door_frame` 1번)인데 `bcm_step`을 **10번** 부른다. 판단 횟수로 셌다면 3번째 판단에서 인정돼 WARNING이 됐을 것이고, 프레임 수로 세니까 1번뿐이라 DRIVING_LOCKED 그대로여야 한다

```c
new_door_frame(&in, true);          /* 열림 프레임은 딱 1개 */
for (int i = 0; i < 10; i++) {
    bcm_step(&ctx, &in, NOW, &out); /* 판단은 10번 (0x100, 0x300 때문에 불린 것처럼) */
}
ASSERT_EQ(BCM_STATE_DRIVING_LOCKED, out.state);   /* 그래도 노이즈 1번 → 무시 */
```

  - 3번 실험(판단 횟수로 세기)으로 바꾸면 **이 테스트가 실패**한다 → 이 테스트가 그 실수를 지키는 **뮤테이션 테스트의 파수꾼**
  - 시나리오 06의 실험 결과(전이 4회 → 12회)를 단위 테스트 하나로 줄여 놓은 것
