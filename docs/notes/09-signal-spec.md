# 09. 신호 정의서 (M1-3)

> 정의서: [`docs/signal-spec.md`](../signal-spec.md)
>
> 목표(DoD): **정의서만 보고 임의의 프레임을 손으로 해석**할 수 있다 → 아래 연습 문제

## 1. 개념

- DBC 파일이란? → CAN 메시지와 신호의 정의. 더 정확히는 그 정의를 담은 **텍스트 파일 형식** (`.dbc`). 사람이 읽는 문서이면서 **도구가 읽는 파일**이기도 하다
  - Vector CANdb++ 같은 도구로 만들고 관리한다
  - CAN 분석 도구(CANoe, CANalyzer)가 DBC를 읽어서 `100#1027...` 같은 날것의 데이터를 "VehicleSpeed = 100.00 km/h"로 바로 보여준다
  - DBC로 디코더 C 코드를 **자동 생성**하기도 한다 (이 프로젝트는 공부를 위해 M2에서 직접 짠다)
  - 차량 제조사가 DBC를 만들어 협력사에 나눠준다 → 서로 다른 회사가 만든 제어기끼리도 같은 해석을 하게 된다
- 메시지(Message)와 신호(Signal)의 차이 →
  - **메시지** = CAN 프레임 하나 (ID 하나). 예: `0x300 IGN_STATUS`
  - **신호** = 메시지의 8바이트 안에 **비트 단위로 들어 있는 값 하나**. 예: `IgnState`, `Gear`
  - 메시지 하나에 신호가 여러 개 들어갈 수 있다 (`DOOR_STATUS`에는 신호 5개, `IGN_STATUS`에는 2개)
  - Java로 치면 메시지 = DTO 클래스, 신호 = 그 안의 필드. 단, 필드가 바이트 단위가 아니라 **비트 단위**로 꽉 채워져 있다

```
메시지 0x300 IGN_STATUS (8바이트)
├── 신호 IgnState : bit 0~1
└── 신호 Gear     : bit 8~10
```

- 웹 개발로 치면 무엇과 같나? → API 정의서. 특히 **OpenAPI(Swagger) 스펙 파일**과 같다. 사람이 읽는 문서이면서, 도구가 읽어서 클라이언트 코드를 자동 생성하거나 테스트 화면을 만든다는 점까지 DBC와 똑같다
  - OpenAPI: 엔드포인트(URL) + 요청/응답 JSON 필드 → DBC: 메시지(ID) + 신호(비트 위치)

## 2. 신호를 정의하는 항목

| 항목 | 뜻 | VehicleSpeed의 값 |
| --- | --- | --- |
| start bit | 시작비트. 신호의 가장 낮은 자리 비트가 몇 번 비트인지 (0 ~ 63) | 0 |
| length | 길이. 신호가 몇 비트를 차지하는지 | 16 |
| byte order | **바이트 순서.** 여러 바이트에 걸친 신호를 어떤 순서로 조립하나 (Intel = Little-endian / Motorola = Big-endian) | Intel (Little-endian) |
| 부호 (signed/unsigned) | 음수가 있는 신호인지 (byte order와는 별개 항목) | unsigned |
| factor | 배율. raw에 곱하는 값 = **한 칸(raw 1)이 실제로 얼마인지** (분해능) | 0.01 (raw 1 = 0.01 km/h) |
| offset | 더하는 값. 물리값이 0이 아닌 값에서 시작할 때 쓴다 (예: 온도 -40℃부터 → offset -40) | 0 |
| 범위 (min/max) | 물리값으로 유효한 최솟값/최댓값 | 0 ~ 655.34 |
| 단위 | 물리값의 단위 | km/h |

- 물리값 = raw × factor + offset → 왜 실수(`100.00`)를 그대로 안 보내고 정수 raw로 보낼까? →
  - **8바이트밖에 없다.** float는 4바이트를 통째로 쓰지만, 0.01 단위 정수로 바꾸면 16비트(2바이트)로 0 ~ 655.35를 표현할 수 있다. 필요한 정밀도만큼만 비트를 쓴다
  - **MCU는 실수 계산이 느리거나 못 하는 경우가 많다** (FPU 없음). 정수는 어디서나 빠르고 정확하다 (M2-3 고정소수점)
  - **실수는 오차가 있다.** `0.1 + 0.2 != 0.3` 같은 문제. 정수 raw는 송신 측과 수신 측이 완전히 같은 값을 갖는다
  - 그래서 "어떤 비트 위치에, 몇 배율로" 넣을지를 정의서로 약속한다
- "무효값(`0xFFFF`)"을 따로 정해 두는 이유 → 신호 무효를 나타내기 위해서. 왜 필요하냐면:
  - 센서가 고장 났을 때 **"0 km/h(정차)"와 "모름"을 구분**해야 한다. 고장 났다고 0을 보내면, BCM은 "정차했네" 하고 **달리는 중에 문 잠금을 풀 수도 있다**
  - 받는 쪽은 무효값이면 그 신호로 판단하지 않고 안전한 쪽으로 처리한다 (M4 Fail-safe)
  - 범위 밖 값(655.35)을 무효 표시로 쓰는 게 관례 → 그래서 유효 범위가 655.34까지
- 송신 주기(100ms)와 타임아웃(500ms)이 정의서에 들어가는 이유 →
  - CAN은 요청-응답이 아니라 **주기적으로 알아서 보내는** 방식이다 (M1-1 10번). 받는 쪽은 "언제 와야 정상인지"를 알아야 "안 오면 이상하다"고 판단할 수 있다
  - 보내는 쪽(ESC)과 받는 쪽(BCM)이 **같은 약속**을 해야 하므로 정의서에 적는다. 웹 API 문서에 "타임아웃 3초, 재시도 정책"을 적는 것과 같다
  - 타임아웃을 주기의 정확히 1배로 하면, 메시지가 한 번만 살짝 늦어도 "끊김"으로 오판한다 → 여유를 둬서 5배

## 3. 연습 문제: 손으로 해석하기

> 정의서 3번(신호 상세)과 비트 번호 그림만 보고 풀기. 코드 실행 금지!

### 문제 A

```
100#B80B000000000000
```

> (풀이 예시 — 이 4단계를 문제 B부터 그대로 적용)

1. ID / 데이터 나누기 → ID `0x100`, data[0] = `0xB8`, data[1] = `0x0B`, 나머지 `0x00`
2. 정의서에서 찾기 → VehicleSpeed: start bit 0, 길이 16 → 비트 0~15 = **data[0], data[1]**. Intel(Little-endian), factor 0.01
3. raw 만들기 → Little-endian이라 **data[1]을 큰 자리로**: `0x0B`,`0xB8` → `0x0BB8` (적힌 순서대로 `0xB80B`로 붙이면 틀림!)

```
0x0BB8 = 0×4096 + 11×256 + 11×16 + 8×1 = 0 + 2816 + 176 + 8 = 3000
```

4. 물리값 → 3000 × 0.01 + 0 = 30.00

- raw = → **0x0BB8 = 3000**
- 차속 = → **30.00** km/h

### 문제 B

```
100#3075000000000000
```

- raw = → 30000 ✅ (data[1] `0x75`, data[0] `0x30` → `0x7530` = 0x75 × 256 + 0x30 = 117 × 256 + 48 = 29952 + 48 = 30000)
- 차속 = → 300.00km/h ✅ (30000 × 0.01)

### 문제 C

```
200#0900000000000000
```

- data[0]을 2진수로 → 0000 1001 ✅
- 열린 문 → DoorFL, DoorRR ✅ (운전석, 뒷좌석 오른쪽)

```
data[0] = 0x09 =  0  0  0  0  1  0  0  1
비트 번호:        7  6  5  4  3  2  1  0
신호:            [예약 ] Tr RR RL FR FL
                             ↑        ↑
                        RR 열림    FL 열림
```

### 문제 D

```
300#0201000000000000
```

> (같이 푼 문제) 신호가 2개 → 신호마다 "위치 찾기 → 잘라내기"

1. 바이트 나누기 → data[0] = `0x02`, data[1] = `0x01`
2. 위치 찾기 → IgnState: start 0, 길이 2 → data[0]의 아래 2비트 / Gear: start 8, 길이 3 → 8 ÷ 8 = 1, 8 % 8 = 0 → **data[1]의 아래 3비트**
3. IgnState → `0x02 & 0x03` = `0000 0010 & 0000 0011` = **2**
4. Gear → `0x01 & 0x07` = `0000 0001 & 0000 0111` = **1**

- IgnState = → **2 = ON**
- Gear = → **1 = R** (후진)
- 문제 A와 다른 점 → 신호가 바이트보다 크면 **합치고**(엔디안), 바이트보다 작으면 **잘라낸다**(마스크). M2-1 `can_get_bits()`가 둘 다 한다

### 문제 E

```
300#0307000000000000
```

- IgnState = → START ✅ (`0x03 & 0x03` = 3)
- Gear = → (주의!) 무효 ✅ (`0x07 & 0x07` = 7 → 정의서상 0~3만 유효, 4~7은 무효)
- 함정의 의미 → 3비트라서 0~7까지 **담을 수는 있지만**, 정의된 값은 0~3(P/R/N/D)뿐이다. 받은 값을 그대로 기어로 믿으면 안 되고 **범위를 검사**해야 한다. C의 `enum`은 그냥 정수라서 7이 들어와도 에러가 안 난다 → M2-5에서 `GEAR_INVALID`로 매핑 (DLC 4비트에 9~15가 들어올 수 있는 것과 같은 문제)

### 문제 F (거꾸로: 프레임 만들기)

BCM이 **WARNING 상태**이고, **도어 잠금 명령 1**, **경고음 ON**, **AliveCounter 12**일 때 보낼 0x400 프레임은?

```
400#020300000000000C
```

- data[0] = 0x02 ✅ (BcmState WARNING = 2 → bit 0~1에 `10`)
- data[1] = 0x03 ✅ (DoorLockCmd = 1 → bit 8 = data[1]의 0번 / WarningBuzzer = 1 → bit 9 = data[1]의 1번 → `0000 0011`)
- data[7] = 0x0C ✅ (AliveCounter 12 → bit 56~59 = data[7]의 아래 4비트 → 12 = `1100` → `0000 1100`)
- 정답 → `400#020300000000000C` ✅ (예약 칸 data[2]~data[6]은 규칙대로 0)
- 해석(디코딩)과의 차이 → 해석은 `>>`와 `&`로 **꺼내고**, 만들기(인코딩)는 `<<`와 `|`로 **넣는다**. M2-2 `can_set_bits()`, M4-8 BCM_STATUS 송신이 이 작업

## 4. 설계 질문

- 모든 메시지의 DLC를 8로 통일하고 "최소 길이"를 따로 둔 이유 → **"보내는 쪽 규칙"과 "받는 쪽 규칙"을 나눈 것**이다
  - **DLC 8 통일 (보내는 쪽):** 지금은 2바이트만 쓰지만 나중에 신호를 추가해도 DLC를 안 바꿔도 된다. 모든 메시지 길이가 같아 다루기도 단순하다
  - **최소 길이 (받는 쪽):** 디코더가 **안전하게 읽으려면 최소 몇 바이트가 와야 하는지.** 차속은 data[0], data[1]만 있으면 해석할 수 있다. DLC가 1인 프레임이 오면 data[1]은 의미 없는 값이라, 읽으면 엉뚱한 차속이 나온다 → 버린다 (M2-6)
  - 그래서 DLC가 8이 아니어도 최소 길이만 넘으면 받아준다 → "보낼 때는 엄격하게, 받을 때는 너그럽게" (견고성 원칙)
- 예약 비트를 "0으로 보내고, 받는 쪽은 무시"하는 이유 → **나중을 위한 빈자리**다
  - 정의서 다음 버전에서 예약 비트에 새 신호를 넣어도, **옛날 수신 제어기는 무시하니까 고장 나지 않는다** (하위 호환)
  - 새 수신 제어기가 옛날 송신 제어기의 메시지를 받으면 그 자리가 0 → **"기본값/없음"**으로 해석할 수 있다. 그래서 0으로 보내기로 약속한다
  - 웹으로 치면 JSON 응답에 새 필드를 추가해도 옛날 클라이언트가 모르는 필드를 무시하면(Jackson `FAIL_ON_UNKNOWN_PROPERTIES = false`) 안 깨지는 것과 같다
- 0x400의 AliveCounter를 맨 뒤 바이트(bit 56)에 둔 이유 (힌트: 앞쪽 바이트에 나중에 신호를 추가한다면?) →
  - 앞쪽(data[0]부터)에 상태 신호를 채우고 AliveCounter를 맨 뒤에 두면, 그 사이 **data[2]~data[6]이 이어진 빈 공간**으로 남는다 → 나중에 신호를 추가하기 쉽다. AliveCounter가 중간에 있으면 빈 공간이 쪼개진다
  - 실무에서도 메시지 보호용 값(AliveCounter, 체크섬)은 **맨 앞이나 맨 뒤 바이트에 고정**하는 경우가 많다 (AUTOSAR E2E 보호). 위치가 정해져 있으면 어떤 메시지든 같은 코드로 검사할 수 있다
