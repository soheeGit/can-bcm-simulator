# 40. canplayer로 E2E 테스트 (M5-10)

> 코드: `scripts/e2e_replay.sh` (★ `run_live()` 안의 TODO: `kill`, `wait`, 종료 코드), `Makefile`(`make e2e`)
> 실행 (VM 안): `make e2e` 또는 `./scripts/e2e_replay.sh 02 03`
> 한 번 도는 데 약 1분 (시나리오마다 실제로 10초씩 재생하니까)

## 0. 직접 채우기

| 확인 (`./scripts/e2e_replay.sh 01`) | 결과 |
| --- | --- |
| 채우기 전 | `exit 99` ❌ FAIL — `종료 코드 99`, `요약이 없음`, `최종 상태: 기대 IDLE / 실제 없음` (전이 규칙 T3 T7, 시간 차는 맞음) |
| 채운 뒤 (`make e2e`) | ✅ 6개 전부 PASS, 종료 코드 0 (Claude가 채움) |

```bash
kill -TERM "$pid"      # 1) bcm_sim에 SIGTERM → M5-9의 핸들러가 "멈춰" 표시
wait "$pid"            # 2) bcm_sim이 정리하고 끝날 때까지 기다림. wait의 종료 코드 = 그 프로세스의 종료 코드
local code=$?          # 3) $? = 방금 명령(wait)의 종료 코드 → 0이면 정상 종료
```

- `$!` = 방금 `&`로 백그라운드에 띄운 프로세스의 번호(pid). 그래서 `"$BIN" ... &` 바로 다음 줄에서 `pid=$!`로 받아 둔다
- `$?` = **바로 앞** 명령의 종료 코드. 다른 명령을 하나라도 끼우면 그 명령의 코드로 바뀐다 → `wait` 바로 다음 줄에서 받는다
- 채우기 전에도 "전이 규칙"과 "시간 차"는 맞았다. 그런데도 요약이 없는 이유 → 판단(전이)은 재생 **도중에** 로그로 이미 찍혔다. 요약은 `bcm_sim`이 **정상 종료할 때** `main`이 찍는데, 채우기 전에는 SIGTERM을 안 보내고 안전장치의 `kill -KILL`(SIGKILL)로 바로 죽였다 → 우리 코드가 한 줄도 더 못 돌아서 요약이 없다. 종료 코드는 스크립트의 기본값 99 그대로
- `kill -TERM` 대신 `kill -9`(SIGKILL)를 쓰면 어떻게 되나 (39번 노트 2번) → VM에서 확인: **종료 코드 137**(= 128 + 9), **요약 0줄**, 셸이 `Killed`. SIGKILL은 잡을 수 없어서 M5-9의 정리 경로를 못 탄다 → 3)의 "정상 종료", 4)의 "최종 상태" 확인이 전부 실패
- `wait`를 빼면 무엇이 문제인가 (두 가지)
  1. **종료 코드를 못 받는다.** 백그라운드 프로세스의 종료 코드는 `wait`로만 받을 수 있다 (`$?`는 `kill` 명령 자체의 결과 = "신호를 보냈다"(0)일 뿐, bcm_sim이 잘 끝났는지가 아니다)
  2. **아직 끝나지 않았는데 로그를 읽는다.** SIGTERM을 받은 bcm_sim이 소켓 닫고 요약을 쓰는 데 잠깐 걸린다. 그 사이에 비교를 시작하면 요약이 없을 수 있다 (**경쟁 상태, race condition**). VM에서 `wait` 없이 해 보니 이번엔 바로 요약이 있었다 → **운 좋게** 빨랐을 뿐. 컴퓨터가 바쁘면 실패한다. 다음 시나리오의 bcm_sim과 겹쳐 돌 수도 있다
  - Java로: `Process p = pb.start(); p.destroy(); int code = p.waitFor();` — `waitFor()`가 `wait`. 안 부르면 프로세스가 끝났는지도, 결과도 모른다

## 1. E2E 테스트란

```
단위 테스트 (make test)            E2E 테스트 (make e2e)
───────────────────────           ─────────────────────────────────────────────
함수 하나씩 (가짜 소스, 파일)        진짜 프로그램 + 진짜 vcan0 + 진짜 canplayer + 진짜 시그널
빠름 (몇 초), 맥에서도              느림 (1분), VM에서만
"부품이 맞나"                      "다 조립해서 실제로 돌리면 맞나"
```

- 단위 테스트(`test_frame_loop`, `test_can_socket` ...)가 다 통과하는데 E2E가 또 필요한 이유 → 단위 테스트는 **부품을 따로** 확인한다. 부품이 다 맞아도 **조립(연결)**에서 틀릴 수 있다
  - 예: `main.c`가 필터 목록을 잘못 넘김, `-o`를 소켓 출력과 같이 못 씀, SIGTERM 핸들러를 실시간 모드에서 안 걸어 둠 — 각 함수 테스트는 통과하지만 **프로그램 전체**로는 틀린다. `main.c`는 단위 테스트가 아예 없다 (정거장 1 질문 3)
  - 진짜 환경에서만 생기는 것: 실제 시각 흐름(canplayer가 10초 동안 보냄), 커널 필터, 소켓 버퍼, 프로세스 종료와 시그널. 가짜 소스로는 흉내만 냈다
  - "실제 사용자가 하는 그대로" 돌려 보는 마지막 확인 = 출시 전 점검. 여기서 PASS면 "M5가 동작한다"고 말할 수 있다
- 웹 개발에서 같은 것 (테스트 피라미드) →

```
        /\        E2E      : Selenium / Playwright로 브라우저 띄워 실제 화면 클릭   ← 우리 make e2e
       /  \                  (느리고 깨지기 쉬움 → 적게, 중요한 흐름만)
      /----\      통합      : @SpringBootTest + Testcontainers(진짜 DB)            ← test_scenarios, test_can_socket
     /      \
    /--------\    단위      : JUnit + Mockito                                     ← test_bcm, test_frame_loop (가짜 소스)
                              (빠르고 많이)
```

## 2. 무엇과 비교하나: 파일 모드 = 정답지

| 확인 | 어떻게 |
| --- | --- |
| 전이 규칙 순서 | 파일 모드의 `STATE` 줄과 실시간의 `STATE` 줄에서 규칙만 뽑아 비교 (`T3 T6 T9 T7`) |
| 시간 | 첫 전이를 0으로 맞춘 뒤, 각 전이의 시각 차이가 `TOL_MS`(200ms) 안인지 |
| 정상 종료 | SIGTERM 후 종료 코드 0, 요약이 있는가 |
| 최종 상태 | 요약의 `최종 상태`가 같은가 |
| 0x400 | `-o`로 기록한 줄 수가 파일 모드 개수보다 크게 적지 않은가 |

- 기대값(1.8초에 T3 ...)을 스크립트에 직접 적지 않고, 매번 **파일 모드를 돌려서** 정답으로 쓰는 이유 → 파일 모드는 이미 `test_scenarios`(M4-7)로 기대값이 **검증된** 결과다. 그걸 기준으로 쓰면 E2E는 "**실시간 모드 = 파일 모드**"만 확인하면 된다 (M5-5의 목표 "소스만 바꿨고 판단은 같다" 그 자체)
  - 기대값을 두 군데(`test_scenarios.c`와 스크립트)에 적으면, 시나리오나 규칙을 바꿀 때 한쪽을 잊는다 (37번 노트 3번의 "한 가지 사실은 한 곳에"). 지금은 시나리오를 추가해도 스크립트를 안 고쳐도 된다
  - 이런 "정답을 대신 알려 주는 것"을 테스트에서 **오라클(oracle)**이라고 부른다. 리팩터링 전 버전, 다른 구현, 참조 구현을 오라클로 쓰는 경우가 많다
- 절대 시각(1.800s)이 아니라 "첫 전이를 0으로 맞춘 간격"으로 비교하는 이유 → 실시간의 0초는 `bcm_sim`을 **켠 순간**이고, `canplayer`가 시작하기까지(0.3초 + α) 밀린다 (35번 노트 2번). 이 밀림은 매번 다르고 판단과 상관없다 → 첫 전이를 기준점으로 맞추면 밀림이 사라지고 **판단 사이의 간격**만 남는다
- 실행 결과에서 03, 07만 시간 차가 50ms 넘게 나는 이유 (38번 노트 3번) → 둘 다 **신호 끊김(T5)**이 있는 시나리오다. 파일 모드는 다음 프레임이 와야 판단해서 "마지막 수신 + 600ms"에 알고, 실시간은 10ms마다 판단해서 "+ 500 ~ 510ms(+ VM 지연)"에 안다 → 실시간이 **더 빨리** 안다. 나머지 전이는 프레임 값으로 정해져서 0 ~ 1ms
  - 즉 이 차이는 버그가 아니라 **실시간 쪽이 더 정확해서** 생긴 차이. 그래서 "정확히 같아야 한다"가 아니라 허용 오차를 둔다

## 3. 실험

| 실험 | 결과 |
| --- | --- |
| `TOL_MS=10 ./scripts/e2e_replay.sh 01 03` | 01 ✅, 03 ❌ `시간 차 83ms > 허용 10ms`, 종료 코드 1 → **스크립트가 실패를 제대로 잡는다** |
| `make e2e`를 여러 번 돌려서 03, 07의 `max_diff` 비교 | 1회: 03 **55** / 07 **65**ms, 2회: **52** / **51**ms, 3회: **99** / **59**ms. 나머지(01, 02, 05, 06)는 매번 0 ~ 1ms |
| 재생 도중 `cansend vcan0 200#01`을 0.5초 간격으로 4번 | ✅ PASS. 전이 그대로 `T3 T7` |
| 재생 도중 `200#01`을 **한꺼번에 3번** (10ms 안에) | ❌ FAIL `규칙이 다름: 기대 [T3 T7] / 실제 [T3 T6 T9 T7]` |

- 0.5초 간격 4번은 왜 아무 일도 없었나 → **디바운싱(M4-5)**: 문은 도어 프레임 **3개 연속** 같은 값이어야 인정한다. canplayer가 100ms마다 "닫힘"(`200#00`)을 보내니까, 끼워 넣은 "열림"은 매번 1개뿐 → 노이즈로 무시. 설계대로 동작
- 한꺼번에 3번은 왜 FAIL인가 → 10ms 안에 "열림"이 3개 **연속**으로 들어가서 디바운싱을 통과 → 달리는 중 문 열림 = T6(WARNING) → 다음 "닫힘" 3개로 T9. BCM은 **옳게** 판단했다. 시나리오에 없는 입력을 넣었으니 정답지(파일 모드)와 달라진 것 → E2E가 "입력이 바뀌면 결과도 바뀐다"를 잡아냈다
  - 그래서 E2E를 돌릴 때는 **다른 프로그램이 vcan0에 보내지 않아야** 한다 (스크립트가 돌고 있는 `canplayer`를 확인하는 이유. `cansend`는 못 막는다)
- `TOL_MS`를 200ms로 정한 근거, 너무 작게 / 너무 크게 하면 →
  - 근거: 정상 차이는 ① 신호 끊김을 일찍 아는 것(파일 600ms vs 실시간 500ms → 최대 약 100ms) + ② VM 타이머 지연(38번 노트 4번: 10ms 요청이 최대 54ms). 실측 최대 99ms → 그 두 배 정도로 여유
  - 너무 작게(10ms): 정상인데도 실패 → 테스트를 안 믿게 된다 (위 실험)
  - 너무 크게(1000ms): 진짜 버그(예: 타임아웃이 500ms가 아니라 1000ms로 잘못 바뀜)를 못 잡는다. 디바운싱 지연(200ms) 같은 규칙 단위의 차이보다는 작아야 의미가 있다
- 여러 번 돌렸을 때 `max_diff`가 매번 다른 이유. 이런 테스트를 뭐라고 부르나 → 실시간 판단 시각이 **OS 스케줄링과 VM 타이머**에 따라 매번 수십 ms씩 흔들리기 때문 (38번 노트 4번). 같은 코드, 같은 입력인데 결과가 조금씩 다르다
  - 이런 테스트를 **flaky test**(가끔 실패하는 테스트)라고 부른다. 허용 오차가 빡빡하면 "10번 중 1번 실패"가 생긴다
  - 대처: 시간처럼 흔들리는 값은 **범위**로 비교, 규칙 순서처럼 흔들리면 안 되는 값은 **정확히** 비교 (이 스크립트가 그렇게 나눴다). 단위 테스트는 가짜 시계로 흔들림 자체를 없앴다 (`test_silence_keeps_judging`)

## 4. 한계

- 04(이상한 프레임)를 뺀 이유 → `canplayer`는 깨진 줄(`100#10G7...`)을 만나면 **거기서 재생을 멈춘다** (32번 노트 3번). 우리 파서는 건너뛰고 계속 읽으니 결과가 달라질 수밖에 없다 → 04는 "이상한 입력에도 안 죽는지"를 보는 **파일 모드 전용** 시나리오
  - 소켓으로는 애초에 "깨진 줄"이 올 수 없다 (프레임은 늘 16바이트 구조체). 소켓 쪽의 "이상한 입력"(29비트 ID, Remote)은 `test_can_socket`이 확인한다
- 이 E2E가 확인하지 못하는 것 →
  - **0x400의 내용**: 개수만 본다. 잠금 명령 비트, Alive Counter 순서, 상태 값까지 비교하려면 `-o` 기록을 파싱해야 한다 (내용은 단위 테스트 `test_tx_round_trip`, `test_sinks_get_tx`가 확인)
  - **"아무 프레임도 안 올 때"**: 재생이 끝나고 0.2초 만에 끄므로, 500ms 뒤의 신호 끊김(M5-8)은 안 본다 (`test_silence_keeps_judging`이 확인)
  - **진짜 CAN 하드웨어**: vcan은 ACK, 버스 오류, bus-off, 송신 실패(`ENOBUFS`)가 없다 (36번 노트 4번)
  - **여러 노드가 동시에 보낼 때의 순서**: 시나리오는 0x300 → 0x200 → 0x100 순서로만 온다
  - 시간이 흔들려서 가끔 실패할 수 있다 (flaky). CI(GitHub Actions)에서 돌리려면 vcan 커널 모듈이 필요해서 지금은 VM에서 손으로만 돌린다

## 5. 정리 (M5 회고)

- 이번 이슈를 한 줄로 → 시나리오를 `canplayer`로 vcan0에 진짜로 재생하고, `kill`(SIGTERM)로 정상 종료시킨 뒤, 실시간 결과(전이 규칙, 간격, 종료 코드, 최종 상태, 0x400)가 **파일 모드 결과와 같은지** 자동으로 비교하는 스크립트(`make e2e`)를 만들었다. 6개 시나리오 전부 PASS
