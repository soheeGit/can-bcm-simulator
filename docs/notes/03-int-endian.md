## 실험 1: 정수 타입의 크기 (`01_int_sizes.c`)

| 타입 | 예상 (바이트) | 실제 (맥) | 실제 (컨테이너) |
| --- | --- | --- | --- |
| `char` | 1 | 1 | 1 |
| `short` | 2 | 2 | 2 |
| `int` | 4 | 4 | 4 |
| `long` | 8 | 8 | 8 |
| `void *` | 8 | 8 | 8 |
| `uint8_t` / `uint16_t` / `uint32_t` | 1, 2, 4 | 1, 2, 4 | 1, 2, 4 |

참고: 다른 환경에서는 이렇게 다르다

| 타입 | 맥 / 리눅스 (64비트) | Windows (64비트) | 32비트 MCU | 16비트 MCU |
| --- | --- | --- | --- | --- |
| `int` | 4 | 4 | 4 | **2** |
| `long` | 8 | **4** | 4 | 4 |
| 포인터 | 8 | 8 | **4** | **2** |
| `uint32_t` | 4 | 4 | 4 | 4 |

- `int` 대신 `uint32_t` 같은 고정폭 타입을 쓰는 이유 → int, long은 플랫폼마다 크기가 다르다(16비트 MCU에서 int = 2바이트). uint32_t 같은 고정폭 타입은 어디서든 크기가 같아서, 같은 코드가 맥과 차량 MCU에서 똑같이 동작한다.
- CAN 신호(예: 16비트 차속)를 담을 때 어떤 타입을 써야 하나? → uint16_t. 신호 길이(16비트)와 크기가 같고, 차속은 음수가 없으니 unsigned를 쓴다.
- `u`(unsigned)와 아무것도 없는 것(signed)의 차이 → unsigned는 음수가 없고 0부터 시작한다. signed는 음수를 포함한다. 비트 수가 같아서 표현할 수 있는 개수는 같고 범위만 다르다 (uint8_t 0~255, int8_t -128~127).

## 실험 2: 오버플로우 (`02_overflow.c`)

| 번호 | 예상 | 실제 |
| --- | --- | --- |
| [1] `uint8_t` 255 + 1 | 0 | 0 |
| [2] `uint8_t` 0 - 1 | 255 | 255 |
| [3] `uint32_t` 3 - 5 | 4294967294 | 4294967294 |
| [4] `(uint16_t)70000` | 4464 | 4464 |
| [5] `int8_t` 127 + 1 | 이식성 있는 결과를 보장할 수 없음 | 범위를 벗어난 signed 정수 변환 결과는 구현에 따라 달라질 수 있음 |

- unsigned가 범위를 넘으면 어떻게 되나? (자동차 주행거리계 비유) → 표현 가능한 최댓값을 넘으면 0부터 다시 시작하고, 0에서 빼면 최댓값으로 돌아간다. 자동차 주행거리계 숫자가 최댓값 다음에 0으로 돌아가는 것과 비슷하다.
- [4]가 4464인 이유 (70000 - 65536 = ?) → uint16_t의 범위는 0~65535(65536가지)이고, 범위를 넘는 값은 65536으로 나눈 나머지만 남는다. 70000 - 65536 = 4464이므로 저장 결과는 4464다.
- [3]처럼 unsigned 뺄셈이 위험한 경우 (예: 타임아웃 계산 `now - last`) → uint32_t에서 3 - 5를 계산하면 음수 -2가 아니라 4294967294가 된다. 따라서 타임아웃 계산에서 시간 값의 순서와 조건을 잘못 처리하면 예상하지 못한 큰 값이 나올 수 있다.
- signed 오버플로우가 "정의되지 않은 동작(UB)"이라는 건 무슨 뜻인가? → signed 정수의 산술 연산 결과가 표현 범위를 넘으면 C 언어 표준이 결과를 보장하지 않는다. 컴파일러나 실행 환경에 따라 예상과 다르게 동작할 수 있으므로 결과를 믿으면 안 된다.

## 실험 3: 정수 승격 (`03_promotion.c`)

| 번호 | 예상 | 실제 |
| --- | --- | --- |
| [2] `sizeof(a + b)` (a, b는 `uint8_t`) | 2 | 4 |
| [3] `a + b` (200 + 100) | 300 | 300 |
| [4] `uint8_t sum = a + b` | 44 | 44 |
| [5] `x << 1` (x = 0x80) | 256 | 256 |
| [6] `(uint8_t)(x << 1)` | 0 | 0 |
| [8] `~m == 0xF0` (m = 0x0F) | false | false |
| [9] `(uint8_t)~m == 0xF0` | true | true |

- 정수 승격이란? → 작은 정수 타입으로 연산할 때 값이 int 또는 unsigned int로 변환되는 것이다.
- [3]은 300인데 [4]는 44인 이유 → 덧셈 결과는 300이지만, uint8_t에 저장할 때 8비트 범위로 변환되어 44가 된다.
- [8]이 false인 이유 → ~m 연산 전에 m이 int로 승격되어 32비트 전체가 반전된다. 따라서 결과는 0xF0와 같지 않다.
- 비트 연산 결과를 `uint8_t`로 다시 담을 때 주의할 점 → 연산 중에는 int로 승격될 수 있으므로, 연산 결과의 타입과 저장 시 변환되는 값을 구분해야 한다.

## 실험 4: 엔디안 (`04_endian.c`)

`uint32_t v = 0x12345678;` 이 메모리에 저장된 순서:

| 주소 | p[0] | p[1] | p[2] | p[3] |
| --- | --- | --- | --- | --- |
| 예상 | 0x12 | 0x34 | 0x56 | 0x78 |
| 실제 | 0x78 | 0x56 | 0x34 | 0x12 |

- 이 컴퓨터(맥 / 컨테이너)는? → Little-endian
- Little-endian과 Big-endian의 차이 → Little-endian은 낮은 자리의 바이트(LSB)를 낮은 메모리 주소에 먼저 저장하고, Big-endian은 높은 자리의 바이트(MSB)를 낮은 메모리 주소에 먼저 저장한다.
- 이름의 유래 (LSB/MSB 중 무엇이 앞에 오나) → Little-endian은 LSB가 먼저 오고, Big-endian은 MSB가 먼저 온다.

## 실험 5: 바이트 배열 → 숫자 조립 (`05_assemble.c`)

`uint8_t data[2] = {0x10, 0x27};`

| 번호 | 예상 | 실제 |
| --- | --- | --- |
| [1] Little-endian 조립 | 0x2710 | 0x2710 = 10000 |
| [2] Big-endian 조립 | 0x1027 | 0x1027 = 4135 |
| [3] 차속 (LE, ×0.01) | 100.00 km/h | 100.00 km/h |
| [4] memcpy 결과 | 0x2710 | 0x2710 |

- Little-endian 조립식 `data[0] | (data[1] << 8)` 해석 → data[0]은 낮은 8비트에, data[1]은 왼쪽으로 8비트 이동해 높은 8비트에 배치한다. 결과는 0x2710이다.
- Big-endian 조립식 `(data[0] << 8) | data[1]` 해석 → data[0]을 왼쪽으로 8비트 이동해 높은 8비트에, data[1]을 낮은 8비트에 배치한다. 결과는 0x1027이다.
- [4] memcpy 결과가 [1]과 같은 이유 → 현재 컴퓨터가 Little-endian이므로 복사된 메모리의 바이트 순서를 uint16_t로 해석하면 0x2710이 된다.
- 그런데도 memcpy 대신 시프트로 조립하는 이유 (Big-endian CPU에서 돌리면?) → 시프트 조립은 엔디안 규칙을 코드에 명시하므로 CPU의 메모리 엔디안에 영향을 받지 않는다. 반면 memcpy로 복사한 바이트를 정수로 해석하면 CPU의 엔디안에 따라 값이 달라질 수 있다.
- [5]에서 시프트 전에 `(uint32_t)`로 바꾸는 이유 (힌트: 실험 3의 승격 + `0xFF << 24`) → `uint8_t`는 시프트 전에 signed int로 승격된다. `0x12 << 24`(= 0x12000000)는 int 범위 안이라 괜찮지만, 윗바이트가 0x80 이상이면(예: `0xFF << 24` = 0xFF000000) int의 부호 비트를 넘어서 정의되지 않은 동작(UB)이 된다. 데이터 값에 따라 터지는 버그라서, 항상 uint32_t로 바꾼 뒤 시프트한다.

## 실험 6: printf 포맷 (`06_printf.c`)

| 포맷 | 용도 | 예시 결과 |
| --- | --- | --- |
| `%u` | 부호 없는 10진수 출력 | 7 |
| `%d` | 부호 있는 10진수 출력 | -1 |
| `%X` | 대문자 16진수 출력 | A |
| `%02X` | 대문자 16진수, 최소 2자리, 빈자리는 0 | 07 |
| `%zu` | sizeof 결과인 size_t 출력 | 4 |
| `PRIu16`, `PRIx32` | 고정 폭 정수 타입에 맞는 포맷 지정자 제공 | 10000, 100 |

- -1을 `%u`로 출력하면 4294967295가 나오는 이유 → -1을 32비트 unsigned int로 변환하면 (2^{32}-1)이 되기 때문이다.
- CAN 데이터 바이트를 출력할 때 `%02X`를 쓰는 이유 → 한 바이트를 07, 0A, FF처럼 두 자리 16진수로 통일해 로그를 읽기 쉽게 만들기 때문이다.

## 정리: CAN 프로젝트에서 지킬 규칙

- 고정폭 정수 타입 사용: CAN 신호의 비트 길이에 맞춰 uint8_t, uint16_t, uint32_t 등을 사용한다. 단, 실제 신호의 부호와 범위에 맞는 타입을 선택한다.
- 바이트 조립 시 엔디안 명시: 여러 바이트로 된 CAN 신호를 해석할 때는 신호 정의서의 바이트 순서를 확인하고, 시프트와 비트 연산으로 명시적으로 조립한다.
- 정수 연산과 출력 타입 확인: unsigned 오버플로우, 정수 승격, 시프트 연산의 범위를 주의하고, printf()에서는 타입에 맞는 포맷 지정자를 사용한다.
