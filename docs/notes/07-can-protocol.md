## 1. CAN이 뭐야?

- CAN = Controller Area Network
- 차 안의 제어기(ECU)들이 서로 데이터를 주고받는 통신 방식
- 왜 만들었나? (힌트: 1980년대 차 안의 전선 문제) → 예전에는 제어기끼리 주고받는 신호마다 **전선을 따로** 깔았다. 기능이 늘수록 전선이 폭발적으로 늘어서 무겁고, 비싸고, 고장 나기 쉬웠다. 1986년 독일 **보쉬(Bosch)**가 "모든 제어기가 **선 2개를 공유**하고 메시지로 주고받자"며 CAN을 발표했다. 1991년 벤츠가 처음 양산차에 적용했고, 지금은 거의 모든 차에 들어간다.

```
예전 (점대점 배선)               CAN (버스)
엔진 ──── 계기판                 엔진  ESC  BCM  계기판
엔진 ──── ESC                     │    │    │    │
ESC  ──── 계기판                ══╪════╪════╪════╪══  선 2개면 끝
BCM  ──── 계기판 ...
→ 제어기가 늘면 전선이 폭발
```

- 특징 키워드 → 선 2개 공유(버스), 브로드캐스트, ID = 내용 + 우선순위, 비파괴적 중재, 최대 8바이트, 강한 오류 검출(CRC, ACK), 잡음에 강함(차동 신호)

## 2. 버스(Bus) 구조

```
   ECU(엔진)    ECU(ESC)    ECU(BCM)    ECU(클러스터)
      │            │           │            │
 ═════╪════════════╪═══════════╪════════════╪═════  CAN_H
 ═════╪════════════╪═══════════╪════════════╪═════  CAN_L
 [120Ω]                                        [120Ω]
```

- 선 2개(CAN_H, CAN_L)에 모든 제어기가 **같이** 매달려 있다 (보통 서로 꼬아서 깐다: twisted pair)
- 0과 1을 보내는 방법: 두 선의 **전압 차이**

| 값 | CAN_H | CAN_L | 차이 | 이름 |
| --- | --- | --- | --- | --- |
| 0 | 3.5V | 1.5V | 2V (벌어짐) | dominant (우세) |
| 1 | 2.5V | 2.5V | 0V (같음) | recessive (열세) |

- 두 선의 **전압 차이**로 0과 1을 구분하는 이유 (차동 신호) → 차 안은 엔진, 모터 때문에 전기 잡음이 심하다. 잡음은 두 선에 **똑같이** 들어오므로 전압은 같이 출렁여도 **차이는 그대로**다 → 잡음에 강하다. (흔들리는 배 위에서 두 사람의 키 차이를 재는 것과 같다)

```
          잡음 없음    잡음 +1V
CAN_H :     3.5V   →   4.5V
CAN_L :     1.5V   →   2.5V
차이  :     2.0V   →   2.0V   ← 그대로 0으로 읽힘
```

- 양 끝의 120Ω 저항(종단 저항)의 역할 → 신호가 선 끝에 부딪혀 **되돌아오는 것(반사)**을 막는다. 반사된 신호가 다음 비트와 섞이면 0/1이 깨진다.

## 3. 브로드캐스트 & ID의 의미

- CAN 메시지에는 "누구에게" 보내는지(수신자 주소)가 있나? → **없다.** 버스에 올리면 연결된 모든 제어기가 받는다 (브로드캐스트)
- 그럼 ID는 무엇을 뜻하나? → **"무슨 내용인지"** (메시지의 주제 번호). 예: `0x100` = 차속, `0x200` = 도어 상태. 그리고 **우선순위**(작을수록 급함, 5번 중재)
- 받는 쪽은 필요 없는 메시지를 어떻게 하나? → ID를 보고 **무시**한다 (하드웨어/커널 필터로 아예 안 받게 할 수도 있다 → M5-7)
- 예: ESC가 `0x100`(차속)을 보내면 누가 받나? → **모두 받는다.** BCM은 자동잠금 판단에, 클러스터는 계기판 표시에 쓰고, 필요 없는 제어기는 무시한다
- 백엔드 비유: **Kafka topic**. ID = topic 이름, 송신 = publish, 필요한 제어기만 읽음 = subscribe. 보내는 쪽은 누가 받는지 몰라도 된다. (HTTP는 `POST /api/orders`처럼 받는 서버를 정해서 보낸다)

## 4. Standard vs Extended ID

| | Standard | Extended |
| --- | --- | --- |
| ID 길이 | 11비트 | 29비트 |
| ID 범위 | `0x000` ~ `0x7FF` | `0x00000000` ~ `0x1FFFFFFF` |
| 표현 가능한 ID 개수 | 2¹¹ = 2,048개 | 2²⁹ = 약 5억 3천만 개 |
| 다른 이름 | CAN 2.0A | CAN 2.0B |
| 주로 쓰는 곳 | 일반 승용차 | 트럭, 버스, 농기계 (J1939 표준: ID 안에 송신자, 데이터 종류 등을 쪼개 넣음) |
| 우리 프로젝트 | ✅ 사용 | 안 씀 |

- 구분 방법 → 제어 필드의 **IDE 비트** (0 = Standard, 1 = Extended). 같은 버스에 섞여 다닐 수 있다
- 비유 → 사내 내선 번호(짧음, 회사 안에서는 충분) vs 전체 전화번호(지역번호까지 포함)
- 프로젝트에서 지킬 것 → ID는 `0x7FF` 이하. `0x800` 이상은 Standard로 불가능 → `can_frame_is_valid()`에서 거부 (M1-2)

```
0x7FF =  111 1111 1111   ← 11비트 전부 1 = 최댓값 ✅
0x800 = 1000 0000 0000   ← 12번째 비트 필요 ❌
```

- 그래도 `CanFrame.id`는 `uint32_t` → Extended(29비트)도 담을 수 있게 여유를 둔다 (Linux `struct can_frame`과 동일)

## 5. 중재 (Arbitration) — 실험

여러 제어기가 **동시에** 보내려고 하면?

- 규칙: 0 = dominant(우세), 1 = recessive(열세). 버스 = 모든 송신 비트의 _AND_ (AND / OR)
- 실험 결과

| 시나리오 | 경쟁 | 승자 | 몇 번 비트에서 갈렸나 |
| --- | --- | --- | --- |
| 1 | 0x200 vs 0x100 vs 0x300 | SPEED (0x100) | 9번 비트 (DOOR, IGN 동시 탈락) |
| 2 | 0x300 vs 0x200 | DOOR (0x200) | 8번 비트 |
| 3 | 0x101 vs 0x100 | B (0x100) | 0번 비트 (맨 마지막까지 같다가 마지막 비트에서 갈림) |

```
ID를 2진수(11비트)로 쓰면:
0x100 = 001 0000 0000
0x200 = 010 0000 0000   ← 9번 비트가 1 → 0x100(9번 비트 0)에게 짐
0x300 = 011 0000 0000   ← 9번 비트가 1 → 짐 / 0x200과는 8번 비트에서 갈림
0x101 = 001 0000 0001   ← 0x100과 0번 비트만 다름
```

- 결론: ID가 낮을수록 우선순위가 높다 → 앞쪽(높은 자리) 비트부터 비교하면서 **먼저 0이 나오는 쪽이 이기므로**, 결국 숫자가 작은 ID가 이긴다
- "비파괴적 중재"라는 이름의 뜻 (진 쪽의 메시지는 어떻게 되나?) → 밀린다. 더 정확히는:
  - 이긴 쪽의 메시지는 **하나도 깨지지 않고** 그대로 끝까지 전송된다 (다시 보낼 필요 없음) → "비파괴적"
  - 진 쪽은 바로 송신을 멈추고 **받는 쪽으로 돌아서서** 이긴 메시지를 듣는다. 버스가 비면 **자동으로 다시 시도**한다 (하드웨어가 알아서 함)
  - 비교: 이더넷(옛날 방식)은 동시에 보내면 **둘 다 깨지고(충돌)** 둘 다 다시 보내야 했다
- 차속(0x100)이 도어(0x200)보다 ID가 작게 정해진 이유 → 차 속도가 더 신속하게 판단해야 하기 때문에. 차속은 브레이크, 자동잠금, 계기판 등 많은 제어기가 실시간으로 쓰는 중요한 정보라 늦게 도착하면 위험하다. 도어 상태는 조금 늦어도 괜찮다. → **ID 번호 = 우선순위 설계**. 실차에서는 브레이크, 에어백 관련 메시지가 가장 작은 ID를 받는다
- 시뮬레이터 코드에서 `bus &= ...`가 하는 일 → 경쟁 중인 모든 노드의 현재 비트를 **AND로 합친다.** `bus`를 1로 시작해서, 누구 하나라도 0을 보내면 `1 & 0 = 0`이 되어 버스가 0이 된다. "0(dominant)이 1을 이긴다"는 CAN 전기 규칙을 코드 한 줄로 흉내 낸 것. (`(id >> bit) & 1u`는 M0-5의 비트 추출 공식)

## 6. 프레임 구성 (Data Frame)

```
┌─────┬────────┬─────┬────────┬──────────────┬───────┬─────┬───────┐
│ SOF │   ID   │ RTR │  제어  │     Data     │  CRC  │ ACK │  EOF  │
│  1  │   11   │  1  │   6    │    0 ~ 64    │  16   │  2  │   7   │  ← 비트 수
└─────┴────────┴─────┴────────┴──────────────┴───────┴─────┴───────┘
 왼쪽부터 한 비트씩 버스로 나간다
```

| 필드 | 비트 수 | 역할 | 택배 비유 |
| --- | --- | --- | --- |
| SOF (Start of Frame) | 1 | "지금부터 메시지 시작" 신호. 항상 0(dominant). 모든 제어기가 이걸 보고 박자를 맞춘다 | 초인종 |
| ID (Identifier) | 11 | 무슨 내용인지 + 우선순위. **중재(5번)가 여기서 일어난다** | 품목 라벨 |
| RTR | 1 | 0 = 데이터 보냄(Data Frame), 1 = 데이터 달라고 요청(Remote Frame) | 배송 vs 요청 |
| 제어 필드 (DLC 포함) | 6 | Standard/Extended 구분 비트 등 + **DLC 4비트**(데이터 길이) | 송장의 "내용물 개수" |
| Data | 0 ~ 64 (0 ~ 8바이트) | **실제 값** (차속, 도어 상태 등) | 상자 안 내용물 |
| CRC | 16 | 전송 중 비트가 깨졌는지 검사하는 값 (15비트 CRC + 구분 1비트) | 파손 검사 스티커 |
| ACK | 2 | 받는 쪽 **누구든** 잘 받았으면 0을 끼워 넣는 자리. 보내는 쪽은 1을 보내고, 버스가 0이 되면 "누군가 받았다"고 안다 (AND 규칙). 아무도 안 넣으면 자동 재전송 | 수령 확인 서명 |
| EOF (End of Frame) | 7 | "메시지 끝". 1이 7개 연속 | 배송 완료 |

- DLC가 뜻하는 것 → **Data Length Code.** 데이터가 몇 바이트인지 (0 ~ 8). 4비트라 0~15까지 표현은 되지만 일반 CAN은 **8까지만 유효** → 9 이상은 잘못된 값 (M1-2 `can_frame_is_valid`에서 거부)
- 데이터는 최대 몇 바이트? → **8바이트** (64비트). 그래서 `uint8_t data[8]`
- 우리가 코드에서 다룰 부분 (M1-2 `CanFrame`에 들어갈 필드) → **ID, DLC, Data** 3개뿐. SOF, CRC, ACK, EOF는 **CAN 컨트롤러 칩(하드웨어)이 자동 처리**한다. (웹에서 TCP 헤더/체크섬은 OS가 처리하고 우리는 HTTP 바디만 다루는 것과 같다)

```c
typedef struct {
    uint32_t id;       /* ID (11비트지만 Extended 29비트도 담을 수 있게 32비트) */
    uint8_t  dlc;      /* 데이터 길이 0 ~ 8 */
    uint8_t  data[8];  /* 실제 값 */
} CanFrame;           /* Linux struct can_frame도 같은 구성 */
```

- ID 경계: 11비트 최댓값은 `0x7FF`(2047). `0x800`은 12비트라 Standard ID로 잘못된 값

## 7. 프레임 종류

| 종류 | 용도 |
| --- | --- |
| Data Frame | **데이터를 보내는 일반 메시지.** 99%가 이것. 우리 프로젝트가 다루는 것도 이것뿐 |
| Remote Frame | "그 ID의 데이터 좀 보내줘"라는 **요청.** 데이터 칸이 없고 RTR 비트가 1. 실무에서는 거의 안 쓴다 (대부분 메시지가 정해진 주기로 알아서 오기 때문) |
| Error Frame | 어떤 제어기든 **오류를 발견하면** 즉시 보내서 "방금 메시지 깨졌어!"라고 모두에게 알린다. 보낸 쪽은 자동으로 다시 보낸다 |
| Overload Frame | "나 바빠, 다음 메시지 조금만 늦게 보내줘"라는 **지연 요청.** 요즘 하드웨어에서는 거의 안 쓰인다 |

- 어디서 구분하나? → 전부 **같은 버스**를 지나간다. 프레임 안의 비트로 구분한다
  - Data vs Remote → ID 다음의 **RTR 비트** (0 = Data, 1 = Remote)
  - Error → **0이 6개 연속**이라는 특별한 패턴. 정상 메시지는 같은 비트가 5개 연속되면 하드웨어가 반대 비트를 끼워 넣어서(비트 스터핑) 6개 연속이 절대 안 나온다 → 6개 연속 = 경보
  - Overload → Error와 비슷한 패턴인데 메시지와 메시지 **사이**에 나온다
- 코드에서는? → Linux SocketCAN은 `can_id`(32비트)의 **남는 윗비트 3개**에 종류를 표시한다 (ID는 최대 29비트라 위가 비어 있음)

```
 31    30    29    28 ──────── 0
[EFF] [RTR] [ERR] [   ID 29비트   ]
CAN_EFF_FLAG 0x80000000U  → Extended ID
CAN_RTR_FLAG 0x40000000U  → Remote Frame
CAN_ERR_FLAG 0x20000000U  → Error Frame

if (frame.can_id & (CAN_RTR_FLAG | CAN_ERR_FLAG)) { /* 무시 */ }   ← M5-4
```

- 오류에 강한 이유 → 모든 제어기가 **모든 메시지를 감시**하다가 이상하면 Error Frame을 보낸다. 그리고 오류를 자주 내는 제어기는 스스로 버스에서 빠진다(**Bus Off**) → 고장 난 제어기 하나 때문에 버스 전체가 마비되는 걸 막는다
- 우리 코드에서 → Linux SocketCAN에서는 Error Frame도 받을 수 있는데(`CAN_ERR_FLAG`), M5-4에서 **무시**하기로 했다. Remote Frame(`CAN_RTR_FLAG`)도 무시

## 8. CAN FD (참고)

- CAN과 다른 점 (데이터 길이, 속도) →

| | 일반 CAN (Classic CAN) | CAN FD (Flexible Data-rate) |
| --- | --- | --- |
| 데이터 최대 길이 | 8바이트 | **64바이트** |
| 속도 | 최대 1 Mbps | 데이터 구간만 **최대 5~8 Mbps** (ID/중재 구간은 기존 속도 유지) |
| 등장 | 1986년 | 2012년 (보쉬) |
| 쓰는 곳 | 대부분의 차체/공조 등 | 카메라, 레이더, ADAS, 소프트웨어 업데이트처럼 데이터가 많은 곳 |

  - 데이터 구간만 빠르게 하는 이유 → 중재는 모든 제어기가 **동시에 비트를 비교**해야 해서 너무 빠르면 안 된다. 중재가 끝나고 한 명만 보내는 데이터 구간은 빠르게 해도 된다
  - DLC는 그대로 4비트지만, 9 ~ 15를 12, 16, 20, 24, 32, 48, 64바이트에 대응시킨다
- 이 프로젝트에서는? → **일반 CAN만** 다룬다 (BCM의 도어/차속/시동 신호는 8바이트로 충분). M6-4 회고의 "다음에 해볼 것"에 CAN FD 지원을 적어둘 예정. Linux에서는 `struct canfd_frame`(data[64])로 다룬다

## 9. 차량 네트워크에서 BCM(BDC)의 역할

- BCM = **Body Control Module** (차체 제어기). 사람이 직접 만지고 보는 "몸(Body)" 기능 담당
  - **BDC** = Body Domain Controller. BCM + 스마트키 + 게이트웨이 등을 합친 통합 제어기 (현대·기아 명칭, 지원 직무의 "차체제어기 BDC")

| 분야 | 담당 | 예시 제어기 |
| --- | --- | --- |
| 파워트레인 | 달리게 하기 | 엔진(ECM), 변속기(TCU) |
| 섀시 | 멈추고 방향 바꾸기 | 브레이크(ESC), 조향(MDPS) |
| **바디** | **사람이 만지고 보는 것** | **BCM / BDC** |
| 인포테인먼트 | 보고 듣기 | 내비, 오디오 |

- BCM이 담당하는 기능 예시 →
  - 도어: 중앙 잠금, **속도 감응 자동 잠금**, 열림 경고
  - 램프: 전조등, **방향지시등/비상등(깜빡이 → toggle)**, 실내등
  - 와이퍼: 속도, 워셔, 레인센서 자동 와이퍼
  - 창문/미러: 파워 윈도우, 사이드미러 폴딩
  - 경고: 안전벨트 미착용, 키 두고 내림, **주행 중 문 열림**
  - 보안: 스마트키 인증, 도난 경보
- 동작 구조 → **입력 → 판단(상태 머신) → 출력**. 입력은 스위치/센서(직접 배선) + 다른 ECU의 CAN 메시지(차속, 기어 등 BCM이 직접 모르는 정보). 출력은 릴레이/모터(직접 배선) + CAN 메시지(계기판 경고 등). Spring Controller가 요청을 받아 로직을 처리하고 응답하는 구조와 비슷하다
- BCM이 받는 메시지 / 보내는 메시지 (M1-3 신호 정의서와 연결) →

```
받는 메시지                      우리 BCM               보내는 메시지
0x100 차속 (ESC)         ─┐
0x200 도어 상태           ─┼─→  자동잠금 / 경고  ─→  0x400 BCM_STATUS
0x300 시동/기어 (스마트키) ─┘     / Fail-safe         (상태, 잠금 명령, 경고음, AliveCounter)
```

  - 이 프로젝트 기능: 자동 잠금(M4-4), 주행 중 문 열림 경고(M4-3), 신호 끊김 Fail-safe(M4-6)
  - 실차에서는 도어 스위치가 보통 BCM에 **직접 배선**되지만, 이 프로젝트에서는 CAN 연습을 위해 0x200 메시지로 받는다고 가정

## 10. CAN vs HTTP/TCP

| | HTTP / TCP | CAN |
| --- | --- | --- |
| 주소 방식 | 받는 쪽 주소를 지정 (IP:포트, URL) | **주소 없음.** ID는 "무슨 내용인지" |
| 보내는 대상 | 1:1 (특정 서버) | 1:N 브로드캐스트 (모두가 받고 필요한 것만 읽음) |
| 연결 | TCP 3-way handshake로 연결부터 맺음 | 연결 없음. 그냥 버스에 올림 |
| 통신 패턴 | **요청 → 응답** (물어봐야 답함) | **주기적 송신** (안 물어봐도 10ms/100ms마다 보냄) |
| 페이로드 크기 | 사실상 제한 없음 (KB ~ GB) | **최대 8바이트** |
| 우선순위 | 기본적으로 없음 (먼저 온 순서) | **ID가 작을수록 우선** (비파괴적 중재) |
| 메시지 의미 결정 | URL + 메서드 + JSON 스키마 (API 문서, OpenAPI) | ID + 신호 정의서 (DBC) |
| 데이터 형식 | 텍스트(JSON), 사람이 읽을 수 있음 | 비트 단위로 꽉 채운 바이너리 → 비트 연산으로 해석 |
| 오류 처리 | TCP 체크섬 + 재전송, HTTP 상태코드(4xx/5xx), 타임아웃 | CRC + Error Frame + **하드웨어 자동 재전송**, 고장 노드는 스스로 빠짐(Bus Off) |
| 속도 | Mbps ~ Gbps | 125 kbps ~ 1 Mbps |
| 응답 시간 | 들쭉날쭉 (네트워크 상황에 따라) | **예측 가능** (ID 우선순위로 최악의 지연을 계산 가능 → 실시간성) |
| 비유 | 📦 주소 적어 보내는 택배 / 전화 | 📢 건물 전체 사내 방송 / 단톡방 / Kafka topic |

- 속도가 느린데 차에 괜찮은 이유 → "속도"는 두 가지다
  - **대역폭**(1초에 얼마나 많이): CAN 0.5 Mbps < HTTP Gbps
  - **지연 시간**(메시지 하나가 얼마나 빨리 도착): CAN 메시지(약 111비트) ÷ 500 kbps = **약 0.2ms** → 수십~수백 ms인 웹 요청보다 훨씬 빠르고 **예측 가능**
  - 대역폭을 낮게 둔 이유: ① **중재** — 모든 노드가 같은 비트를 동시에 봐야 해서, 신호가 버스 끝까지 갔다 올 시간이 필요 (1 Mbps ≈ 40m, 500 kbps ≈ 100m, 125 kbps ≈ 500m) ② **잡음** — 느리면 비트가 길어져 잡음에 강함 ③ **비용** — 싼 칩과 꼰 선 두 가닥이면 충분 ④ 차체 데이터는 작아서 충분함
  - 데이터가 많은 카메라/라이다는 **차량용 이더넷**(100 Mbps ~ 1 Gbps)을 같이 쓴다
- 이 프로젝트와의 연결
  - **주기적 송신** → 와야 할 메시지가 안 오면 "보낸 쪽이 죽었다"고 판단할 수 있다 → M4-6 신호 타임아웃 & Fail-safe (HTTP 타임아웃 경험과 연결)
  - **8바이트** → JSON `{"speed": 100.00}`만 해도 17바이트. CAN은 여러 신호를 비트 단위로 채워 넣는다 → M2 비트 연산 디코더
  - **ID = 내용** → 받는 쪽은 ID로 어떤 디코더를 쓸지 고른다 → M2-6 메시지 디스패처 (웹의 URL 라우터와 같은 역할)
- 면접용 한 문장 → "HTTP는 주소를 지정해 요청-응답하는 방식이었다면, CAN은 주소 없이 ID로 메시지 내용과 우선순위를 표현해 브로드캐스트합니다. Kafka의 topic 기반 pub/sub과 비슷하지만, ID 중재로 응답 시간을 예측할 수 있다는 점이 다릅니다. 이 프로젝트에서는 HTTP 타임아웃 경험을 살려, 주기적으로 와야 할 CAN 메시지가 끊겼을 때 Fail-safe로 전환하는 로직을 설계했습니다."

## 11. 1분 요약: CAN의 특징 3가지

1. **주소 없는 브로드캐스트** — 모든 제어기가 선 2개(버스)를 공유하고, 메시지에 받는 사람 주소가 없다. ID는 "누구에게"가 아니라 "무슨 내용인지"를 나타내고, 모두가 받아서 필요한 것만 읽는다. (Kafka topic과 비슷)
2. **ID 기반 비파괴적 중재** — 여러 제어기가 동시에 보내면 ID를 한 비트씩 비교해서 0(dominant)이 이긴다. 그래서 ID가 작을수록 우선순위가 높고, 이긴 메시지는 깨지지 않으며 진 쪽은 자동으로 다시 보낸다. → 응답 시간을 예측할 수 있다(실시간성).
3. **작고 튼튼한 메시지** — 데이터는 최대 8바이트라 비트 단위로 신호를 채워 넣는다. 두 선의 전압 차이로 신호를 보내 잡음에 강하고, CRC·ACK·Error Frame으로 오류를 스스로 감지해 재전송하며, 고장 난 노드는 스스로 빠진다(Bus Off).
