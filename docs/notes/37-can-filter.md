## 1. 필터는 어디서 거르나

```
          커널 (SocketCAN)                       우리 프로그램
vcan0 ──→ [CAN_RAW_FILTER: 0x100,0x200,0x300] ──read()──→ socket_source → 디스패처
              ↑ 여기서 버림                                 ↑ M5-6까지는 여기서 버림 (IGNORED)
```

- 디스패처가 어차피 모르는 ID를 `IGNORED`로 버리는데, 왜 커널에서 또 거르나 → **버리는 데도 비용이 든다.** 필요 없는 프레임은 일찍 버릴수록 싸다
  - 커널에서 안 거르면 프레임마다: 커널 → 우리 프로그램으로 **복사**(`read()` 시스템 호출 1번) → 깨어남 → 변환 → 디스패처 → BCM 판단 → (DEBUG 로그). 전부 하고 나서 "관심 없음"
  - 실제 차의 CAN 버스에는 수십 개 ECU가 보내는 수백 개 ID가 흐른다. BCM이 쓰는 건 그중 몇 개뿐 → 대부분이 쓸데없는 일
  - 커널에서 거르면 그 프레임은 우리 프로그램을 **깨우지도 않는다.** CPU 사용이 줄고, 진짜 필요한 프레임 처리가 늦어지지 않는다
  - 안전 장치도 된다: 수신 큐가 쓸데없는 프레임으로 꽉 차서 중요한 프레임이 **밀려 버려지는**(overflow) 일을 막는다
  - 디스패처의 `IGNORED`는 그대로 둔다 (두 겹 방어). 파일 모드나 `--no-filter`에는 커널 필터가 없고, 필터를 잘못 걸어도 디스패처가 마지막으로 거른다
  - 웹으로: 애플리케이션 코드에서 `if (!allowed) return;` 하는 것보다 앞단(방화벽, nginx, API Gateway)에서 막는 게 서버 부담이 적은 것과 같다
- 실제 ECU의 CAN 컨트롤러에도 같은 기능이 있다. 무엇이고 왜 하드웨어에 있나 → **하드웨어 수신 필터 (acceptance filter, 또는 mask/filter 레지스터)**
  - CAN 컨트롤러 칩 안에 "이 ID:마스크만 받아라"를 적는 레지스터가 있다. 우리 `can_filter`(ID + 마스크)와 같은 모양
  - 맞지 않는 프레임은 **CPU에 알리지도 않는다** (인터럽트 없음). 칩이 알아서 버린다
  - 하드웨어에 있는 이유: ECU의 CPU는 작고 느리다(수십~수백 MHz, 메모리 수십 KB). 버스의 모든 프레임마다 인터럽트가 걸리면 CPU가 그것만 처리하다 본업(판단, 제어)을 못 한다 → **CPU 부담을 0으로**
  - 단계별로 보면: 하드웨어 필터(칩) → 커널 필터(우리 `CAN_RAW_FILTER`, OS가 있는 경우) → 앱의 디스패처. **앞에서 걸러질수록 싸다**
  - 실제 개발에서는 DBC(신호 정의서)에서 "이 ECU가 받는 메시지" 목록을 뽑아 필터 설정을 자동으로 만든다. 우리의 `DISPATCH_RX_IDS`가 그 목록 역할 (3번)

## 2. 필터 있음 / 없음 비교 (VM, 터미널 2개)

터미널 A: `./build-linux/bcm_sim -i vcan0 -l debug` (필터 있음) → 끝나면 Ctrl+C하고 `--no-filter`를 붙여서 한 번 더
터미널 B (매번 같은 6개):
```
cansend vcan0 300#0203
cansend vcan0 7FF#00
cansend vcan0 12345678#00
cansend vcan0 100#R
cansend vcan0 500#00
cansend vcan0 100#D007
```

| 터미널 A에 찍힌 것 | 필터 있음 (기본) | `--no-filter` |
| --- | --- | --- |
| `RX ... → OK` | ✅ 2줄: `RX 0x300 [2] 02 03`, `RX 0x100 [2] D0 07` | ✅ 2줄: 같은 둘 |
| `RX ... → IGNORED` | ✅ **없음** | ✅ 2줄: `RX 0x7FF [1] 00`, `RX 0x500 [1] 00` |
| `무시: Extended / Remote / 에러 프레임` | ✅ **없음** | ✅ 2줄 (`12345678#00`, `100#R`) |
| 시작할 때 `수신 필터: ...` 줄 | ✅ `수신 필터: 3개 ID만 받음` | ✅ 없음 |

- 결과의 차이를 한 줄로 → BCM이 하는 일(OK 2개)은 **똑같고**, 필터가 있으면 쓸데없는 4개가 **우리 프로그램까지 오지도 않는다.** 필터가 없으면 4개를 받아 놓고 우리 코드가 직접 버린다 (`IGNORED` 2: 모르는 ID, `무시` 2: 29비트/Remote)
  - 보낸 6개 중 우리가 받은 것: 필터 있음 **2개** / 없음 **6개**
  - 판단 결과(시동 ON, 차속 20 km/h, 상태 전이)는 같다 → 필터는 **동작을 바꾸지 않고 일만 줄인다.** 바뀌면 필터가 잘못된 것 (그래서 3번의 테스트가 필요)
  - 29비트 ID `12345678`과 Remote `100#R`은 0번에서 마스크에 EFF/RTR을 넣은 덕분에 막혔다. 특히 `100#R`은 ID가 0x100인데도 막혔다

## 3. 필터 목록은 어디서 오나 (`DISPATCH_RX_IDS`)

- 필터 목록을 `main.c`에 `{0x100, 0x200, 0x300}`으로 직접 안 쓰고 디스패처 옆에 둔 이유 → "BCM이 **어떤 ID를 처리하는가**"를 아는 곳이 디스패처(`can_dispatch`의 `switch`)이기 때문. 같은 사실을 두 군데에 따로 적으면 언젠가 **어긋난다**
  - 예: 나중에 0x150(브레이크)을 디스패처에 추가하고 `main.c`의 목록은 깜빡 → 커널이 0x150을 막아서 **디스패처까지 안 온다.** 코드는 맞는데 동작을 안 하고, 파일 모드(필터 없음)에서는 잘 돼서 원인 찾기도 어렵다
  - 디스패처 옆(`dispatcher.c`)에 두면 고칠 때 **바로 눈에 보이는 곳**에 있다. `main.c`는 그 목록을 가져다 쓰기만 한다
  - 원칙: 한 가지 사실은 한 곳에만 (DRY, Single Source of Truth). Java로: 상수를 여기저기 쓰지 않고 한 `enum`/설정 클래스에 두는 것
- `test_rx_ids_match_dispatch`는 무엇을 확인하나. 이 테스트가 없을 때 생길 수 있는 버그 → **"필터 목록 = 디스패처가 실제로 처리하는 ID"**를 확인한다
  - 방법: 0x000 ~ 0x7FF(2048개 전부)를 디스패처에 넣어서, `IGNORED`가 **아닌** ID를 센다 → 정확히 3개이고, 3개 모두 `DISPATCH_RX_IDS`에 있어야 통과
  - 그래도 목록과 `switch`는 아직 **두 군데**다(C에서 `switch`의 `case`를 배열에서 자동으로 만들 수는 없다). 이 테스트가 둘을 **묶어 주는** 역할
  - 없을 때 버그 ①: 디스패처에 ID 추가, 목록에는 안 추가 → 실시간 모드에서만 그 메시지가 **안 들어옴** (위의 0x150 예)
  - 없을 때 버그 ②: 목록에 오타(`0x30` 같은) → 0x300이 막혀서 시동 신호가 안 옴 → BCM이 영원히 IDLE. 파일 모드 테스트는 전부 통과하니 못 잡는다
  - 이 테스트가 있으면 둘 다 `make test`에서 맥에서도 바로 실패한다 (소켓 없이 확인 가능)

## 4. 덤프 모드는 왜 필터를 안 거나

- `--dump`에는 필터가 없다(`socket_source_open(..., NULL, 0)`). 이유 → 덤프는 "**버스에 무엇이 오는지 보는**" 도구라서 (candump처럼). 우리가 모르는 ID(`→ -`)도 보여 줘야 의미가 있다
  - 필터를 걸면 0x100, 0x200, 0x300만 보인다 → "다른 ECU가 뭘 보내나", "내 0x400이 나가나"를 확인할 수 없다
  - BCM 모드는 **판단**이 목적이라 필요한 것만 받고, 덤프 모드는 **관찰**이 목적이라 전부 받는다. 목적에 따라 필터를 다르게
- 필터 개수가 0개(`can_socket_set_filter(fd, NULL, 0)`)인 것과 필터를 안 건 것(`NULL`을 넘겨 아예 안 부름)의 차이 → 정반대다
  - 필터를 **안 건 것**: 소켓을 열면 기본 필터가 "전부 통과"(ID 0, 마스크 0 → 어떤 ID든 `& 0` = 0이라 다 같음) → **전부 받는다** (덤프, `--no-filter`)
  - 필터 **0개**를 건 것: "통과시킬 목록이 비었다" → **아무것도 안 받는다** (`test_filter_on_vcan0` 마지막에서 확인: 0x100을 보내도 안 옴)
  - 받기는 안 하고 **보내기만** 하는 프로그램(cansend 같은)에서 쓴다. 쓸데없이 받는 큐가 차지 않게
  - 그래서 `socket_source_open`에서는 `rx_ids == NULL`이면 `can_socket_set_filter`를 **아예 안 부른다** (0개로 부르면 전부 막혀 버림)

## 5. 정리

- 이번 이슈를 한 줄로 → 커널에 `CAN_RAW_FILTER`(ID + 마스크 목록)를 걸어서, BCM이 처리하는 0x100, 0x200, 0x300의 **일반 데이터 프레임만** 받게 했다. 나머지는 우리 프로그램까지 오지 않는다 (판단 결과는 그대로, 일만 줄어듦)
- 32번 노트 4번의 `candump vcan0,100:7FF`와 이번 필터의 관계 → **같은 것이다.** `candump`의 `,ID:마스크`가 내부적으로 바로 이 `CAN_RAW_FILTER`를 건다
  - `candump vcan0,100:7FF,200:7FF,300:7FF` ≈ 우리 필터 (우리는 마스크에 EFF/RTR 비트까지 넣어서 조금 더 엄격하다)
  - 32번에서 배운 규칙 "`(받은 ID & 마스크) == (ID & 마스크)`면 받음, 범위가 아님"이 커널의 실제 규칙이었다. 그때는 도구로 써 봤고, 이번엔 그 도구가 하는 일을 직접 코드로 했다
