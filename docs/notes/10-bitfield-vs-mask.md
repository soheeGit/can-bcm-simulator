# 10. 비트필드 vs 마스크/시프트 (M1-4)

> 실험 코드: `playground/can/02_bitfield_basics.c`, `playground/can/03_bitfield_vs_mask.c`
> 실행: `make -C playground/can && ./playground/can/build/02_bitfield_basics`
>
> 목표(DoD): 실험 결과와 **설계 결정(ADR)**을 기록한다

## 1. 비트필드란?

```c
typedef struct {
    uint8_t fl    : 1;   /* fl은 1비트만 쓴다 */
    uint8_t fr    : 1;
    ...
} DoorBits;
```

- `: 1`의 뜻 → 1비트만 사용한다. ✅ (`: 3`이면 3비트, 0~7)
- 장점 (마스크/시프트와 비교해서 코드가 어떻게 생겼나) → 간결하다. ✅ 마스크를 외울 필요 없이 **보통 변수처럼** 읽고 쓴다

```c
/* 마스크/시프트 (M0-5) */          /* 비트필드 */
doors |= (1u << DOOR_TRUNK);        d.trunk = 1;
if ((doors >> DOOR_FL) & 1u) ...    if (d.fl) ...
```

## 2. 실험 1: 비트필드 기초 (`02_bitfield_basics.c`)

| 번호 | 예상 | 실제 |
| --- | --- | --- |
| [1] `sizeof(DoorBytes)` (uint8_t 5개) | 5 | 5 |
| [1] `sizeof(DoorBitsUint)` (unsigned int 비트필드) | | 4 |
| [1] `sizeof(DoorBitsU8)` (uint8_t 비트필드) | | 1 |
| [3] 1비트 `fr`에 2를 넣으면 | 0 | **0** |
| [3] 1비트 `rl`에 3을 넣으면 | 1 | 1 |
| [4] signed 1비트에 1을 넣으면 | 1 | **-1** |

- 바탕 타입(`unsigned int` vs `uint8_t`)에 따라 크기가 다른 이유 → 비트필드는 **바탕 타입 크기의 "상자"** 안에 비트를 채운다. `unsigned int`(4바이트) 상자 하나에 5비트를 넣어도 상자는 4바이트, `uint8_t`(1바이트) 상자면 1바이트. 비트필드 없이 `uint8_t` 5개면 5바이트
  - 5비트만 쓰는데 4바이트 → **바탕 타입을 뭘로 하느냐에 따라 크기가 달라진다** → 통신 데이터 크기와 맞추려면 신경 써야 한다
- [3]에서 값이 이렇게 된 이유 (M0-4 오버플로우와 연결) → 1비트 칸에는 0 또는 1만 들어간다. 넣은 값의 **맨 아래 1비트만 남고** 나머지는 잘린다 (uint8_t에 300을 넣으면 44가 됐던 것과 같다)

```
2 = 1 0  → 맨 아래 비트 0 → 0
3 = 1 1  → 맨 아래 비트 1 → 1
```

  - 컴파일러가 경고 없이 잘라버리면 "문을 열었는데(2) 닫힘(0)으로 저장"되는 버그가 조용히 생긴다
- [4]가 -1인 이유 (M0-6에서 본 부호 비트와 연결) → signed 비트필드는 **맨 위 비트가 부호 비트**다. 1비트짜리면 그 하나뿐인 비트가 곧 부호 비트라서, 자릿값이 -1이다. 그래서 담을 수 있는 값은 **0과 -1** 두 개뿐이다 (int8_t `1000 0000` = -128인 것과 같은 원리). `if (s.flag == 1)`은 영원히 거짓 → 비트필드는 반드시 **unsigned**로
- 주석 실험 (5) `&d.fl` 결과:

```
error: address of bit-field requested
```

- 비트필드의 주소를 구할 수 없는 이유 → 메모리 주소는 **바이트 단위**로만 매겨진다 (M1-3 아파트 비유: 층 번호는 있지만 방 하나하나에는 주소가 없음). 비트필드는 바이트 안의 몇 비트라서 가리킬 주소가 없다 → 포인터로 넘기거나 `memcpy`, `scanf` 같은 함수에 바로 쓸 수 없다

## 3. 실험 2: CAN 데이터에 memcpy로 덮어쓰기 (`03_bitfield_vs_mask.c`)

| 경우 | 비트필드 결과 | 마스크 결과 | 같은가? |
| --- | --- | --- | --- |
| [1] DOOR `0x11` | FL=1 FR=0 RL=0 RR=0 TRUNK=1 | FL=1 FR=0 RL=0 RR=0 TRUNK=1 | ✅ 같음 |
| [2] IGN `02 03` | ign=2 gear=3 | ign=2 gear=3 | ✅ 같음 |
| [3] 바이트 경계를 넘는 신호 (start 4, 길이 8) | sig=**0x0B** | sig=**0xBA** | ❌ **다름** |

- 실험의 목적 → 받은 바이트를 비트필드 구조체에 `memcpy`로 **그대로 덮어쓰면** 마스크 없이 신호를 꺼낼 수 있을까? 마스크 결과(정답)와 비교
- [1], [2]가 같게 나온 이유 (이 컴퓨터에서는) → 이 컴파일러(clang/gcc, Little-endian)는 비트필드를 **바이트의 오른쪽(0번 비트)부터 선언 순서대로** 채운다. 마침 정의서(FL = bit 0 ... TRUNK = bit 4)와 **우연히 같은 순서**라서 맞았다

```
DoorBits 배치:  [ 예약  ][TR][RR][RL][FR][FL]
비트 번호:        7 6 5   4   3   2   1   0
```

- [3]이 다르게 나온 이유 (힌트: `sizeof(CrossBits)`와 `uint8_t` 칸) → `uint8_t` 비트필드는 **1바이트 상자를 넘어갈 수 없다.** `low:4`를 넣고 상자에 4칸이 남았는데 `sig:8`은 8칸이 필요하다 → 컴파일러가 `sig`를 **다음 상자(data[1])로 통째로 옮긴다.** data[0]의 위 4비트는 비어 버린다 → `sizeof`가 2, `sig`는 data[1] = 0x0B만 읽음

```
정의서(마스크):  bit 4~11 = data[1]의 아래 4비트 + data[0]의 위 4비트
                 0000 1011 1010 0000 >> 4 & 0xFF = 1011 1010 = 0xBA ✅

비트필드:        상자1 data[0] = [ 빈칸 4 | low 4 ]
                 상자2 data[1] = [ sig 8         ]  → 0x0B ❌
```

  - 정의서는 "8바이트를 **이어 붙인** 비트 번호"로 신호 위치를 정하는데, 비트필드는 "**바이트 상자 단위**"로 끊어서 배치한다 → 생각하는 방식이 달라서 어긋난다
- 이 결과가 "모든 컴퓨터에서" 같다고 믿을 수 있나? → **아니다.** C 표준은 비트필드를 어떤 순서로 채울지 정하지 않았다 (**implementation-defined**, 컴파일러 마음대로). Big-endian CPU용이나 일부 차량 MCU용 컴파일러는 **왼쪽(7번 비트)부터** 채우기도 한다 → 같은 코드가 차에서는 FL과 TRUNK 위치를 다르게 읽는다. [1], [2]도 "이 컴퓨터라서" 맞은 것뿐이다
  - 마스크 방식은 "bit 4부터 8비트"를 **코드에 직접 적어서** 어떤 컴퓨터에서든 결과가 같다

## 4. 비트필드의 문제점 정리

| 문제 | 설명 |
| --- | --- |
| 비트 배치 순서 | 비트필드를 바이트의 **오른쪽(0번)부터 채울지, 왼쪽(7번)부터 채울지** C 표준이 정하지 않았다 (implementation-defined). 이 컴퓨터에서는 오른쪽부터라 정의서와 우연히 맞았지만(실험 2 [1], [2]), 다른 컴파일러/MCU에서는 FL과 TRUNK 위치가 뒤바뀔 수 있다 |
| 바이트 경계 | 바탕 타입 상자를 넘어가는 필드는 **다음 상자로 통째로 밀린다** (실험 2 [3]: `sig`가 data[1]로 밀려 0x0B). 정의서의 "8바이트를 이어 붙인 비트 번호"와 맞지 않는다. 밀릴지 말지도 컴파일러마다 다르다 |
| 엔디안 | 여러 바이트에 걸친 필드(예: 16비트 차속)를 어떤 바이트 순서로 놓을지가 **CPU 엔디안을 따른다.** Little-endian 컴퓨터에서 맞게 짠 코드가 Big-endian MCU에서는 바이트가 뒤집혀 읽힌다. 게다가 Motorola(Big-endian) 신호는 비트필드로 표현할 방법 자체가 없다 |
| 바탕 타입 | 바탕 타입이 **상자 크기**를 정해서 같은 5비트도 `unsigned int`면 4바이트, `uint8_t`면 1바이트 (실험 1 [1]). C 표준이 보장하는 바탕 타입은 `unsigned int`, `signed int`, `_Bool`뿐이고 `uint8_t` 비트필드는 컴파일러 확장이다 |
| 값 넘침 / 부호 | 칸보다 큰 값을 넣으면 **경고 없이 잘린다** (1비트에 2 → 0). signed 1비트는 0과 -1밖에 못 담는다 (실험 1 [3], [4]) |
| 주소 / 포인터 | 비트필드는 **주소를 구할 수 없다** (`&d.fl` 에러, 실험 1 [5]). 포인터로 넘기거나 `memcpy`/`scanf`에 직접 쓸 수 없다 |
| 코딩 규칙 (MISRA-C) | 자동차 코딩 규칙 MISRA-C:2012는 비트필드에 **unsigned/signed int 같은 정해진 타입만** 쓰라고 하고(Rule 6.1), **1비트짜리 signed 비트필드를 금지**한다(Rule 6.2). 그리고 implementation-defined 동작에 기대는 코드는 문서화와 검증을 요구한다 → 통신 데이터 해석에 비트필드를 쓰면 근거를 남기기 어렵다 |

> 정리: 비트필드는 **코드는 깔끔하지만, 메모리에 실제로 어떻게 놓이는지를 컴파일러가 정한다.** 그래서 "정확한 비트 위치가 약속된 외부 데이터(CAN)"를 해석하는 데는 믿을 수 없다. 반대로 **내 프로그램 안에서만 쓰는 값**이라면 배치가 어떻든 상관없어서 쓸 수 있다

## 5. 설계 결정 (ADR: Architecture Decision Record)

> ADR = "왜 이렇게 설계했는지"를 남기는 짧은 기록. 나중에 "왜 비트필드 안 썼어요?"라는 질문에 이 문서로 답한다.

### 제목

- **ADR-001: CAN 신호 해석은 마스크/시프트로, 내부 상태는 일반 구조체(bool)로 표현한다**
- 상태: ✅ 채택 (M1-4)

### 상황 (Context)

- CAN 메시지 8바이트 안에는 신호가 **비트 단위**로 들어 있고, 위치는 신호 정의서(`docs/signal-spec.md`)가 "start bit + 길이 + Little-endian"으로 정한다
- C에는 이런 비트 묶음을 표현하는 방법이 두 가지 있다: **① 비트필드 구조체** (`uint8_t fl : 1;`) **② 마스크/시프트** (`(data >> n) & mask`)
- 비트필드는 코드가 깔끔하지만, 실험 결과:
  - 비트 배치 순서가 **컴파일러마다 다를 수 있다** (C 표준이 정하지 않음)
  - 바이트 경계를 넘는 신호에서 **값이 틀렸다** (기대 0xBA → 실제 0x0B)
  - 엔디안이 바뀌면 여러 바이트 신호가 뒤집힌다
- 이 코드는 맥(개발), 리눅스(테스트), 나중에는 다른 MCU에서도 **같은 결과**를 내야 한다

### 결정 (Decision)

1. **외부 데이터(CAN 프레임) → 마스크/시프트로 해석**
   - M2-1 `can_get_bits(data, start_bit, length)` / M2-2 `can_set_bits(...)` 범용 함수 두 개로 모든 신호를 꺼내고 넣는다
   - 받은 바이트를 구조체에 `memcpy`로 덮어쓰는 방식은 **쓰지 않는다**
2. **내부 상태 → 비트필드가 아니라 일반 구조체(`bool` 필드)로 표현**
   - 예: M2-4 `DoorStatus`

```c
typedef struct {
    bool fl;
    bool fr;
    bool rl;
    bool rr;
    bool trunk;
} DoorStatus;          /* 디코더가 can_get_bits()로 꺼낸 값을 여기에 담는다 */
```

```
CAN 프레임 (외부, 비트 위치가 약속됨)        내부 상태 (우리 프로그램 안에서만)
200#1100000000000000  ── can_get_bits() ──→  DoorStatus { fl=true, trunk=true, ... }
                         (마스크/시프트)        (bool, 배치는 상관없음)
```

### 이유 (Consequences)

- 👍 **어디서 돌려도 결과가 같다.** 비트 위치를 코드(`start_bit`, `length`)에 직접 적으므로 컴파일러, CPU 엔디안에 영향을 받지 않는다
- 👍 **정의서와 코드가 1:1로 맞는다.** 정의서의 "start bit 8, 길이 3"을 그대로 `can_get_bits(data, 8, 3)`으로 쓴다 → 리뷰하기 쉽다
- 👍 바이트 경계를 넘는 신호, 16비트 신호도 같은 함수 하나로 처리한다
- 👍 내부 상태를 `bool`로 두면 읽기 쉽고, 디버거로 보기 쉽고, 주소도 구할 수 있다(포인터로 넘기기 가능). 차량 BCM이 다루는 상태는 몇 바이트뿐이라 1비트로 아낄 필요가 없다
- 👎 마스크/시프트 코드가 비트필드보다 길다 → 범용 함수 `can_get_bits()`로 감싸고, 신호마다 테스트를 만들어 실수를 막는다
- 👎 해석 단계(바이트 → bool)가 한 번 더 들어간다 → 대신 "외부 형식"과 "내부 표현"이 분리되어, 정의서가 바뀌어도 디코더만 고치면 된다 (웹의 DTO ↔ Entity 분리와 같은 생각)

### 대안 (검토했지만 안 쓴 것)

| 대안 | 안 쓴 이유 |
| --- | --- |
| 비트필드 구조체에 `memcpy`로 덮어쓰기 | 실험 2에서 바이트 경계 신호가 틀렸고, 비트 배치가 컴파일러마다 다르다 |
| `__attribute__((packed))` 구조체에 덮어쓰기 | 패딩은 없앨 수 있지만 **컴파일러 확장**(표준 아님)이고, 엔디안 문제는 그대로다 |
| DBC 파일에서 디코더 코드 자동 생성 | 실무에서 많이 쓰는 좋은 방법이지만, 이 프로젝트는 비트 연산을 **직접 이해하는 게 목적**이라 손으로 짠다. 회고(M6-4)의 "다음에 해볼 것"으로 남긴다 |
| 내부 상태도 비트필드로 (메모리 절약) | 내부용이라 배치 문제는 없지만, 아낄 메모리가 몇 바이트뿐이라 이득이 작다. 읽기 쉬운 `bool`을 택한다 |

> 면접용 한 문장: "비트필드는 비트 배치가 컴파일러에 따라 달라서(implementation-defined), 정확한 비트 위치가 약속된 CAN 데이터 해석에는 마스크/시프트를 쓰고, 내부 상태는 읽기 쉬운 bool 구조체로 분리했습니다. 실제로 바이트 경계를 넘는 신호에서 비트필드가 다른 값을 내는 걸 실험으로 확인했습니다."
