# 12. 범용 비트 삽입 함수 `can_set_bits()` (M2-2)

> 코드: `include/can_signal.h`, `src/can_signal.c`, `tests/test_can_signal.c`
> 실행: `make test`

## 1. 이 함수가 하는 일

```c
void can_set_bits(uint8_t data[8], uint8_t start_bit, uint8_t length, uint32_t value);
```

- 한 줄 설명 → CAN 데이터 8바이트의 start_bit부터 length비트 자리에 value를 넣는다 (다른 비트는 그대로)
- `can_get_bits()`와의 관계 → 정반대 방향. get은 바이트에서 값을 **꺼내고**(조회), set은 값을 바이트에 **넣는다**(세팅). set으로 넣은 값을 get으로 꺼내면 같은 값이 나와야 한다(왕복)
- 어디에 쓰나? (BCM이 보내는 메시지) → BCM이 보내는 **0x400 BCM_STATUS** 프레임을 만들 때 (BcmState, DoorLockCmd, WarningBuzzer, AliveCounter → M4-8). 테스트용 프레임이나 시나리오 로그(M3-4)를 만들 때도 쓴다
- `can_get_bits()`의 `data`는 `const`인데 이 함수는 `const`가 없는 이유 → get은 data를 **읽기만** 하지만, set은 data를 **직접 바꿔야** 하기 때문 (M0-3 실험 6: `const`면 값 변경이 컴파일 에러)

## 2. 동작 원리 (3단계)

```c
uint64_t field = (uint64_t)low_mask(length) << start_bit;   /* 신호 자리만 1 */

uint64_t word = load_le64(data);
word &= ~field;                                  /* 1) 그 자리를 0으로 지우고 */
word |= ((uint64_t)value << start_bit) & field;  /* 2) 새 값을 그 자리에만 넣고 */
store_le64(data, word);                          /* 3) 다시 8바이트로 풀어 놓는다 */
```

- `field`는 무엇인가? → **바꿀 자리만 1**인 마스크. `low_mask(length)`를 `start_bit`만큼 올린 것 (start 2, 길이 3 → `0001 1100`)
- 1단계 `&= ~field`는 M0-5의 무엇? → **clear** (`& ~`). 그 자리만 0으로 지우고 나머지는 그대로
- 2단계 `|= ...`는 M0-5의 무엇? → **set** (`|`). 새 값을 그 자리에 켠다
- 2단계에서 `& field`를 한 번 더 하는 이유 → value가 자리보다 크면 넘친 비트가 **옆 자리를 켜버린다.** field로 한 번 더 잘라서 그 자리 밖으로 못 나가게 막는다
- 바로 `|=`만 하지 않고 1단계(지우기)부터 하는 이유 (기존 값이 `11`인 자리에 `01`을 넣는다면?) → OR는 1을 켤 수만 있고 끌 수 없다. `11 | 01 = 11`(❌)이 되므로 먼저 `00`으로 지우고 넣어야 `01`(✅)이 된다

### 손으로 따라가기: 전부 `0xFF`인 데이터에 start 2, 길이 3, 값 0

```
data[0]            = 1111 1111   (처음: 전부 1)
field              = 0001 1100   (비트 2~4만 1)
~field             = 1110 0011   (비트 2~4만 0)
data[0] & ~field   = 1110 0011   (1단계: 비트 2~4만 지워지고 나머지 1은 그대로)
| (0 << 2) & field = 0000 0000   (2단계: 넣을 값이 0)
결과 data[0]        = 1110 0011 = 0xE3   (test_set_keeps_neighbor_bits의 기대값)
```

> 처음에 `data[0] & ~field`를 `0000 0000`으로 계산했다 → data[0]을 0으로 착각. 이 실험은 **전부 1인 데이터**에서 시작해야 "옆 비트가 안 망가지는지"가 보인다

## 3. 값이 자리보다 클 때 — 설계 결정

- `can_set_bits(data, 0, 4, 0x1F)` → 결과 → data[0] = **0x0F** (`0001 1111` 중 아래 4비트 `1111`만 들어가고, 넘친 비트 4는 버려짐 → 옆 비트 4는 0 그대로)

```
value          = 0001 1111   (5비트짜리 값)
& field(0x0F)  = 0000 1111   (자리는 4칸)
결과 data[0]    = 0000 1111   ← 비트 4를 건드리지 않음
```

- 아래 4비트만 넣기로 한 이유 → **옆 신호를 절대 망가뜨리지 않기 위해서.** 자르지 않으면 넘친 비트 4가 옆 신호(예: 도어 메시지라면 Trunk)를 켜버린다. 한 신호의 실수가 **다른 신호까지 번지는 것**을 막는다
- 그런데 M1-4에서는 "비트필드가 조용히 자르는 게 문제"라고 했다. 이건 괜찮은가? → 솔직히 **자르는 것 자체의 위험은 같다** (넣으려던 값과 다른 값이 들어감). 차이점과 보완책:
  - M1-4에서 비트필드를 안 쓴 **핵심 이유는 자르기가 아니라 "비트 배치를 컴파일러가 정한다"**는 것이었다. `can_set_bits()`는 위치를 코드에 직접 적으니 그 문제가 없다
  - 자르는 동작을 **헤더 주석에 명시**했고(문서화), `test_set_value_too_big_is_truncated`로 **테스트**한다 → "조용히"가 아니라 "약속된 동작"
  - 넣는 값은 CAN에서 들어온 값이 아니라 **우리 코드가 만든 값**(BcmState 0~2, AliveCounter 0~15 등)이다. 범위는 넣는 쪽에서 지킨다 → 예: AliveCounter는 `counter = (counter + 1) & 0x0Fu;`로 늘 0~15 유지 (M4-8)
  - 더 엄격하게 하려면 범위를 넘으면 `false`를 반환하는 방법도 있다 (M2-1 4번의 ② 방식). 지금은 값이 전부 우리 코드에서 나오므로 단순한 쪽을 택했다

## 4. 테스트

| 테스트 | 확인하는 것 |

| `test_set_32bit_full` | 길이 32 → `{0x78, 0x56, 0x34, 0x12}` (마스크 UB 없이 동작하는지) |
| `test_set_invalid_args_change_nothing` | 길이 0 / 33 / 프레임 밖 / NULL → 데이터가 **하나도 안 바뀌고** 죽지 않는지 |
| `test_round_trip` | set으로 넣은 값을 get으로 꺼내면 같은지 (여러 조합을 반복문으로) |

- 결과 → `[test_can_signal]` **225 passed**, 0 failed (맥, 컨테이너, Sanitizer 빌드 모두 통과)
- 왕복(round-trip) 테스트란? → **넣고(set) → 꺼내서(get) → 원래 값과 같은지** 확인하는 테스트. get과 set이 서로 정확히 반대로 동작하는지를 한 번에 검증한다. Java에서 객체를 JSON으로 직렬화했다가 다시 역직렬화하면 원래 객체가 나오는지 확인하는 테스트와 같다
- 배경을 `0x00`과 `0xFF` 두 가지로 하는 이유 →
  - `0x00` 배경: 값의 **1을 제대로 켜는지** 확인
  - `0xFF` 배경: 값의 **0을 제대로 끄는지**(1단계 지우기가 되는지) 확인. 배경이 0이면 "지우기를 빼먹은 버그"가 숨어서 안 보인다
- 테스트 수가 225개로 늘어난 이유 → 왕복 테스트가 **시작 비트 12가지 × 길이 9가지 × 배경 2가지** 조합을 반복문으로 돌기 때문 (프레임 밖 조합은 건너뛰고 약 196개 검사). 손으로 쓰면 수백 줄인 테스트를 반복문 몇 줄로 만들었다

## 5. 리팩터링: `can_get_bits()`도 바뀌었다

- 공통 함수로 빼낸 것 3개 (`static`) → get과 set이 **똑같이 하던 일**을 하나로 모았다

| 함수 | 하는 일 | 전에는 |
| --- | --- | --- |
| `args_valid()` | 인자 검사 (NULL, 길이 0/33, 프레임 밖) | `can_get_bits()` 안에 `if` 3개로 직접 |
| `load_le64()` | 8바이트 → 64비트 숫자로 합치기 | `can_get_bits()` 안에 반복문으로 직접 |
| `store_le64()` | 64비트 숫자 → 8바이트로 풀기 (load의 반대) | 없음 (set에서 새로 필요) |

  - `static`을 붙여서 **이 파일 안에서만** 쓴다 (M0-7: Java의 `private`). 헤더에도 안 나온다 → 밖에서는 `can_get_bits()`, `can_set_bits()`만 보인다
  - 같은 검사·조립 코드를 두 군데 쓰면, 하나만 고치고 하나를 깜빡하는 버그가 생긴다 → 한 곳에 두면 **고칠 곳도 한 곳** (DRY: Don't Repeat Yourself)
- 이렇게 바꿔도 안전하다는 걸 어떻게 알 수 있나? → **M2-1에서 만든 `can_get_bits()` 테스트 20개가 그대로 통과**했다. 겉으로 보이는 동작(입력 → 출력)은 그대로이고 안쪽 구조만 바꾸는 게 리팩터링인데, 그걸 테스트가 증명해 준다. 테스트가 없었다면 "바꿨는데 뭔가 망가졌나?"를 확인할 방법이 없다 → 리팩터링 전에 테스트부터 있어야 하는 이유
