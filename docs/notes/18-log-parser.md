# 18. 로그 한 줄 파서 (M3-2)

> 코드: `include/log_parser.h`, `src/log_parser.c`, `tests/test_log_parser.c`
> 실행: `make test`

## 1. 이 함수가 하는 일

```c
ParseResult parse_candump_line(const char *line, CanFrame *out, uint64_t *ts_us);
```

```
"(0.100000) vcan0 100#1027000000000000"  ──→  CanFrame { 0x100, 8, {10 27 ...} } + 100000us
```

- 한 줄 설명 → candump 형식의 **글자 한 줄**을 읽어서, 형식이 맞으면 `CanFrame`과 타임스탬프(마이크로초)로 바꾸고, 틀리면 **어디가 틀렸는지**(`ParseResult`)를 알려준다
- 웹으로 치면? → **요청 바디 파싱 (역직렬화).** `objectMapper.readValue(jsonString, CanFrameDto.class)`처럼 문자열을 객체로 바꾸는 단계. 형식이 깨지면 Jackson이 `JsonParseException`을 던지듯, 이 파서는 `PARSE_ERR_xxx`를 돌려준다. 값이 범위 안인지는 그다음 단계(`can_frame_is_valid()` = `@Valid`)가 본다

## 2. C 문자열 기초

- C 문자열은 무엇인가? (`'\0'`) → **`char` 배열 + 맨 뒤의 `'\0'`(값 0인 글자)**. C에는 문자열 타입이 따로 없고, 글자를 차례로 놓고 끝에 `'\0'`을 붙여서 "여기서 끝"이라고 표시한다

```
"100#10"  →  [ '1' ][ '0' ][ '0' ][ '#' ][ '1' ][ '0' ][ '\0' ]
               [0]    [1]    [2]    [3]    [4]    [5]    [6]   ← 6글자인데 7칸
```

- `const char *line`에서 `*p`, `p++`는 무엇을 하나? →
  - `line`(= `p`의 시작값)은 문자열 **첫 글자의 주소**를 가리킨다
  - `*p` → 지금 가리키는 **글자 하나를 읽는다** (M0-3 역참조). 처음엔 `'('`
  - `p++` → **다음 글자로 한 칸 옮긴다** (M0-3 포인터 산술: `char`는 1바이트라 주소 +1)
  - 그래서 `while (*p != '\0') { ...; p++; }`는 "끝(`'\0'`)이 나올 때까지 한 글자씩 읽기"가 된다
  - `const`라서 글자를 **읽기만** 하고 바꿀 수 없다 (M0-3 실험 6)

```
p → '('  →  p++  →  '0'  →  p++  →  '.'  → ... → '\0' (끝)
```

- Java `String`과 다른 점 →

| | Java `String` | C 문자열 |
| --- | --- | --- |
| 정체 | 객체 | `char` 배열 + `'\0'` |
| 길이 | `s.length()`가 저장돼 있음 | 저장 안 됨 → `'\0'`이 나올 때까지 **세야** 함 (`strlen`) |
| 끝 표시 | 없음 (길이로 앎) | `'\0'` |
| 범위 밖 접근 | `StringIndexOutOfBoundsException` | 에러 없이 **옆 메모리를 읽음** (M0-6 실험 2) |
| 크기 | 알아서 늘어남 | 배열 크기 고정 → 넘치면 버퍼 오버플로우 (그래서 `snprintf`) |
| 비교 | `a.equals(b)` | `strcmp(a, b) == 0` (`==`는 주소 비교) |

  - 그래서 C 파서는 **`'\0'`을 만나면 반드시 멈춰야** 한다. 이걸 빼먹으면 문자열 끝을 지나 남의 메모리를 계속 읽는다 → 퍼징(30만 줄)으로 이런 실수가 없는지 확인했다

## 3. 동작 순서 (포인터로 한 글자씩 걷기)

```
"(0.100000) vcan0 100#1027000000000000"
 ↑
 p  → 1) 타임스탬프 → 2) 공백 + 인터페이스 → 3) 공백 + ID# → 4) 데이터 → 5) 줄 끝
```

| 단계 | 함수 | 실패하면 |
| --- | --- | --- |
| 0 | `is_skip_line()` (빈 줄 / `#` 주석인가) | — (해당하면 `PARSE_SKIP`) |
| 1 | `parse_timestamp()` | `PARSE_ERR_TIMESTAMP` |
| 2 | `*p != ' '` 검사 + `parse_interface()` | `PARSE_ERR_INTERFACE` |
| 3 | `*p != ' '` 검사 + `parse_id()` | `PARSE_ERR_INTERFACE` (공백 없음) / `PARSE_ERR_ID` / `PARSE_ERR_UNSUPPORTED` (8자리 Extended) |
| 4 | `parse_data()` | `PARSE_ERR_DATA` / `PARSE_ERR_UNSUPPORTED` (`R`, `##`) |
| 5 | `while (*p != '\0')` + `is_trailing_space()` | `PARSE_ERR_TRAILING` |

- 각 단계 함수가 `const char **pp`(포인터의 포인터)를 받는 이유 → 각 단계 함수가 **"어디까지 읽었는지"를 호출한 쪽에 알려주려고.** 함수 안에서 `p`를 옮겨도, 그냥 `const char *p`로 받으면 **복사본**이 옮겨질 뿐이라 바깥의 `p`는 그대로다 (M0-3 실험 2 swap: 값 복사). 포인터의 주소(`&p`)를 넘기면 함수가 바깥 `p` 자체를 다음 위치로 옮길 수 있다

```c
const char *p = line;            /* p는 '('를 가리킴 */
parse_timestamp(&p, &ts);        /* 함수가 *pp = ...로 바깥 p를 옮김 */
/* 이제 p는 ')' 다음 공백을 가리킴 → 다음 단계가 거기서부터 읽는다 */
```

  - 비유: 책 읽기 바통 넘기기. 각 단계가 "나는 여기까지 읽었어"라며 **책갈피(p)를 옮겨서** 다음 단계에 넘긴다
  - 성공했을 때만 `*pp = p;`로 옮긴다 → 실패하면 책갈피가 원래 자리 그대로라 어디서 틀렸는지 알 수 있다

## 4. 16진수 글자 → 숫자

```c
static int hex_value(char c) {
    if (c >= '0' && c <= '9') { return c - '0'; }
    if (c >= 'A' && c <= 'F') { return c - 'A' + 10; }
    ...
}
```

- `c - '0'`이 숫자가 되는 이유 (ASCII) → 컴퓨터는 글자도 **숫자 코드(ASCII)**로 저장한다. `'0'`~`'9'`는 코드가 **48~57로 연속**이라, 글자 코드에서 `'0'`(48)을 빼면 실제 숫자가 나온다

| 글자 | ASCII 코드 | `c - '0'` |
| --- | --- | --- |
| `'0'` | 48 | 48 - 48 = **0** |
| `'1'` | 49 | 49 - 48 = **1** |
| `'7'` | 55 | 55 - 48 = **7** |
| `'9'` | 57 | 57 - 48 = **9** |

  - `'A'`~`'F'`도 65~70으로 연속이라 `c - 'A' + 10` → `'A'` = 10, `'B'` = 11, ..., `'F'` = 15
  - 소문자 `'a'`~`'f'`는 97~102라서 `c - 'a' + 10`으로 따로 처리
  - 주의: 글자 `'7'`과 숫자 `7`은 다르다. `'7'`은 메모리에 55로 들어 있다 (Java의 `char`도 같다: `'7' - '0' == 7`)
- `"1027"` → `{0x10, 0x27}`로 만드는 방법 (`parse_data`의 `<< 4`와 `|`) → 16진수 **2글자 = 1바이트**. 앞 글자는 바이트의 **윗 4비트**, 뒤 글자는 **아랫 4비트**가 된다

```
글자:        '1'        '0'        '2'        '7'
hex_value:    1          0          2          7
             앞 글자    뒤 글자     앞 글자    뒤 글자
             << 4       |          << 4       |
           0001 0000  | 0000     0010 0000  | 0111
           ────────────────      ────────────────
data[0] =  0001 0000 = 0x10      data[1] = 0010 0111 = 0x27
```

```c
if (digits % 2u == 0u) {
    data[byte_index] = (uint8_t)(v << 4);    /* 짝수 번째 글자: 윗 4비트에 놓기 */
} else {
    data[byte_index] |= (uint8_t)v;          /* 홀수 번째 글자: 아랫 4비트에 OR로 합치기 */
}
```

  - `<< 4` = 4칸 위로 올리기 (16진수 한 글자 = 4비트, M0-5)
  - `|` = 비어 있는 아랫 4비트에 끼워 넣기 (M0-5 set)
  - `byte_index = digits / 2` → 글자 0, 1번은 `data[0]`, 2, 3번은 `data[1]`...

## 5. 타임스탬프: double 대신 정수 (마이크로초)

- `(0.100000)` → `100000`, `(0.5)` → `500000`이 되는 과정 → 점(`.`)을 기준으로 **초 부분**과 **소수 부분**을 따로 정수로 읽고, 마지막에 합친다

```
(0.100000)
  초 부분  "0"      → 0
  소수 부분 "100000" → 100000 (6자리 그대로)
  결과 = 0 × 1000000 + 100000 = 100000 us

(0.5)
  초 부분  "0"  → 0
  소수 부분 "5"  → 5 (1자리) → 6자리가 될 때까지 뒤에 0 붙이기(× 10 다섯 번) → 500000
  결과 = 0 × 1000000 + 500000 = 500000 us

(2.25)
  초 부분 2, 소수 부분 "25" → 250000
  결과 = 2 × 1000000 + 250000 = 2250000 us
```

  - 소수 부분을 "6자리로 채우는" 이유: 마이크로초는 1초의 100만분의 1 → 소수점 아래 **6자리**가 정확히 마이크로초 단위다. `0.5`초는 `0.500000`초와 같다
  - 소수점 아래가 7자리 이상이면 마이크로초보다 정밀한 값이라 형식 위반(`PARSE_ERR_TIMESTAMP`)
- `double`로 안 받은 이유 → **오차 때문이다** (M1-3에서 본 `0.1 + 0.2 = 0.30000000000000004`). `0.1`초를 double로 받으면 정확히 0.1이 아니라 0.1000000000000000055...가 된다. 이걸 ms로 바꾸다 99ms가 될 수도 있다. 시나리오의 "500ms 타임아웃" 같은 판단이 이 오차로 1ms 어긋나면 테스트 결과가 달라진다. 정수 마이크로초면 `0.1초 = 100000`으로 **정확**하다 (금액을 센트 정수로 저장하는 것과 같은 이유)
- `uint32_t`가 아니라 `uint64_t`인 이유 (`(1697800000.123456)`) → 실제 candump 시각은 **1970년부터 센 초**(유닉스 시간)라 크다. 마이크로초로 바꾸면 `1697800000123456`(16자리). `uint32_t` 최댓값은 약 **43억**(10자리)이라 담을 수 없다 → 넘쳐서 엉뚱한 값이 된다 (M0-4 오버플로우). `uint64_t`는 약 1800경까지 담을 수 있다

| 타입 | 최댓값 | `1697800000123456` 담기 |
| --- | --- | --- |
| `uint32_t` | 4,294,967,295 (약 43억) | ❌ 넘침 |
| `uint64_t` | 18,446,744,073,709,551,615 (약 1800경) | ✅ |

  - 그래도 초 부분은 최대 12자리까지만 받는다 (`TS_MAX_SEC_DIGITS`). 그보다 크면 `uint64_t`도 넘칠 수 있어서 미리 막는다
  - M3-3에서 디스패처에 넘길 때는 "첫 프레임 기준 몇 ms"로 바꿔서 `uint32_t now_ms`에 넣는다 (상대 시각은 작다)

## 6. 왜 `sscanf`나 `strtoul`을 안 썼나 (이슈 키워드)

- `sscanf("%s")`의 위험 → `%s`는 공백이 나올 때까지 **몇 글자든** 읽어서 버퍼에 넣는다. 버퍼가 `char data[17]`인데 줄에 100글자가 있으면 **버퍼 밖까지 써 버린다** (버퍼 오버플로우, M0-6 실험 2). `%16s`처럼 최대 길이를 꼭 적어야 하는데, 빼먹기 쉽다. 그리고 `%x`는 자리 수를 검사하지 않는다 → 직접 확인해 보니 4자리 ID `1000#`도 그냥 받아줬다

```
sscanf("(0.1) vcan0 1000#10", "%*s %*s %x#%16s", &id, data)
→ 성공(n=2), id = 0x1000   ← 형식상 틀린 4자리 ID를 그대로 받아버림
```

- `strtoul`이 너무 너그러운 점 (예: `" -1"`, `"0x100"`) → 직접 돌려본 결과:

| 입력 | `strtoul(입력, &end, 16)` 결과 | 문제 |
| --- | --- | --- |
| `"100"` | 0x100 | 정상 |
| `" -1"` | **0xFFFFFFFFFFFFFFFF** | 앞 공백과 마이너스를 받아들이고, -1을 unsigned로 바꿔 거대한 값이 됨 |
| `"0x100"` | 0x100 | `0x` 접두사를 받아줌 (우리 형식에는 없음) |
| `"  7FF"` | 0x7FF | 앞 공백을 몰래 건너뜀 |
| `"+10"` | 0x10 | `+` 기호를 받아줌 |
| `"1000"` | 0x1000 | 자리 수 제한이 없음 (4자리 ID도 통과) |

  - `strtoul`은 "어떻게든 숫자로 읽어 주려는" 함수라, **우리 형식에 없는 것들까지 정상으로 받아준다.** 그러면 틀린 로그가 오류 없이 통과해서 엉뚱한 프레임이 만들어진다
- 직접 한 글자씩 검사하는 방식의 장점 →
  - **형식을 정확히 지킨다.** "16진수 정확히 3자리 + `#`", "공백 정확히 한 칸"처럼 정의서 규칙을 그대로 코드로 옮길 수 있다
  - **버퍼를 넘칠 수 없다.** 자리 수를 세면서 읽고, 최대치(데이터 16자리, ID 8자리 등)에서 바로 멈춘다
  - **어디서 왜 틀렸는지 안다.** 실패한 단계에 맞는 `PARSE_ERR_xxx`를 돌려줄 수 있다 (`sscanf`는 "몇 개 읽었나" 숫자만 알려줌)
  - 단점: 코드가 길어진다 → 단계별 작은 함수(`parse_timestamp`, `parse_id` 등)로 나누고, 테스트 69개 + 퍼징으로 검증했다

## 7. 오류를 enum으로 (이슈 할 일)

| 결과 | 예시 줄 |
| --- | --- |
| `PARSE_OK` | `(0.100000) vcan0 100#1027000000000000` |
| `PARSE_SKIP` | 빈 줄, `# 주석` |
| `PARSE_ERR_TIMESTAMP` | `vcan0 100#1027...` (타임스탬프 없음), `(0.1234567) ...` (소수점 7자리) |
| `PARSE_ERR_INTERFACE` | `(0.1) 100#1027...` (인터페이스 없음), `(0.5)vcan0 ...` (공백 없음) |
| `PARSE_ERR_ID` | `(0.1) vcan0 10#...` (2자리), `(0.1) vcan0 1G0#...` (16진수 아님) |
| `PARSE_ERR_DATA` | `(0.1) vcan0 100#102` (홀수 자리), `(0.1) vcan0 100#10G7` |
| `PARSE_ERR_UNSUPPORTED` | `(0.1) vcan0 100#R` (Remote), `12345678#...` (Extended), `100##...` (CAN FD) |
| `PARSE_ERR_TRAILING` | `(0.1) vcan0 100#1027 extra` |
| `PARSE_ERR_NULL` | `parse_candump_line(NULL, ...)` |

- `bool` 대신 enum으로 돌려주는 이유 → `bool`은 "성공 / 실패"만 알려준다. 로그 파일이 수천 줄일 때 "**몇 번째 줄이 왜 틀렸는지**" 알아야 고칠 수 있다. M3-3 파일 읽기 루프에서 `"5번째 줄: ERR_DATA"`처럼 출력하고, 종류별로 개수를 셀 수 있다. 또 `PARSE_SKIP`(정상적으로 건너뜀)과 오류를 구분할 수 있다 → bool로는 "주석이라 건너뛴 것"과 "깨진 줄"이 똑같이 false가 된다
- `PARSE_SKIP`이 오류가 아닌 이유 → 빈 줄과 주석은 **형식에서 허용한 줄**이다 (`docs/log-format.md` 2번). 사람이 읽기 쉽게 넣은 것이지 깨진 데이터가 아니다. 오류로 세면 정상 파일도 "오류 10개"처럼 보여서 진짜 오류가 묻힌다 (M2-6 IGNORED와 ERROR를 나눈 것과 같은 이유)
