- 채우기 전의 CPU가 그렇게 나온 이유 → `n = 0`이면 **기다리지 않고 바로** "시간 초과"를 돌려준다 → 루프가 쉬지 않고 돈다 (**busy loop**, 바쁜 대기)
  - 1초에 수백만 번 `read_frame` → TIMEOUT → `judge()`를 반복한다. 할 일이 없는데 CPU 코어 하나를 통째로 쓴다 (3초 동안 CPU 3.28초)
  - `poll(..., 10)`은 **커널에게 "10ms 동안 재워 줘, 프레임 오면 깨워 줘"**라고 맡긴다. 자는 동안 CPU를 0 쓴다 → 상태 `S`(sleeping)
  - 그래서 "10ms마다 판단"을 `while (1) { if (지금 - 지난번 >= 10) 판단; }`처럼 시계를 계속 보면서 만들면 안 된다. **잠들었다가 깨어나는 방식**(poll, sleep, 타이머)이어야 한다
  - 실제 ECU도 같다: 할 일이 없으면 CPU를 저전력 대기(idle, `WFI` 명령)로 두고 타이머 인터럽트로 깨어난다. 차가 꺼져 있을 때 배터리를 아끼는 것도 이 덕분
  - Java로: `while (!queue.hasItem()) {}`(바쁜 대기) vs `queue.poll(10, MILLISECONDS)`(블로킹 큐, 스레드가 잠듦)

## 1. 무엇이 바뀌었나

```
M5-7까지:  read() ──(프레임이 올 때까지 끝없이 잠듦)──→ 프레임 → 판단
M5-8:      poll(fd, 10ms) ─┬─ 프레임 옴   → read() → 디스패처 → 판단
                           └─ 10ms 지남  → (TIMEOUT)      → 판단   ← 새로 생김
```

- 프레임이 없을 때 판단하면 무엇이 달라지나 (`bcm_step`은 새 입력이 없는데 무엇을 보나) → 입력(`VehicleInputs`)은 그대로지만 **`now_ms`(지금 시각)가 커진다.** 시간으로 정해지는 판단이 바뀐다

| 판단 | 무엇을 보나 | 프레임 없이 시간만 흐르면 |
| --- | --- | --- |
| 신호 끊김 (M4-6) | `now_ms - *_rx_ms > 500` | ✅ 바뀐다: 500ms가 넘는 순간 "끊김" → WARNING (T5) |
| 0x400 송신 (M4-8) | `now_ms >= next_tx_ms` | ✅ 바뀐다: 100ms마다 계속 나간다 (Alive Counter도 계속 증가) |
| 잠금/해제, 문 열림 경고 (T3, T6 ...) | 차속, 기어, 문 **값** | ❌ 그대로 (값이 안 바뀌었으니 같은 결론) |
| 디바운싱(M4-5), 신호 복귀(M4-6) | 프레임 **개수**(`*_rx_count`) | ❌ 그대로. 그래서 "판단 횟수가 아니라 프레임 수를 센다"고 설계했었다 (판단을 10ms마다 해도 "3번 연속"이 망가지지 않음) |

  - 즉 TIMEOUT 판단은 "**시간이 흘렀다는 사실**"만 새 정보다. M4에서 `bcm_step(ctx, in, now_ms, out)`에 시각을 따로 받게 만들어 둔 덕분에 코드 변경 없이 그대로 부를 수 있었다
  - 디스패처는 안 부른다 (새 프레임이 없다). 그래서 `judge()`만 따로 뽑아서 두 경우가 같이 쓴다
- 파일 소스는 `timeout_ms`를 무시하고 TIMEOUT을 안 준다. 그래서 파일 모드 테스트(`test_scenarios`)가 안 바뀌었다. 파일 모드에도 TIMEOUT을 흉내 냈다면 무엇이 달라졌을까 → **신호 끊김을 더 빨리(정확히) 잡아서, 시나리오 테스트의 기대 시각이 바뀐다**
  - 지금 파일 모드는 "다음 프레임이 올 때"만 판단한다. 시나리오 03: 차속 마지막 수신 2.9s → 500ms 넘는 첫 **프레임**이 3.5s(0.1초 간격) → T5가 **3.5s** (`test_scenarios`의 `3500u`, "+600ms")
  - 가짜 틱(다음 프레임 시각 전까지 10ms씩 시계를 돌려 TIMEOUT)이 있었다면 2.9 + 0.5를 넘는 첫 틱 **3.41s**에 T5 → 테스트 기대값을 바꿔야 한다 (07도 3.6s → 3.51s 정도)
  - 파일 끝 뒤로는 시간이 없으니(END) 재생 후 "조용한 구간"은 여전히 못 본다
  - 일부러 안 바꾼 이유: M5-5부터의 원칙 "파일 모드 결과는 그대로(회귀 없음)". 파일 모드는 **기록된 프레임만큼만** 보는 재현 도구로 두고, 시간 흐름은 실시간 모드와 가짜 시계 테스트(`test_silence_keeps_judging`)로 확인한다
  - 둘의 차이(3.5s vs 약 3.4s)는 3번 실험에서 직접 비교한다

| | 파일 모드 | 실시간 |
| --- | --- | --- |
| T3 시각 | 1.3s | ✅ 1.882s (켠 뒤 `canplayer`까지 0.582s 밀림, 35번 노트 2번) |
| `신호 끊김: 차속` / T5 시각 | 3.5s (마지막 수신 2.900s) | ✅ 4.007s (마지막 수신 3.482s = 2.9 + 0.582) |
| 마지막 수신 → T5 | **600ms** | ✅ **525ms** |
| T3 → T5 간격 | 2.2s | ✅ **2.125s** (75ms 빠름) |

- 실시간에서 T5가 (간격으로 봐서) 더 빨리 나온 이유. 파일 모드의 3.5s는 정확히 무엇의 시각인가 → 파일 모드의 3.5s는 "끊긴 순간"이 아니라 **500ms를 넘긴 뒤 처음 도착한 다른 프레임**(0x300, 0x200)의 시각이다
  - 파일 모드는 프레임이 올 때만 판단 → 3.4s 프레임: 3.4 - 2.9 = 500ms, "초과"가 아님 → 다음 판단은 0.1초 뒤 3.5s 프레임 → 그제서야 600ms로 끊김. 판단 간격(100ms)만큼 **늦게** 안다
  - 실시간은 10ms마다 판단 → 500ms를 넘긴 첫 틱(이론상 510ms 안)에 안다. 여기서는 VM 타이머가 거칠어서 525ms (4번)
  - 즉 "끊김을 아는 시각" = 500ms + **판단 간격만큼의 지연**. 판단 간격이 100ms(프레임 주기)에서 10ms(틱)로 줄어서 빨라졌다
  - 나머지 전이(T9, T7)는 **프레임 값**으로 정해져서 간격이 같다: T5→T9 0.775s(파일 0.7s, VM 지연이 겹침), T9→T7 3.3s(파일 3.3s)
- 어느 쪽이 실제 ECU에 가까운가 → **실시간(주기 판단).** 실제 ECU는 다른 메시지가 오든 말든 주기 태스크(10ms 등)가 타임아웃을 검사한다. 모든 신호가 한꺼번에 끊겨도 잡는다
  - 파일 모드처럼 "다른 프레임이 와야 안다"면, 다른 신호까지 다 끊긴 경우(선이 빠짐)에는 **영원히 모른다** (35번 노트 5번)
  - 안전 규격(ISO 26262)의 FTTI(고장 허용 시간, M4-6): "고장 발생 → 안전한 상태"까지 걸리는 시간이 정해져 있다. 감지가 판단 간격만큼 늦어지니, 판단 간격도 이 시간 예산에 들어간다

## 4. 10ms는 정말 10ms인가

VM에서 `poll(NULL, 0, 10)`(10ms 자기)을 300번 재 보면: **min 10.06 / avg 32.72 / max 54.29 ms**

- 10ms를 요청했는데 평균 33ms인 이유 → `poll`의 시간은 "**최소** 이만큼 잔다"는 약속이지 "정확히"가 아니다. 깨어나는 시각은 OS가 정한다
  - 우리 VM은 맥 위의 가상 머신이다. 맥이 VM을 "가끔" 돌려주고, 한가할 때는 전기를 아끼려고 타이머를 **몰아서**(timer coalescing) 깨운다 → 10ms 요청이 20 ~ 50ms로 늘어난다
  - 진짜 리눅스 PC에서는 보통 10.05 ~ 10.1ms 정도로 훨씬 정확하다. 그래도 바쁘면(다른 프로세스, 스케줄링) 늦어질 수 있다
  - 일반 리눅스는 "공평하게 나눠 쓰기"가 목표인 OS라 **마감 시간 보장**이 없다
- 그런데도 0x400의 **평균** 간격이 100ms로 맞는 이유 (2번의 `candump -td` 간격은 들쭉날쭉) → 다음 송신 시각을 **"보낸 시각 + 100"이 아니라 "예정 시각 + 100"**으로 정하기 때문 (M4-8의 `next_tx_ms += 100`)
  - 이번에 30ms 늦게 보냈으면, 다음 예정은 그대로라 다음 것은 상대적으로 **일찍** 나간다 (`-td`에 0.07 같은 짧은 간격이 섞이는 이유) → 오차가 **쌓이지 않고** 평균이 맞는다
  - "보낸 시각 + 100"이었다면 늦을 때마다 밀려서 평균이 130ms가 됐을 것 (3초에 30개가 아니라 23개)
  - 2번 결과: 3초에 30개 = 평균 100ms ✅
- 진짜 ECU는 이 문제를 어떻게 피하나 → **실시간 OS(RTOS) + 하드웨어 타이머**를 쓴다
  - 하드웨어 타이머가 정확히 10ms마다 인터럽트 → 10ms 태스크를 깨운다. 흔들림(jitter)이 µs 단위
  - RTOS(예: AUTOSAR OS, FreeRTOS)는 **우선순위**가 높은 태스크를 반드시 먼저, 마감 안에 돌린다 (일반 OS는 "공평", RTOS는 "마감 보장")
  - 다른 일(통신, 진단)이 많아도 안전 판단 태스크는 밀리지 않는다
  - 리눅스로 비슷하게 하려면: `PREEMPT_RT` 커널 + 실시간 우선순위(`SCHED_FIFO`) + `timerfd`/`clock_nanosleep(TIMER_ABSTIME)`. 우리 시뮬레이터는 학습용이라 일반 `poll`로 충분

## 5. 정리

- 이번 이슈를 한 줄로 → `read()`(끝없이 기다림)를 `poll(fd, 10ms)`(프레임 **또는** 10ms)로 바꿔, 프레임이 없어도 10ms마다 BCM이 판단하게 했다. 그래서 0x400이 계속 나가고, 모든 신호가 끊겨도 500ms 뒤 알아챈다. 기다리는 동안은 잠들어서 CPU 0%
- `poll()`과 웹에서 비슷한 것 (Java NIO `Selector`, Node.js 이벤트 루프) → 셋 다 "**여러 입력 중 무엇이든 준비되거나, 시간이 다 되면 깨워 줘**"를 OS에 맡기는 같은 방식이다

| | 기다리는 것 | 시간 제한 |
| --- | --- | --- |
| 우리 `poll(&p, 1, 10)` | CAN 소켓 fd 1개 | 10ms |
| Java NIO `selector.select(10)` | 등록한 채널(소켓) 여러 개 | 10ms |
| Node.js 이벤트 루프 | 소켓, 파일, 타이머(`setTimeout`) | 가장 가까운 타이머까지 |
| Netty, nginx, Redis | 수천 개 연결 (`epoll`) | |

  - 스레드 하나가 **여러 연결**을 처리할 수 있는 이유가 이것이다 (연결마다 스레드를 두고 `read()`에서 각자 잠드는 대신). 우리도 M5-9에서 "Ctrl+C 시그널"이라는 두 번째 사건을 같은 루프에 넣는다
  - 리눅스 `poll`의 개선판이 `epoll`(연결이 많을 때 빠름). Java NIO와 Node.js(libuv)도 리눅스에서는 내부적으로 `epoll`을 쓴다
