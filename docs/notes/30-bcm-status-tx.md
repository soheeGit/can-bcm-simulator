## 1. 출력 파일 손으로 해석하기

`signal-spec.md`의 0x400 표를 보고 해석한다.

| 줄 | BcmState | DoorLockCmd | WarningBuzzer | AliveCounter |
| --- | --- | --- | --- | --- |
| `(1.900000) vcan0 400#0101000000000003` | DRIVING_LOCKED ✅ (`data[0]` = 01 → 아래 2비트 01 = 1) | 도어 잠금 ✅ (`data[1]` = 01 → bit 0 = 1) | OFF ✅ (`data[1]` = 01 → bit 1 = 0) | 3 ✅ (`data[7]` = 03 → 아래 4비트 0011 = 3) |
| `(4.300000) vcan0 400#020200000000000B` | WARNING ✅ (`data[0]` = 02 → 아래 2비트 10 = 2) | 0 ✅ (`data[1]` = 02 = 0000 0010 → bit 0 = 0) | ON ✅ (`data[1]` = 02 → bit 1 = 1) | 11 ✅ (`data[7]` = 0B → 1011 = 11) |
| `(3.300000) vcan0 400#0100000000000001` | DRIVING_LOCKED ✅ (`data[0]` = 01 → 1) | 0 ✅ (`data[1]` = 00 → bit 0 = 0) | 0 ✅ (`data[1]` = 00 → bit 1 = 0) | 1 ✅ (`data[7]` = 01 → 1) |

- 3.3초 줄의 Alive Counter가 1인 이유 (1.9초에 3이었는데) → **15 다음에 0으로 돌아가서 한 바퀴 돌았기 때문**

```
시각     1.9  2.0  2.1  ...  3.1  3.2  3.3
Alive     3    4    5   ...   15    0    1
                               ↑    ↑
                         4비트 최대  다시 0부터
```

  - 1.9초 → 3.3초는 0.1초 간격으로 **14번** 더 보냈다 → 3 + 14 = 17. 그런데 Alive Counter는 **4비트**(0 ~ 15)라 16을 넘으면 다시 센다 → 17 - 16 = **1**
  - 다른 계산: 0.0초에 0부터 시작했으니, 3.3초는 34번째 송신 = 0부터 세면 33번 → 33 ÷ 16의 나머지 = **1** (`n % 16`. `test_tx_round_trip`이 이 규칙으로 확인한다)
  - 코드: `ctx->alive_counter = (ctx->alive_counter + 1u) % (BCM_STATUS_ALIVE_MAX + 1u);` → 15 + 1 = 16 → 16 % 16 = 0
  - 받는 쪽은 "**값이 1씩 늘어나다가 15 다음 0**"을 기대한다. 그러니 3 → 1은 이상한 게 아니라, 그 사이 14개를 모두 받았다면 정상이다. 만약 3 다음에 바로 5가 오면 → 프레임 하나를 **놓쳤다**는 뜻(3번 질문)

- 세 줄을 비교하면 (손으로 푼 결과)

| 시각 | 상태 | 잠금 명령 | 경고음 | 왜 |
| --- | --- | --- | --- | --- |
| 1.9초 | DRIVING_LOCKED | **1** | 0 | 1.8초에 T3 잠금 → 다음 송신에 한 번 |
| 3.3초 | DRIVING_LOCKED | 0 | 0 | 그냥 잠금 주행 중 (명령은 1회만이라 0) |
| 4.3초 | **WARNING** | 0 | **1** | 4.2초 문 열림(T6) → 경고음은 WARNING인 동안 계속 |

  - 같은 DRIVING_LOCKED인데 1.9초엔 잠금 명령이 1, 3.3초엔 0 → **Mealy**(전이 순간 한 번) / 경고음은 WARNING이면 1 → **Moore**(상태로 정해짐). 23번 노트 4번의 두 종류 출력이 0x400에 그대로 보인다
  - 코드의 `decode_bcm_status()`가 하는 일을 손으로 해 본 것: 바이트를 고르고 → 2진수로 펼치고 → 자리(비트)별로 읽기

## 2. 잠금 명령 기억 (`lock_cmd_pending`)

- 잠금 명령이 1.8초(T3)가 아니라 1.9초 0x400에 실린 이유 → 1.8초 송신은 그 시각 **첫 프레임(0x300) 판단 뒤**에 끝나고, T3은 **마지막 프레임(0x100) 판단**에서 일어난다. 그래서 기억해 뒀다가 다음 송신(1.9초)에 싣는다
- 실험(확인됨): 기억 없이 싣으면 → 시나리오 01, 02, 05 모두 **0번**. 다음 송신 때 `door_lock_cmd`는 이미 0이라 실릴 기회가 없다. BCM 로그엔 "잠금 1회"인데 버스엔 안 나감 → round-trip 테스트가 잡음
- Mealy 출력을 주기 메시지에 실을 때의 문제 → 한 번만 생기는 **이벤트**가 송신 시각과 안 맞으면 **사라진다**. 해결: 보낼 때까지 기억(latch) → 보낸 뒤 **꼭 지움** (안 지우면 매 송신마다 1 → 모터 반복). 상태(경고음)는 언제 보내도 실리니 필요 없다

## 3. Alive Counter

- 무엇이고 왜 필요한가 (받는 쪽 입장에서) → 보낼 때마다 1씩 늘어나는 4비트 숫자(0 ~ 15). 받는 쪽은 이 값이 **계속 바뀌는지**로 "BCM이 살아서 새로 판단한 프레임인가"를 안다
  - 프레임이 오기만 한다고 BCM이 정상이라는 보장은 없다. BCM 프로그램이 멈춰도 통신 칩이 **마지막 프레임을 계속 다시 보내는** 경우가 있다 → 내용(상태, 경고음)은 그대로라 겉보기엔 정상
  - Alive Counter가 **같은 값으로 멈춰 있으면** → BCM이 멈춘 것. 그 프레임의 상태 값을 믿지 않는다
- 15 다음에 0으로 돌아가게 한 코드 → `src/bcm.c`의 `bcm_tx_poll()`

```c
ctx->alive_counter = (uint8_t)((ctx->alive_counter + 1u) % (BCM_STATUS_ALIVE_MAX + 1u));   /* 15 + 1 = 16 → 16 % 16 = 0 */
```

  - `%`(나머지)로 0 ~ 15 안에 가둔다. 4비트 칸에 16 이상을 넣으면 `can_set_bits`가 어차피 아래 4비트만 남기지만(16 = 1 0000 → 0000), 값 자체를 0 ~ 15로 유지하는 게 뜻이 분명하다
- 받는 쪽이 "BCM이 멈췄다"를 알아채는 방법 2가지 (힌트: M4-6 타임아웃) →

| 방법 | 잡는 고장 | 우리 BCM의 M4-6과 비교 |
| --- | --- | --- |
| **타임아웃**: 0x400이 500ms 넘게 안 옴 | BCM이 꺼짐, 선이 끊김 → **아예 안 옴** | 우리가 0x100 ~ 0x300에 하는 것과 같음 |
| **Alive Counter 확인**: 값이 안 바뀜, 또는 1씩이 아니라 건너뜀 | BCM이 멈췄는데 **같은 프레임이 계속 옴** / 중간 프레임을 놓침 | 우리는 아직 안 함 (받는 메시지에 Alive Counter가 없음) |

  - 둘 다 필요하다: 타임아웃은 "안 옴"을, Alive Counter는 "오긴 오는데 죽은 데이터"를 잡는다
  - 건너뜀 예: 3 다음에 5 → 4가 든 프레임을 놓쳤다 (15 → 0은 정상)
  - 실무에서는 여기에 **체크섬/CRC** 신호를 더해 "값이 깨지지 않았나"까지 본다 (AUTOSAR E2E 보호). 이 프로젝트 범위 밖

## 4. 0x400에 보이는 상태가 늦을 수 있는 이유

- 시나리오 02에서 T6은 4.2초인데 0x400의 WARNING은 4.3초부터 보이는 이유 → 2번과 같은 이유. 4.2초 송신은 **0x300 판단 뒤**에 이미 끝났고, T6은 그다음 **0x200(도어) 판단**에서 일어났다 → 다음 송신(4.3초)에 실린다

```
4.2초 0x300 → 판단 (아직 DRIVING_LOCKED) → 4.2초 송신 (상태 1)
4.2초 0x200 → 판단: 문 3번째 열림 → T6 → WARNING     (송신 안 함)
4.3초 0x300 → 판단                       → 4.3초 송신 (상태 2, 경고음 1)
```

  - 그 칸의 첫 프레임(0x300)이 아닌 프레임 때문에 생긴 변화는 전부 **다음 칸**에 보인다 → 최대 100ms 늦음
- 이 지연을 없애려면 어떻게 바꿀 수 있나 (그리고 왜 지금은 안 바꿨나) →
  - 방법 1: **상태가 바뀌면 주기를 기다리지 않고 바로 한 번 보내기** (이벤트 송신, 실무에서 흔함: 주기 송신 + 변화 시 즉시 송신)
  - 방법 2: 한 칸의 프레임을 **다 처리한 뒤** 보내기. 파일 모드에서는 "칸의 끝"을 미리 알 수 없어서(다음 칸 첫 줄을 읽어야 앎) 어렵다
  - 안 바꾼 이유: 100ms 늦게 보여도 경고음, 잠금에는 문제가 없고(사람은 못 느낌), 정의서가 "100ms 주기"라 지금이 정의서대로다. 방법 1은 버스에 프레임이 늘어나서 다른 메시지와 부딪힐 수 있다(CAN 버스 부하). M5 실시간 모드에서 다시 볼 거리

## 5. round-trip 세 단계

| 단계 | 쓰기 | 읽기 | 테스트 |
| --- | --- | --- | --- |
| 신호 ↔ 프레임 | `encode_bcm_status()` | `decode_bcm_status()` | `test_bcm_status_round_trip` (256가지 조합 전부), 정의서 예시 5 |
| 프레임 ↔ 한 줄 | `format_candump_line()` | `parse_candump_line()` (M3-2) | `test_format_parse_round_trip` (프레임 4개, 시각까지) |
| 전체 (시나리오 → 파일 → 해석) | `log_read_file(..., tx_out)` | 파일을 다시 `parse` + `decode` | `test_tx_round_trip` (시나리오 02, 106프레임) |

- round-trip 테스트가 잡는 버그의 종류 → **쓰는 쪽과 읽는 쪽이 서로 다르게 알고 있는 버그**
  - 비트 위치, 길이가 어긋남 (예: 경고음을 bit 9가 아니라 bit 10에 씀) → 다시 읽으면 값이 다름
  - 바이트 순서(리틀 엔디안) 실수, 16진수 대소문자, 자릿수, 시각 형식 실수
  - **한쪽만 고친** 경우: 정의서가 바뀌어 인코더만 고치고 디코더를 안 고치면 바로 실패
  - 전체 단계는 그 밖의 것도 잡는다: 송신 개수와 주기(100ms마다 빠짐없이), Alive Counter 순서, **잠금 명령이 실제로 나갔나**(2번 실험에서 잡은 것)
  - 한계: 인코더와 디코더가 **똑같이 틀리면** 못 잡는다 (둘 다 bit 10으로 착각하면 왕복은 맞음) → 그래서 정의서 예시 5(`400#0101000000000005`)처럼 **정해진 정답 바이트**와 비교하는 테스트도 같이 둔다
- 이슈의 완료 조건 "출력 로그를 다시 파서로 읽어 디코딩하면 원래 출력과 같다"와의 관계 → `test_tx_round_trip`이 그 조건을 자동으로 확인한다
  - 다시 읽은 값이 BCM이 알던 값과 같은지: 프레임 수 = `stats.tx_frames`, 잠금 명령 수 = `stats.bcm_lock_cmds`, 경고음 = WARNING일 때만, 상태가 처음 보이는 시각(1.9초 잠금, 4.3초 경고)
  - 덤: can-utils `log2long`이 이 파일을 읽었다 → **우리 파서뿐 아니라 남의 도구**로도 읽히는 진짜 candump 형식

## 6. can-utils 호환

- `log2long < result.log`가 읽어 준다는 게 왜 중요한가 (M5와 연결) → 우리 출력이 **표준 candump 형식**이라는 증거. 우리 파서로만 읽히면 "우리끼리만 맞는 형식"일 수도 있다
  - M5에서 쓸 수 있다: `canplayer`로 `result.log`를 vcan에 **그대로 재생**하거나, 실시간으로 보낸 0x400을 `candump`로 받아 지금 파일과 비교할 수 있다
  - 실무 도구(Vector CANoe, BusMaster 등)도 이런 로그 형식을 읽는다 → 다른 사람, 다른 도구와 결과를 주고받을 수 있다
