# 32. can-utils로 CAN 통신 체험하기 (M5-2)

> 전부 **VM 안**에서 한다: 맥 터미널에서 `multipass shell can-vm` → `cd ~/can-bcm-simulator` → `./scripts/setup_vcan.sh`
> 터미널 두 개가 필요한 실험은 맥 터미널 창(또는 탭)을 하나 더 열고 거기서도 `multipass shell can-vm`
> 코드는 없다. API를 만들기 전에 `curl`로 먼저 찔러 보는 것과 같다

## 1. 보내고 받기 (`cansend` / `candump`)

| 터미널 A (받기) | 터미널 B (보내기) |
| --- | --- |
| `candump vcan0` | `cansend vcan0 100#1027000000000000` |
| | `cansend vcan0 200#01` |
| | `cansend vcan0 7FF#DEADBEEF` |

| 확인 | 예상 | 실제 |
| --- | --- | --- |
| 터미널 A에 나온 세 줄 | | ✅ `vcan0 100 [8] 10 27 00 00 00 00 00 00` / `vcan0 200 [1] 01` / `vcan0 7FF [4] DE AD BE EF` (인터페이스, ID, `[DLC]`, 데이터) |
| `100#1027000000000000`의 차속은 몇 km/h인가 (signal-spec) | 199.88km/h | ❌ **100.00 km/h**. 리틀 엔디안이라 `data[0]`(`10`)이 낮은 자리 → `0x2710` = 10000 → × 0.01 = 100.00 km/h. `10 27`을 순서대로 읽으면 안 된다 (M2, 30번 노트 1번과 같은 방법) |

- 터미널 A를 안 켜 둔 상태에서 `cansend`만 하면 프레임은 어떻게 되나 → (화면엔 아무 일도 없지만) 프레임은 **보내지고, 받는 사람이 없으니 그냥 사라진다.** 어디에도 저장되지 않아서 나중에 `candump`를 켜도 안 보인다
  - CAN은 **방송**이라 "받는 사람"을 정하지 않고 버스에 띄우기만 한다. 우편함(큐)이 아니라 **라디오 방송**: 그 순간 켜 둔 사람만 듣는다
  - 실제 CAN 하드웨어에서는 다르다: 받는 노드가 하나도 없으면 **ACK**(받았다는 신호, M1)가 없어서 송신 쪽이 오류로 보고 계속 다시 보낸다. vcan은 가상이라 ACK 없이 그냥 성공

## 2. 랜덤 프레임 + 로그 저장 (`cangen` / `candump -l`)

| 터미널 A | 터미널 B |
| --- | --- |
| `candump -l vcan0` (Ctrl+C로 멈춤) | `cangen vcan0 -g 100 -n 20` (100ms마다 20개) |

- 만들어진 파일 이름과 첫 두 줄 → ✅ `candump-2026-11-06_190654.log` (`candump-날짜_시각.log`, candump를 **실행한 폴더**에 생김)

```
(1793959624.507495) vcan0 141#B9BC7662
(1793959624.649496) vcan0 5FD#9AEC8A6FE45A582C
```

  - `candump -l` 중에는 파일이 0줄로 보이고, **Ctrl+C로 멈춰야** 적힌다 (모아 뒀다가 한꺼번에 쓰는 버퍼)
- 이 파일을 우리 프로그램에 넣으면? `./build/bcm_sim -f candump-....log` (VM에서 `make` 먼저) → ✅ **그대로 읽힌다** (`read 40, ok 40, error 0`). 형식이 우리 파서와 같다

```
결과
  read 40, ok 40, error 0  (빈 줄/주석 0)
  디스패처: ok=0 ignored=40 error=0
최종 차량 상태
  차속 : INVALID
  시동 : IGN=OFF GEAR=INVALID
BCM
  최종 상태 : IDLE
  상태 전이 : 0회
```

  - `ignored=40`: `cangen`은 ID를 **랜덤**으로 만든다(`141`, `5FD` ...). 우리가 쓰는 0x100, 0x200, 0x300이 하나도 없어서 디스패처가 전부 "관심 없음"(M2-6)으로 버렸다 → 차속, 시동은 한 번도 못 받아서 처음 값(INVALID, OFF) 그대로, BCM도 IDLE 그대로. **정상 동작**
  - 형식이 깨졌으면 `error`가 늘었을 것. `error 0`이라 "형식은 맞는데 내용이 우리와 상관없다"는 걸 알 수 있다
- 파일 속 시각(`(1793958475.604929)`)이 아주 큰 숫자인 이유와, 우리 로그에는 `[0.000s]`부터 나오는 이유 (M3-3) → 큰 이유는 실제 시간이기 때문이고, 우리 로그는 사람이 보기 쉽게 0부터 시작하도록 ~~현재시간을~~ **첫 프레임의 시각**을 빼고 시작하기 때문이다. 🔺
  - 실제 시간 = **1970년 1월 1일부터 센 초** (유닉스 시간). `1793959624`초 ≈ 2026년 11월
  - 빼는 건 "지금 시각"이 아니라 **파일의 첫 프레임 시각**이다 (`log_read_stream`의 `first_ts_us`). 그래서 언제 실행해도 첫 줄은 항상 `0.000s`

## 3. 시나리오 재생 (`canplayer`)

| 터미널 A | 터미널 B |
| --- | --- |
| `candump vcan0` | `canplayer -I data/scenarios/02_door_open_while_driving.log vcan0=vcan0` |

| 확인 | 예상 | 실제 |
| --- | --- | --- |
| 02 재생에 걸린 시간 (`time canplayer ...`) | real 0m10.520s | ✅ `real 0m10.520s` → 로그의 마지막 시각(10.5초)과 거의 같다 |
| 04(`04_invalid_frames.log`)를 재생하면 | real 0m1.732s | ✅ `real 0m1.732s`에 멈춤. `wrong CAN frame format: '100#10G7000000000000'!` → 1.71초의 깨진 줄에서 중단 (그 앞 56프레임만 보냄) |

- `-I 파일`, `vcan0=vcan0`의 뜻 →
  - `-I 파일`: 재생할 로그 파일 (Input)
  - `vcan0=vcan0`: "로그에 `vcan0`이라고 적힌 줄을 → 지금 컴퓨터의 `vcan0`으로 보내라" (`보낼곳=로그속이름`). 차에서 `can0`으로 녹화한 로그를 집에서 `vcan0`으로 재생할 때는 `vcan0=can0`
- 재생이 한 번에 끝나지 않고 10초쯤 걸리는 이유 → `canplayer`가 로그의 **시각대로** 보내기 때문. 0.1초 간격으로 적힌 프레임은 실제로 0.1초씩 기다렸다가 보낸다 → 녹화 당시와 **같은 속도로** 다시 틀어 준다 (동영상 재생처럼)
  - 그래서 M5의 BCM 입장에서는 진짜 차가 10초 동안 달리는 것과 같다. 파일 모드(M3)는 같은 파일을 순식간에 읽고 끝났다
- 04가 끝까지 재생되지 않는 이유. 시나리오 README에 "M5 재생에는 01~03만"이라고 적어 둔 이유 → wrong CAN frame format: '100#10G7000000000000'! 틀린 프레임이 있기 때문에 ✅ `canplayer`는 깨진 줄을 만나면 **거기서 멈춘다**. 우리 파서(M3-2)는 깨진 줄을 WARN으로 찍고 **건너뛰지만** can-utils는 그렇지 않다
  - 04는 "이상한 입력에도 안 죽는지"를 보는 **파일 모드 전용** 시나리오라 일부러 깨진 줄을 넣었다 → 재생용이 아니다
  - 지금은 README의 "01~03만"보다 늘었다: 05, 06, 07도 깨진 줄이 없어서 재생된다 (01, 03, 07 재생 확인함)
- 이슈의 "M3에서 만든 시나리오 파일을 재생 (호환성 확인! 안 되면 M3-1 포맷 수정)" → 고쳐야 했나? → **안 고쳐도 됐다.** M3-1에서 처음부터 `candump -l` 형식에 맞춰 정해서, `canplayer`가 그대로 재생한다 (깨진 줄을 일부러 넣은 04만 빼고)
  - 반대 방향도 된다: 진짜 `candump -l`이 저장한 파일을 우리 `bcm_sim`이 그대로 읽는다 (2번) → **양쪽으로 호환**

## 4. ID 필터

| 터미널 A | 터미널 B |
| --- | --- |
| `candump vcan0,100:7FF` | `cansend vcan0 100#01` / `cansend vcan0 200#02` / `cansend vcan0 101#03` |

- 터미널 A에 나온 것과 안 나온 것 → cansend vcan0 100#01 이것만 나왔다. ✅ `200`, `101`은 안 나옴
- `100:7FF`의 뜻 (ID와 마스크) → ~~100부터 7FF까지의 범위~~ ❌ **"`ID:마스크`" = 마스크가 1인 비트만 비교해서 ID와 같으면 받는다.** 범위가 아니다
  - 규칙: `(받은 ID & 마스크) == (100 & 마스크)` 이면 받음 (M0 비트 마스크, M2 `can_get_bits`의 `&`와 같은 원리)
  - `7FF` = 11비트 전부 1 → **모든 비트가 같아야** → 정확히 `0x100`만. 범위였다면 `101`, `200`도 나왔어야 하는데 안 나왔다 (위 결과가 증거)
- 0x100 ~ 0x3FF만 받으려면? → ~~candump vcan0,100:3FF~~ ❌ **`candump vcan0,100:700,200:600`** (필터 두 개). VM에서 ID 9개를 보내서 직접 확인했다

| 필터 | 받은 ID | 왜 |
| --- | --- | --- |
| `100:7FF` | `100` | 11비트 전부 비교 → 0x100 하나 |
| `100:3FF` | `100`, **`500`** ❌ | 아래 10비트만 비교 → 0x500(101 0000 0000)도 아래 10비트가 0x100과 같음. 범위가 아니라 엉뚱한 게 들어온다 |
| `100:700,200:600` | `100 101 1FF 200 300 3FF` ✅ | 아래 |

  - `100:700`: 마스크 `700` = 위쪽 3비트만 비교 → 위 3비트가 `001` → **0x100 ~ 0x1FF**
  - `200:600`: 마스크 `600` = 위쪽 2비트만 비교 → 위 2비트가 `01` → **0x200 ~ 0x3FF**
  - 둘을 쉼표로 이으면 "**둘 중 하나라도** 맞으면 받음" → 0x100 ~ 0x3FF
  - 마스크 하나로는 "범위"를 마음대로 못 만든다. 2의 거듭제곱 단위로 끊어지는 범위만 된다 → 필요하면 필터를 여러 개 쓴다
  - M5-7에서 우리 BCM에 이 필터(`CAN_RAW_FILTER`)를 직접 건다: 0x100, 0x200, 0x300만 받기

## 5. 정리

| 도구 | 하는 일 | M5에서 우리가 만들 것 |
| --- | --- | --- |
| `candump` | vcan0의 프레임을 **받아서 보여 줌** (`-l`: 파일로 저장, `,ID:마스크`: 필터) | 소켓으로 **받기** (M5-3, M5-4), 수신 필터 (M5-7) |
| `cansend` | 프레임 **하나를 보냄** | 0x400 **보내기** (M5-6) |
| `canplayer` | 로그 파일을 **시각대로 재생**해서 보냄 | BCM의 **입력으로** 씀 → 시나리오 자동 테스트 (M5-10) |
| `cangen` | **랜덤** 프레임을 계속 보냄 | 관심 없는 ID가 섞여도 안 죽는지 확인, 필터 확인 |

- M5에서 만들 BCM 프로그램 = `candump`(받기) + 우리 판단(M4) + `cansend`(보내기)를 **한 프로그램에** 합친 것
- 그래서 M5를 테스트할 때는 이렇게 쓴다: `canplayer`로 시나리오를 넣고 → 우리 BCM이 받아서 판단 → 0x400을 보내면 → 옆에서 `candump`로 확인
