# 20. 시나리오 로그 데이터 (M3-4)

> 시나리오: `data/scenarios/*.log`, 설명서: `data/scenarios/README.md`
> 생성기: `tools/gen_scenarios.c` (`make scenarios`)
> 실행: `./build/bcm_sim data/scenarios/02_door_open_while_driving.log`

## 1. 시나리오란?

- 한 줄 설명 → BCM 상태 머신(M4)을 검증하기 위한 주행 시나리오. ✅ 구체적으로는 **"이런 주행 상황이 오면(입력 로그) BCM은 이렇게 반응해야 한다(기대 결과)"**를 짝지어 둔 것. 입력은 `.log` 파일, 기대 결과는 `README.md`에 있다
- 왜 M4 상태 머신보다 먼저 만드나? (TDD의 인수 테스트) →
  - **"무엇을 만들어야 하는지"가 먼저 분명해진다.** 시나리오를 쓰다 보면 "문이 열린 채 출발하면?", "신호가 끊기면 몇 ms 뒤에 알아채야 하지?" 같은 질문이 먼저 나온다 → M4-1 상태 전이 표를 설계할 때 빠뜨리는 경우가 줄어든다
  - **완성 기준이 생긴다.** M4를 만든 뒤 4개 시나리오를 돌려서 README의 기대 결과와 같으면 "다 됐다", 다르면 "아직"이다. 코드를 짠 사람의 느낌이 아니라 **미리 정한 기준**으로 판단한다
  - **결과에 맞춰 기대값을 정하는 실수를 막는다.** 코드를 먼저 짜고 나서 기대값을 쓰면, 버그가 있는 출력을 "원래 이런 거구나" 하고 정답으로 적어 버리기 쉽다
  - TDD(테스트 주도 개발)에서 테스트를 먼저 쓰는 것과 같은 생각이다. 단위 테스트가 함수 하나를 검사한다면, **인수 테스트**는 "사용자가 원하는 기능 전체가 되는가"를 검사한다
- 웹으로 치면? → **API 시나리오 테스트 / E2E 테스트의 테스트 데이터.** 예: "회원가입 → 로그인 → 주문 → 결제" 흐름을 요청 순서대로 적어 두고, 각 단계의 기대 응답을 정해 놓는 것 (Postman 컬렉션, Cucumber의 Given-When-Then). 로그 파일 = 요청 순서, README의 기대 BCM 동작 = 기대 응답

## 2. 시나리오 4개

| 파일 | 상황 | 기대 BCM 동작 |
| --- | --- | --- |
| 01_normal_drive | 시동 ON → D → 0→60 km/h 가속 → 정속 → 감속 → 정차 → P → 시동 OFF. 문은 계속 닫힘 | 1.8초(16 km/h) **DRIVING_LOCKED** + 잠금 명령 → 9.5초(0 km/h + P) **IDLE**. 경고음 없음 |
| 02_door_open_while_driving | 40 km/h로 달리다 **4.0~4.9초에 운전석 문 열림**, 5.0초에 닫힘 | 1.8초 DRIVING_LOCKED → **4.0초 WARNING (경고음 ON)** → 5.0초 DRIVING_LOCKED (경고음 OFF) → 9.5초 IDLE |
| 03_signal_timeout | 50 km/h로 달리는 중 **3.0~3.9초에 0x100(차속)만 안 옴**, 다른 메시지는 계속 옴. 4.0초에 다시 옴 | 1.3초 DRIVING_LOCKED → 마지막 차속(2.9초)에서 500ms 지난 **약 3.4~3.5초 타임아웃 → WARNING (Fail-safe)** → 4.0초 복귀 → 7.5초 IDLE |
| 04_invalid_frames | 30 km/h 짧은 주행 중에 깨진 줄, 관심 없는 ID, 짧은 DLC, ID 초과, **차속 무효값(FFFF)**, **기어 무효값(7)**, 우리 BCM 메시지를 끼워 넣음 | 0.8초 DRIVING_LOCKED. 깨진 줄로는 상태가 안 바뀌고 프로그램이 안 죽음. 무효값(1.8초, 2.2초)에 대한 반응은 M4-6에서 결정 |

- 각 시나리오를 실행했을 때의 `read / ok / error` →

| 파일 | read | ok (파싱 성공) | error (형식 오류) | 디스패처 ok / ignored / error |
| --- | --- | --- | --- | --- |
| 01_normal_drive | 318 | 318 | 0 | 318 / 0 / 0 |
| 02_door_open_while_driving | 318 | 318 | 0 | 318 / 0 / 0 |
| 03_signal_timeout | 248 | 248 | 0 | 248 / 0 / 0 |
| 04_invalid_frames | 137 | 133 | 4 | 129 / 2 / 2 |

  - 01, 02: 0~10.5초 106시점 × 메시지 3개 = 318줄
  - 03: 0~8.5초 86시점 × 3 = 258에서 차속 10줄(3.0~3.9초)이 빠져서 248줄
  - 04: 정상 43시점 × 3 = 129줄 + 끼워 넣은 8줄 = 137줄. 형식 오류 4 (`10G7`, `102`, `R`, `garbage`), 디스패처 ignored 2 (`555`, `400`), error 2 (`100#10` 짧은 DLC, `800#00` ID 초과)
  - 지금은 BCM 상태 머신이 없어서 **"기대 BCM 동작"은 아직 확인할 수 없다** → M4에서 이 표를 정답지로 쓴다

## 3. 생성기를 만든 이유

- 손으로 318줄을 쓰면 어떤 문제가? →
  - **16진수 계산을 수백 번** 해야 한다. 가속 구간만 해도 차속이 100ms마다 바뀌니 "16 km/h = 1600 = 0x0640 → `40 06`"을 줄마다 손으로 바꿔야 한다
  - **실수를 찾기 어렵다.** 300줄 중 한 줄의 바이트 순서를 뒤집어도(M0-6 실험 6의 엔디안 버그) 눈으로는 안 보인다
  - **바꾸기 어렵다.** "가속을 3초에서 2초로" 같은 작은 변경에도 수십 줄을 다시 계산해야 한다
  - 반면 생성기는 "4.0~5.0초에 운전석 열림" 같은 **규칙 한 줄**만 쓰면 된다. 사람이 읽는 것도 규칙이라 리뷰하기 쉽다
- `can_set_bits()`(M2-2)를 쓴 부분 → `emit_tick()` 안에서 **상태 값을 정의서 위치에 넣을 때** 쓴다

```c
can_set_bits(data, IGN_STATE_START_BIT, IGN_STATE_LENGTH, s->ign);      /* 시동 → 0x300 bit 0~1 */
can_set_bits(data, GEAR_START_BIT, GEAR_LENGTH, s->gear);               /* 기어 → 0x300 bit 8~10 */
can_set_bits(data, 0, 5, s->doors);                                     /* 도어 5개 → 0x200 bit 0~4 */
can_set_bits(data, VEHICLE_SPEED_START_BIT, VEHICLE_SPEED_LENGTH, s->speed);  /* 차속 → 0x100 bit 0~15 */
```

  - M1-3 연습 문제 F(손으로 프레임 만들기)를 코드가 대신 한다. 디코더(M2-3~5)가 쓰는 **같은 상수**(`signals.h`)로 넣으므로, 생성기와 디코더가 정의서를 똑같이 해석한다
  - M2-2에서 만든 인코더를 **실제로 처음 쓴 곳**이다 (원래 용도인 BCM_STATUS 송신은 M4-8)
- 시나리오 파일을 손으로 고치지 말고 생성기를 고치라고 한 이유 →
  - **"진짜 원본"이 하나여야 한다.** 생성기가 원본이고 `.log` 파일은 결과물이다. 파일을 손으로 고치면 다음에 `make scenarios`를 할 때 **손으로 고친 내용이 덮어써져서 사라진다**
  - 생성기를 고치면 **변경 이유가 코드에 남는다** (예: `s->doors = (i >= 40u && i < 50u) ? ...`). 로그 파일 diff는 16진수 숫자만 바뀌어서 뭘 바꿨는지 알기 어렵다
  - 정의서가 바뀌어 신호 위치가 달라져도, `signals.h` 상수만 고치고 `make scenarios`를 다시 하면 4개 파일이 **한 번에** 새 정의서대로 바뀐다
  - 웹으로 치면 Swagger 스펙에서 생성한 코드를 손으로 고치지 않는 것, 또는 DB 마이그레이션 결과가 아니라 **마이그레이션 스크립트**를 고치는 것과 같다

## 4. 직접 확인하기

- 01에서 4.0~6.0초의 차속 줄을 찾아서, 60 km/h가 맞는지 손으로 해석해 보기 (M1-3 방식) →

```
(4.000000) vcan0 100#7017000000000000      ← 4.0, 5.0, 6.0초 모두 같은 줄

1) 바이트 나누기   data[0] = 0x70, data[1] = 0x17
2) 정의서         VehicleSpeed: start 0, 길이 16, Little-endian, ×0.01
3) raw 만들기     data[1]을 큰 자리로 → 0x1770
                 0x17 × 256 + 0x70 = 23 × 256 + 112 = 5888 + 112 = 6000
4) 물리값         6000 × 0.01 = 60.00 km/h ✅
```

  - 찾는 방법: `grep "^(5.000000) vcan0 100" data/scenarios/01_normal_drive.log`
- 02에서 운전석 문이 열린 줄은 몇 초부터 몇 초까지? → **4.0초부터 4.9초까지** (`200#0100000000000000`이 10줄). 5.0초부터 다시 `200#00...`(전부 닫힘)

```
(3.900000) vcan0 200#0000000000000000   ← 닫힘
(4.000000) vcan0 200#0100000000000000   ← 열림 시작 (data[0] = 0000 0001 → bit 0 = FL)
...
(4.900000) vcan0 200#0100000000000000   ← 마지막 열림
(5.000000) vcan0 200#0000000000000000   ← 닫힘
```

  - 생성기 규칙 `(i >= 40u && i < 50u)` → i = 40 ~ 49 → 4.0 ~ 4.9초. `<`라서 50(5.0초)은 포함 안 됨
  - 찾는 방법: `grep "vcan0 200#01" data/scenarios/02_door_open_while_driving.log`
- 03에서 0x100 줄이 빠진 구간 → **3.0초 ~ 3.9초** (10줄). 2.9초에 마지막 차속(`100#8813...` = 0x1388 = 5000 = 50.00 km/h), 4.0초에 다시 나타남. 그 사이에도 0x300, 0x200은 100ms마다 계속 온다 → "ESC만 죽은" 상황

```
(2.900000) vcan0 100#8813000000000000   ← 마지막 차속
(3.000000) vcan0 300#...                ← 차속 없음
(3.000000) vcan0 200#...
...
(3.900000) vcan0 200#...                ← 여기까지 차속 없음
(4.000000) vcan0 300#...
(4.000000) vcan0 200#...
(4.000000) vcan0 100#8813000000000000   ← 차속 복귀
```

## 5. 03 신호 끊김 — 타임아웃 계산

- 마지막 차속 메시지는 몇 초? → **2.9초** (`100#8813...` = 50.00 km/h)
- 타임아웃 500ms면 언제 "끊김"을 알아채야 하나? → 마지막 수신 2.9초 + 500ms = **3.4초**. 정확한 시점은 M4-6에서 비교를 `>`로 할지 `>=`로 할지에 따라 다르다

```
지금 시각 - 마지막 수신 시각 = 지난 시간
   3.3초  -  2.9초          = 400ms   → 아직 OK
   3.4초  -  2.9초          = 500ms   → ">= 500"이면 여기서 타임아웃
   3.5초  -  2.9초          = 600ms   → "> 500"이면 여기서 타임아웃
```

  - 그런데 **시간은 프레임이 올 때만 흐른다.** 파일 모드에서는 "지금 시각"을 다음 프레임의 타임스탬프로 안다. 3.4초에 0x300, 0x200 프레임이 오니까 그때 검사하면 알아챌 수 있다 (차속이 끊겨도 다른 메시지가 계속 와서 다행)
  - 만약 **모든 메시지가 끊기면?** 프레임이 하나도 안 오니 "지금 시각"을 알 수 없어서 타임아웃을 못 잡는다 → M5-8에서 프레임이 없어도 10ms마다 깨어나는 이벤트 루프(`poll`)로 해결한다
- 디스패처의 `speed_rx_ms`(M2-6)가 여기서 하는 역할 → **"차속을 마지막으로 정상 수신한 시각"**을 기억한다. 2.9초에 50 km/h를 받으면 `speed_rx_ms = 2900`. 3.0~3.9초에는 차속 프레임이 없으니 **2900에서 안 바뀐다**. M4 상태 머신은 매번 `now_ms - speed_rx_ms`를 계산해서 500ms를 넘으면 "차속 모름"으로 판단한다

```
시각     차속 프레임    speed_rx_ms    now - rx    판단
2.9초    ✅ 50 km/h     2900           0          OK
3.0초    ❌              2900           100        OK
3.4초    ❌              2900           500        타임아웃 (>= 기준)
3.9초    ❌              2900           1000       타임아웃
4.0초    ✅ 50 km/h     4000           0          복귀
```

  - 이 값이 없으면 BCM은 마지막 차속 **50 km/h를 계속 믿는다.** 실제로는 ESC가 죽었는데 "50 km/h로 잘 달리는 중"이라고 착각하는 것 → 그래서 M2-6에서 "깨진 프레임에는 `rx_ms`를 갱신하지 않는다"가 중요했다

## 6. 04 이상한 프레임 — 세 단계 검사 복습

| 끼워 넣은 줄 | 어디서 걸리나 (파서 / can_frame_is_valid / 디코더 / 디스패처 IGNORED / 통과) |
| --- | --- |
| `555#AABBCCDD` | **디스패처 IGNORED** — 문법·값 다 정상이지만 관심 없는 ID (`switch`의 `default`) |
| `100#10` | **디코더** — 문법·값 정상(DLC 1)이지만 차속은 최소 2바이트 → `decode_vehicle_speed()`가 false → 디스패처 ERROR, 이전 차속 유지 |
| `100#10G7...` | **파서** — `G`는 16진수 아님 → `PARSE_ERR_DATA` (CanFrame이 안 만들어짐) |
| `800#00` | **can_frame_is_valid** — 문법은 맞아서 파서 통과(`id = 0x800`), 하지만 Standard ID 최대 0x7FF 초과 → 디스패처 입구에서 ERROR |
| `100#FFFF...` | **통과** — 모든 검사를 통과하고 디스패처 OK. 신호 값이 무효(0xFFFF)라 `speed.valid = false`로 **상태에 반영**된다 ("센서 고장"이라는 정보를 받은 것, M2-6 4번) |
| `garbage line` | **파서** — `(`로 시작하지 않음 → `PARSE_ERR_TIMESTAMP` |
| (추가) `100#102` | **파서** — 홀수 자리 → `PARSE_ERR_DATA` |
| (추가) `100#R` | **파서** — Remote Frame → `PARSE_ERR_UNSUPPORTED` |
| (추가) `400#0101...` | **디스패처 IGNORED** — 우리 BCM이 보낸 메시지라 입력으로 안 씀 |
| (추가) `300#0207...` (기어 7) | **통과** — 디스패처 OK, `gear = GEAR_INVALID`로 반영 |

```
"줄"
 ↓ ① 파서 (M3-2) ............ 10G7, 102, R, garbage 탈락  → 실행 결과 "error 4"
 ↓ ② can_frame_is_valid ...... 800#00 탈락               ┐
 ↓ ③ 디코더 (M2) ............ 100#10 탈락               ┘ → 디스패처 "error 2"
 ↓ ④ 디스패처 라우팅 .......... 555, 400 무시              → 디스패처 "ignored 2"
 ↓ 통과 → 상태 반영 ........... FFFF(무효), 기어 7(무효) 포함 → 디스패처 "ok 129"
```

  - 실행 결과 `read 137, ok 133, error 4` / 디스패처 `ok=129 ignored=2 error=2`와 정확히 맞는다
  - 무효값(`FFFF`, 기어 7)은 **"걸러야 할 쓰레기"가 아니라 "받아야 할 정보"**라서 마지막까지 통과한다. 어떻게 반응할지는 M4(상태 머신)가 정한다
- 04를 M5 재생에 못 쓰는 이유 → 리눅스 can-utils 도구(`canplayer`, `log2long`)는 **형식이 깨진 줄을 만나면 멈춘다.** 컨테이너에서 `log2long`으로 돌려 보니 137줄 중 **56줄**(첫 깨진 줄 `100#10G7...` 직전)까지만 읽고 `read: incomplete CAN frame`으로 멈췄다
  - M5에서는 `canplayer`로 vcan0에 **실제 CAN 프레임**을 보내는데, 깨진 글자는 애초에 CAN 프레임으로 만들 수 없다 (실제 버스에는 "글자가 깨진 프레임" 같은 게 없다 — 진짜 버스 오류는 CRC/Error Frame으로 하드웨어가 처리, M1-1)
  - 그래서 04는 **"로그 파일이 깨졌을 때 우리 파서가 안 죽는가"**를 보는 **파일 모드 전용** 테스트이고, M5 재생에는 01~03만 쓴다
  - 04 중에서도 문법이 맞는 이상한 값(`100#10`, `FFFF`, 기어 7, `555`, `400`)은 진짜 CAN 프레임으로 보낼 수 있다 → M5에서 필요하면 이것만 모은 재생용 시나리오를 따로 만든다 (`800#00`은 Standard ID 범위 밖이라 실제 버스에서 어떻게 처리되는지 M5에서 확인 필요)

```
tools/gen_scenarios.c:3:41: error: '/*' within block comment [-Werror,-Wcomment]
    3 |  *   make scenarios   → data/scenarios/*.log 4개를 다시 만든다
      |                                       ^
```

  - **원인:** C의 블록 주석은 `/*`로 시작해서 `*/`로 끝난다. 주석 안에 쓴 경로 `scenarios/*.log`에 **`/*`가 들어 있어서**, 컴파일러가 "주석 안에서 또 주석을 시작하려 한다"고 경고했다 (`-Wcomment`). C 주석은 겹쳐 쓸 수 없어서(중첩 불가) 실수일 가능성이 크다는 경고다

```
/* ... data/scenarios/*.log ... */
                     ↑↑
                     컴파일러 눈에는 "/*" = 새 주석 시작?
```

  - 우리 Makefile은 **`-Werror`**(경고 = 에러)라서 경고 하나로 빌드가 멈췄다 (M0-6 실험 1). 원래 경고만 나고 넘어갔을 일이다
  - **해결:** 주석 문장을 `data/scenarios 폴더의 .log 파일`로 바꿔 `/*`가 안 생기게 했다
  - **배운 점:**
    - 주석에 경로나 패턴(`*.log`, `src/*.c`)을 쓸 때 `/*`, `*/`가 생기지 않게 조심한다. 꼭 써야 하면 `//` 한 줄 주석을 쓰거나 띄어 쓴다 (`data/scenarios/ *.log`)
    - `*/`가 생기면 더 위험하다: 주석이 **그 자리에서 끝나 버려서** 뒷부분이 코드로 읽히고 컴파일 에러가 난다
    - `-Werror` 덕분에 "그냥 넘어갈 뻔한 문제"를 바로 알게 됐다. 이 경우는 무해했지만, 진짜 주석 실수(주석이 일찍 끝나서 코드가 사라지는 등)를 잡아 주는 경고다
    - 같은 이유로 `Makefile`의 `# ... *.log` 주석은 괜찮다 (Makefile 주석은 `#`이라 `/*`가 특별한 뜻이 없음)
