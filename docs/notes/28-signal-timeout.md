| | `debounce_update()` (M4-5) | 복귀 판단 (M4-6) |
| --- | --- | --- |
| 같은 점 | **N번 연속**이어야 인정, N에서 멈춰서 넘침 방지, 인정하면 상태를 바꿈 | ← 같음 |
| 세는 것 | 같은 **값**(열림/닫힘)이 연속 몇 번 | **정상 프레임**이 연속 몇 개 |
| 끊기면 | 다른 값이 오면 **1부터** (그 값이 새 후보의 1번째) | 문제(끊김, 무효)가 생기면 **0부터** (문제는 "정상 1개"가 아니니까) |
| 방향 | 양쪽 다 신중 (열림 → 닫힘, 닫힘 → 열림 둘 다 3번) | **한쪽만** 신중 (못 믿게 되는 건 바로, 다시 믿는 것만 3번) |
| 새 프레임이 아닐 때 | `update_doors()`가 아예 안 부름 | 함수 안에서 **아무것도 안 함** (← 여기서 막혔다) |
- 막혔던 곳 / 처음에 틀렸던 것 → **"새 프레임이 아닐 때 0으로 되돌리는 `else`"** 때문에 두 번 실패했다

| 시도 | 코드 | 결과 |
| --- | --- | --- |
| 1번째 | `if (timed_out) 0` / `else if (new_frame) ++` / **`else 0`** | 6개 실패. `value_valid`도 안 봄 |
| 2번째 | `new_frame` 안에 `value_valid` 확인 + N에서 멈추기 추가, 하지만 바깥 **`else 0`은 그대로** | 같은 6개 실패 |
| 3번째 | 바깥 `else` **삭제** | ✅ 전부 통과 |

  - 왜 문제였나: `bcm_step`은 0x300, 0x200 프레임 때도 불린다. 그때 차속 입장에서는 "새 프레임 아님" → `else`로 가서 센 것을 지웠다 → 0x100 사이마다 지워져서 **영원히 1을 못 넘었다**
  - 핵심: 새 프레임이 **안 온 것**은 "문제"가 아니라 "**아직 소식 없음**"이다. 진짜 문제(500ms 끊김)는 `timed_out`이 따로 잡는다 → 그 사이에는 **아무것도 안 하고 기다린다**
  - M4-5 3번의 "판단 횟수 vs 프레임 수" 함정, M4-6 테스트 도우미 `tick_step`의 함정과 **같은 뿌리**: 이 프로그램은 **모든 프레임마다** 판단하니까, "내 신호와 상관없는 판단"이 끼어든다는 걸 항상 생각해야 한다
  - 2번째 시도에서 실패 결과가 **완전히 똑같았던** 게 단서였다. 고친 부분(무효값 처리)은 맞았지만 원인(`else`)을 안 건드려서 결과가 안 바뀐 것

## 1. 시나리오 03 로그 읽기

```
[   3.500s] WARN  신호 끊김: 차속 (마지막 수신 2.900s)
[   3.500s] INFO  STATE DRIVING_LOCKED -> WARNING (T5: 신호 이상 (Fail-safe))
[   4.200s] INFO  신호 복귀: 차속 (정상 프레임 3개 연속)
[   4.200s] INFO  STATE WARNING -> DRIVING_LOCKED (T9: 경고 원인 해소 (신호 정상, 문 닫힘), 잠금 상태로)
```

- M4-3 때 로그 (`T5: 신호 이상` / `T9: 문 닫힘, 잠금 상태로 복귀`)와 비교해서 나아진 점 →

| | M4-3 | M4-6 |
| --- | --- | --- |
| 무엇이 끊겼나 | "신호 이상"뿐 (시동? 차속? 도어?) | **`차속`**이라고 이름이 나온다 |
| 언제부터 | 모름 | **마지막 수신 2.900s** → 600ms 동안 안 왔다는 걸 바로 계산 가능 |
| 끊김인가 무효값인가 | 구별 안 됨 | `신호 끊김` / `신호 이상: 차속 무효값 (0xFFFF)`로 따로 (시나리오 04) |
| 언제 돌아왔나 | 상태 전이로만 짐작 | `신호 복귀: 차속` 줄이 따로 있다 |
| 복귀 이유 | `T9: 문 닫힘` ← **틀린 말** (문은 처음부터 닫혀 있었다) | `T9: 경고 원인 해소 (신호 정상, 문 닫힘)` |

  - 정비사가 로그만 보고 "**차속 센서 쪽** 배선이나 ESC(차속을 보내는 제어기)를 확인해야겠다"를 바로 알 수 있다. 고장 진단에서는 "무엇이 / 언제 / 얼마나"가 핵심
  - M4-3의 T9 이유 문구는 문 열림(T6)으로 WARNING에 왔을 때만 맞는 말이었다. T5(신호 이상)로 왔을 때도 같은 T9로 돌아가니, 이유를 **두 경우 다 맞게** 고쳤다 (26번 노트 2번의 "조건을 바꾸면 이유 문구가 거짓말을 한다"와 같은 문제)
  - 실제 차에서는 이런 정보를 **DTC**(Diagnostic Trouble Code, 고장 코드, 예: `U0121 ABS/ESC 통신 끊김`)로 저장해서 정비소 진단기로 읽는다. 이 로그가 그 역할의 작은 버전
- 차속이 4.0초부터 다시 오는데 복귀가 4.2초인 이유 → 바로 못 믿기 때문에 🔺 (맞다. "얼마나" 기다리는지까지 적으면) 한 번 끊겼던 신호는 **정상 프레임 3개 연속**(`BCM_SIGNAL_RECOVERY_COUNT`)을 확인해야 다시 믿는다

```
시각     차속 프레임   good_count   믿나?
4.0초    옴 (정상)     1            아직
4.1초    옴 (정상)     2            아직
4.2초    옴 (정상)     3 ✅         복귀 → T9
```

  - 4.0초 프레임 하나만 보고 믿으면, 접촉 불량으로 다시 끊길 수 있다 (시나리오 07). 3개 연속(200ms) 잘 오는 걸 보고 "이제 안정적이다"라고 판단하는 것
  - 대가: 진짜로 고쳐졌어도 **200ms 늦게** 경고가 꺼진다. 경고가 조금 더 울리는 건 안전한 쪽이라 괜찮다
- `WARN`과 `INFO`를 나눠 쓴 기준 → **"문제가 생겼다"는 WARN, "정상으로 돌아왔다 / 정상 동작"은 INFO** (21번 노트 2번의 레벨 기준)

| 로그 | 레벨 | 이유 |
| --- | --- | --- |
| `신호 끊김: 차속` | **WARN** | 고장이 의심되는 **문제**. 하지만 프로그램은 계속 돈다 (ERROR는 "더 진행 불가"일 때) |
| `신호 이상: 차속 무효값` | **WARN** | 상대 제어기가 "모름"을 보냈다 = 문제 |
| `신호 복귀: 차속` | INFO | 좋은 소식, 상태 변화 기록 |
| `STATE ... -> WARNING` | INFO | BCM이 **설계대로 정상 동작**한 것 (경고 상태로 간 건 BCM이 할 일을 한 것이지, BCM의 문제가 아니다) |

  - 그래서 `-l warn`으로 실행하면 `신호 끊김`, `신호 이상`만 남는다 → "무엇이 고장 났나"만 빠르게 볼 수 있다
  - 웹으로 치면: 외부 API 타임아웃은 WARN, 서킷 브레이커가 열린 건 INFO(설계대로 동작), 복구도 INFO

## 2. 시나리오 07: 들락날락하는 신호

| 시각 | 0x100 | 예상: 차속을 믿나 / BCM 상태 | 실제 |
| --- | --- | --- | --- |
| 3.0초 | 옴 | | 믿음 (2.9초에 이어 정상) / DRIVING_LOCKED |
| 3.6초 | 옴 (600ms 만에) | | 같은 3.6초의 **0x300 판단**에서 600ms 초과 → **못 믿음** → **WARNING (T5)**. 바로 뒤 0x100이 와서 `good_count` = 1 |
| 4.2초 | 옴 | | 0x300 판단에서 또 600ms 초과 → `good_count` = **0** (처음부터) → 0x100이 와서 다시 1. **WARNING 유지** (4.8, 5.4초도 똑같이 반복) |
| 6.0 ~ 6.2초 | 100ms마다 옴 | | 6.0초 1 → 6.1초 2 → **6.2초 3** → **복귀** → DRIVING_LOCKED (T9) |

- 3.6 ~ 5.4초에 차속이 한 프레임씩 오는데도 복귀하지 않는 이유 → 정상 프레임 3개가 "**연속으로**" 와야 한다. 프레임 사이가 600ms라서 다음 프레임이 오기 **전에 또 끊김**(500ms 초과)이 되고, 그때 `good_count`가 **0으로** 돌아간다 → 3.6, 4.2, 4.8, 5.4초에 1씩 쌓이는 게 아니라 **매번 1에서 끊긴다**

```
시각       3.6        4.2        4.8        5.4        6.0  6.1  6.2
           │          │          │          │          │    │    │
0x100      ●          ●          ●          ●          ●    ●    ●
good_count 1 ─(끊김)→0 1 ─(끊김)→0 1 ─(끊김)→0 1 ─(끊김)→0 1    2    3 ✅
```

  - 누적으로 셌다면 4.8초에 3이 돼서 복귀했다가, 5.4초 직전에 또 끊겨 경고 → 다시 들락날락. "연속"이어야 **진짜로 안정된** 신호만 믿는다 (27번 노트의 "연속 vs 누적"과 같은 이야기)
- 실험: `include/bcm.h`의 `BCM_SIGNAL_RECOVERY_COUNT`를 `1u`로 바꾸고 `make` 후 시나리오 07을 실행 → 상태 전이 횟수, `STATE` 로그 모양 → (끝나면 `3u`로 되돌리고 `make test`) → (복사본으로 확인) 상태 전이 **12회** (3이면 4회)

```
[   3.600s] STATE DRIVING_LOCKED -> WARNING (T5: 신호 이상 (Fail-safe))
[   3.600s] STATE WARNING -> DRIVING_LOCKED (T9: ...)        ← 같은 3.6초에 바로 복귀
[   4.200s] STATE DRIVING_LOCKED -> WARNING (T5: ...)
[   4.200s] STATE WARNING -> DRIVING_LOCKED (T9: ...)
[   4.800s] ... (같은 모양이 4.8, 5.4, 6.0초에 반복)
```

  - 같은 시각 안에서 **0x300 판단 때 경고 → 0x100 판단 때 복귀**. 프레임 하나에 바로 믿으니까 끊길 때마다 켜졌다 꺼진다
- 실제 차였다면 복귀가 1프레임일 때 운전자는 무엇을 듣게 되나 → 0.6초마다 **아주 짧게 "삑"** 하고 끊기는 경고음이 5번 반복된다. 같은 시각 안에서 켜졌다 꺼지니 경고음이 거의 0초짜리라, 실제로는 **"틱, 틱" 하는 잡음**처럼 들리거나 아예 못 들을 수도 있다
  - 그러면 운전자는 "뭔가 고장 났나?" 하고 헷갈리거나, 반대로 무시하게 된다 → 경고의 의미가 사라진다
  - 3프레임 복귀면: 3.6 ~ 6.2초 동안 **계속** 울린다 → "차속 신호에 문제가 있다"는 걸 분명히 전한다
  - 계기판도 같다: 0x400의 `BcmState`가 1 ↔ 2로 계속 바뀌어서, 경고등이 깜빡깜빡

## 3. 걸림은 빠르게, 풀림은 신중하게

| | 걸림 (믿음 → 못 믿음) | 풀림 (못 믿음 → 믿음) |
| --- | --- | --- |
| 조건 | 빠르게: 끊김(500ms 초과) 또는 무효값(0xFFFF)이면 **그 판단에서 바로** | 신중하게: 정상 프레임 **3개 연속** (`BCM_SIGNAL_RECOVERY_COUNT`) |
| 늦어지는 시간 | 더 기다리지 않음 (끊김은 이미 500ms를 기다린 뒤, 무효값은 0ms) | 신호가 돌아온 뒤 **200ms** (100ms 주기 × (3 - 1)) |
| 틀리면 어느 쪽으로 틀리나 | 너무 빨리 걸면 → 경고가 **더 울림** (안전한 쪽) | 너무 빨리 풀면 → 고장 난 신호를 **다시 믿음** (위험한 쪽) |
| 시나리오 03 | 3.5초 (2.9 + 600ms) | 4.0초에 돌아왔지만 **4.2초**에 복귀 |

- 둘의 속도를 일부러 다르게 한 이유 → **틀렸을 때의 대가가 다르기 때문.** 안전한 쪽으로 가는 건 빨리, 위험한 쪽으로 가는 건 천천히
  - 걸림(못 믿음)으로 가면 BCM은 경고를 울리고 마지막 값에 기대지 않는다 = **안전 상태**. 잘못 걸어도 경고가 조금 더 울릴 뿐이다 → 망설일 이유가 없다
  - 풀림(다시 믿음)으로 가면 그 신호 값으로 다시 판단한다. 아직 고장 중인데 풀어 버리면 **틀린 값을 믿고** 문을 잠그거나 경고를 끈다 → 확신이 생길 때까지 기다린다
  - 생활 비유: 화재경보기는 연기를 조금만 감지해도 **바로** 울리지만, 끌 때는 연기가 완전히 빠졌는지 **확인하고** 끈다. 병원에서 열이 나면 바로 격리하고, 해제는 며칠 동안 정상인 걸 보고 한다
  - 웹으로 치면 **서킷 브레이커**: 실패가 쌓이면 바로 OPEN(차단), 다시 열 때는 HALF-OPEN에서 요청 몇 개를 **시험해 보고** 성공해야 CLOSED(정상). Resilience4j의 `permittedNumberOfCallsInHalfOpenState`가 우리의 `BCM_SIGNAL_RECOVERY_COUNT`와 같은 역할
- 이게 M4-4의 히스테리시스와 어떻게 닮았나 → 둘 다 **"들어가는 조건과 나오는 조건을 다르게"** 해서 경계에서 왔다 갔다 하지 않게 한다

| | 들어가는 조건 | 나오는 조건 | 그 사이에서는 |
| --- | --- | --- | --- |
| 자동 잠금 (M4-4) | 15 km/h 이상 | 0 km/h + P | 지금 상태 유지 |
| 신호 못 믿음 (M4-6) | 끊김 1번 | 정상 **3개 연속** | 지금 상태 유지 (못 믿음이면 계속 못 믿음) |

  - 다른 점: M4-4는 **값**(속도)의 기준선이 둘이고, M4-6은 **시간(횟수)**의 기준이 둘이다. 그래서 M4-6은 M4-5 디바운싱(횟수)과 히스테리시스(들어감 ≠ 나옴)를 **합친** 모양
  - 효과도 같다: 시나리오 05(속도 흔들림)에서 잠금이 16번 → 1번, 시나리오 07(신호 들락날락)에서 상태 전이가 12번 → 4번. 둘 다 "**흔들리는 입력이 상태를 흔들지 않게**"
  - 그리고 둘 다 상태(`state`, `latched`)를 **기억**해야 가능하다 (4번 질문)

## 4. "못 믿음"을 기억해야 하는 이유

M4-3까지는 판단할 때마다 "지금 500ms 안에 왔나?"만 계산했다 (기억 없음). M4-6에서 `BcmSignalHealth.latched`를 추가했다.

- 기억 없이 계산만 하면 복귀 조건 "3개 연속"을 왜 만들 수 없나 → `VehicleInputs`에는 **지금 값과 마지막 수신 시각**만 있다. "**과거에** 끊긴 적이 있나?", "그 뒤로 정상 프레임이 **몇 개** 왔나?"는 어디에도 없다 → 판단할 때마다 처음부터 계산하면 이걸 알 길이 없다

```
4.0초 차속 프레임 도착 (2.9초 이후 처음)

기억 없이 (M4-3):  "지금 500ms 안에 왔나?" → 방금 왔으니 예 → 바로 믿음 (4.0초 복귀)
                    → 1.1초 동안 끊겼었다는 사실을 이미 잊어버렸다

기억 있게 (M4-6):  latched = true (3.5초에 걸어 둠), good_count = 0
                    "걸려 있으니 세자" → good_count = 1 → 아직 못 믿음
```

  - "지금 정상인가"는 **지금 입력**만 보면 되지만, "**최근에 계속** 정상이었나"는 **지나온 시간**을 알아야 한다 → 기억(상태)이 필요하다
  - 같은 이유로 디바운싱(M4-5)은 `candidate`, `count`를, 히스테리시스(M4-4)는 `state`를 기억한다. "연속", "이전에 어땠나"가 들어가는 규칙은 전부 기억이 있어야 만들 수 있다
  - 그래서 이 기억은 매번 새로 만드는 `BcmOutputs`가 아니라, 판단과 판단 사이에 살아남는 **`BcmContext`**에 있다 (24번 노트 2번)
  - Java로 치면 stateless 함수로는 안 되고, 필드에 상태를 들고 있는 객체(서킷 브레이커의 state, failure count)가 필요한 것
- 한 번도 못 받은 신호를 "끊김"으로 걸지 않은 이유 (시동 직후) → "**아직 안 옴**"과 "**왔다가 끊김**"은 다른 상황이기 때문

| | 아직 한 번도 안 옴 | 왔다가 끊김 |
| --- | --- | --- |
| 언제 | 시동 직후 (다른 제어기가 켜지는 중) | 주행 중 배선, 제어기 고장 |
| 고장인가 | **아니다** (정상적인 시작 과정) | 고장 의심 |
| BCM | "모름" → IDLE에서 T2로 대기 | "못 믿음"에 걸고 경고 (T5), WARN 로그 |
| 첫 정상 프레임이 오면 | **바로 믿음** | 3개 연속이어야 믿음 |

  - 만약 시작부터 "끊김"으로 걸었다면: 시동을 걸 때마다 `WARN 신호 끊김: 차속`, `도어`, `시동` 로그가 쏟아지고(`test_signal_not_received_is_not_lost`가 막는 것), 첫 프레임이 와도 3개를 기다려야 해서 매번 200ms 동안 판단을 못 한다
  - 23번 노트의 T2("IDLE에서 신호를 모르면 그냥 대기")와 같은 생각. 시동 직후의 "모름"은 이상한 게 아니라 **당연한** 상태라서, 경고하지 않고 조용히 기다린다
  - 도어 디바운싱의 "첫 프레임은 바로 인정"(27번 노트 4번)과도 같은 이유: 비교할 **이전 값이 없으면** 의심할 근거도 없다

## 5. 기능 안전 (용어 정리)

- Fail-safe vs Fail-operational →

| | Fail-safe | Fail-operational |
| --- | --- | --- |
| 고장 나면 | 기능을 멈추거나 줄이고 **안전한 상태로** 간다 | 기능을 **계속** 해야 한다 (멈추는 것 자체가 위험) |
| 예 | 철도 신호 고장 → 빨간불, 엘리베이터 정전 → 브레이크 걸림, **이 BCM** (신호를 모르면 경고) | 전자식 조향(steer-by-wire), 자율주행 중 브레이크: 고장 났다고 멈추면 사고 |
| 어떻게 | 고장을 **알아채는 것**(감지)이 핵심 | 부품을 2~3개 두는 **이중화**(redundancy), 하나가 고장 나도 나머지로 계속 |

  - 이 BCM이 Fail-safe로 충분한 이유: 경고를 울리고 잠금을 유지하는 건 언제든 할 수 있고, 그것만으로 위험이 생기지 않는다. 차를 움직이는 건 BCM이 아니라 운전자
- 안전 상태(safe state): 이 BCM의 안전 상태는 무엇인가 → **신호를 믿을 수 없을 때 들어가는 상태 = 경고를 울리고 잠금은 그대로 두는 것**

| 지금 상태 | 신호를 못 믿게 되면 | 왜 안전한가 |
| --- | --- | --- |
| DRIVING_LOCKED | **WARNING** (T5): 경고음 ON, 잠금 유지 | 운전자에게 알리고, 달리는 중에 갑자기 잠금을 풀지 않는다 |
| WARNING | 그대로 (T8) | 이미 안전 상태 |
| IDLE | 그대로 (T2) | 아무것도 안 하는 것 = 모르는 채로 잠그지 않는 것 (23번 노트 7번) |

  - "안전 상태"는 "아무것도 안 하기"가 아닐 수도 있다. 차마다, 기능마다 **설계로 정한다**. 이 프로젝트에서는 `fsm-design.md`의 T2, T5, T8, `default:`(RESET → IDLE)가 그 결정
- ISO 26262, ASIL을 한 줄씩 →
  - **ISO 26262**: 자동차 전기/전자 시스템의 **기능 안전 국제 표준**. "고장이 나도 사람이 다치지 않게"를 설계 → 개발 → 테스트 → 생산까지 어떻게 증명하는지 정해 둔 규칙 (항공의 DO-178C, 산업 설비의 IEC 61508과 같은 계열)
  - **ASIL** (Automotive Safety Integrity Level): 기능마다 매기는 **위험 등급**. **A < B < C < D** 순으로 엄격하고, 안전과 상관없는 건 **QM**(일반 품질 관리)
    - 등급은 세 가지로 정한다: **심각도**(다치면 얼마나 크게), **노출도**(그 상황이 얼마나 자주), **제어 가능성**(운전자가 피할 수 있나). 이 분석을 HARA(위험 분석)라고 한다
    - 예: 에어백, 브레이크, 조향은 높은 등급(C, D), 실내등은 QM. 도어 잠금이나 경고 같은 바디 기능은 보통 낮은 등급(QM ~ A/B 정도)으로 다뤄지는 경우가 많다
    - 등급이 높을수록 요구가 많아진다: 테스트 커버리지 기준, 코딩 규칙(MISRA C), 독립된 검토, 이중화 등
  - 이 프로젝트는 표준을 따르는 건 아니지만, Fail-safe, 타임아웃 감지, 경계값 테스트, 설계 문서와 코드의 1:1 대응 같은 **사고방식**은 같다
- FTTI(Fault Tolerant Time Interval): 이 프로젝트에서 "고장이 나서 알아채기까지" 걸리는 최대 시간은? → **약 600ms**
  - 용어: **FTTI** = 고장이 생긴 뒤 **사고(위험)로 이어지기 전까지 남은 시간**(시간 예산). 그 안에 **알아채고(FDTI)** + **대응해서 안전 상태로 가야(FRTI)** 한다 → FDTI + FRTI < FTTI
  - 이 BCM의 "알아채기까지"(FDTI):

```
2.9초  마지막 차속 프레임 → 직후 차속 제어기 고장
3.4초  500ms → 아직 "초과"가 아님
3.5초  다음 판단(0x300)에서 600ms → 끊김 감지 ✅
       = 타임아웃 500ms + 판단 간격 최대 100ms (프레임이 올 때만 판단하니까, fsm-design 8번)
```

  - 대응(FRTI): 감지한 **그 판단에서 바로** WARNING → 경고음 ON (M4-8에서 0x400으로 알리는 것도 다음 100ms 송신 안에)
  - 그래서 "고장 → 경고"까지 최대 약 **700ms**. 이게 이 기능의 FTTI보다 짧아야 한다. 문 열림 경고 정도면 1초 안팎은 충분하다고 볼 수 있지만, 브레이크 같은 기능은 수십 ms 단위가 필요하다 → 그래서 기능마다 타임아웃과 주기를 다르게 정한다
  - 숫자를 줄이려면: 타임아웃을 줄이거나(노이즈에 약해짐), 실시간 모드(M5)처럼 **10ms마다** 판단해서 "판단 간격 100ms"를 줄인다

  - 처음 도우미는 한 칸(100ms)의 시동, 도어, 차속을 **한꺼번에** 넣고 `bcm_step`을 **한 번만** 불렀다. 그러면 차속이 600ms 만에 돌아오는 칸에서, 끊김을 확인할 틈 없이 "방금 왔음"만 보게 된다

```
실제 (프레임마다 판단)              처음 도우미 (한 번에)

3.6초 0x200 → 끊김 유지              → 끊김을 한 번도 못 봄
3.6초 0x100 → 1개째
```

  - 그래서 `test_signal_flapping_stays_warning`이 **엉뚱하게 실패**했다 (코드는 맞았는데 테스트가 실제와 다르게 돌아서). 도우미를 실제 순서대로 고치니 통과
  - 교훈: 테스트의 "가짜 입력"도 **실제 입력의 성질**(순서, 타이밍)을 따라야 한다. 안 그러면 테스트가 실제에서는 없는 상황을 보거나, 실제에서 생기는 상황을 놓친다
  - 같은 이유로 `test_signal_lost_reported`는 "새로 끊김"을 확인할 때 0x300 판단 **하나만** 하고 본다 (그 시각의 0x200 판단에서는 이미 "새로"가 아니니까)
- `test_signal_not_received_is_not_lost`가 지키는 것 → **"아직 안 옴 ≠ 끊김"** 규칙 (4번). 시동 직후 아무 신호도 없을 때 `lost_signals`가 0이고, 규칙은 T2(대기)여야 한다
  - 이 규칙이 깨지면 시동을 걸 때마다 `WARN 신호 끊김: 시동/차속/도어` 로그가 쏟아지고, 계기판에도 이상이 있는 것처럼 보인다
  - 뮤테이션으로 직접 확인한 것 (처음엔 "어느 조건을 지워도 잡는다"고 적었다가, 확인해 보니 **틀려서** 테스트를 보강했다)

| --- | --- | --- |

| `update_health()` 마스크의 `in->*_received &&` 삭제 | 못 잡음 | 못 잡음 (**동등 뮤턴트**) |

  - `return`을 지우면: 아직 안 온 신호가 "끊김"으로 걸린다 → 첫 프레임이 오는 순간 `WARN 신호 끊김`이 찍히고 3개를 기다린다. 그런데 처음 테스트는 **프레임이 하나도 없는 순간**만 봐서, 마스크가 `received`를 확인하는 덕분에 우연히 0이 나왔다 → 첫 프레임 뒤까지 확인하도록 보강
  - 마스크 쪽 조건은 지워도 동작이 **완전히 같다**. `return`이 있는 한 안 받은 신호는 애초에 `latched`가 될 수 없으니까. 이렇게 바꿔도 결과가 같은 돌연변이를 **동등 뮤턴트(equivalent mutant)**라고 하고, 테스트로 잡을 수 없는 게 정상이다. 이 조건은 "혹시 몰라서" 넣어 둔 이중 안전장치
  - 교훈: "이 테스트가 이걸 지킨다"는 말은 **직접 망가뜨려 봐야** 믿을 수 있다 (26번 노트 2번)
